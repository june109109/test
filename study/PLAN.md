# 소단원 구성과 작성 계획

## 범위와 순서

대단원 13개를 **소단원 90개**로 나눕니다. 기본 작성 순서는 아래 번호 순서입니다. 현재 완료 범위와 다음 작성 대상은 이 문서 마지막 진행표와 README에서 확인합니다. 한 소단원의 설명·출처·퀴즈가 모두 갖춰진 뒤 다음 소단원으로 넘어갑니다.

일부러 작은 단위로 나눈 이유는 개념을 읽은 직후 스스로 판단하거나 실험하게 하기 위해서입니다. 예컨대 GIL 설명과 병렬 처리 성능 실험은 별도 소단원입니다. 원문의 ‘고급’ 주제도 삭제하지 않고 해당 소단원에 포함합니다.

| 단계 | 대단원 | 단계가 끝나면 남는 결과물 |
| --- | --- | --- |
| 협업 기준 세우기 | 1 | 리뷰 기준, 질문 양식, 결정 기록, 학습 적용 계획 |
| 실행 원리 이해하기 | 2~3 | 요청 경로 그림, 동시성 비교표, 재현 가능한 측정 기록 |
| 서비스 구현하기 | 4~7 | API 실험, DB 설계·격리 실습, 로그인 흐름, 캐시·타임아웃 예산 |
| 운영·검증하기 | 8~11 | 배포·복구 절차, 관측 대시보드, 테스트·부하 실험 보고서 |
| 종합 설계·습관 만들기 | 12~13 | 용량 추정이 포함된 설계서, 리팩토링·코드 읽기 기록 |

3~11장의 실습은 작은 ‘콘텐츠 목록·상세 조회와 파일 메타데이터 저장 API’를 공통 예제로 확장합니다. 초기에는 표준 라이브러리로 시작하고, 필요한 시점에 FastAPI, PostgreSQL, S3 호환 환경, Redis를 추가할 계획입니다. 12장의 네이버 메인 설계는 실제 네이버 내부 구조를 추측하는 과제가 아니라 공개된 서비스 형태를 바탕으로 한 가상 설계 과제입니다.

## 모든 소단원의 집필 규격

| 구성 | 작성 기준 |
| --- | --- |
| 목표·선수 지식 | 학습 후 설명하거나 수행할 수 있는 행동 2~4개, 필요한 앞 단원 |
| 도입 상황 | 실무에서 만날 법한 구체적인 문제와 제약 |
| 개념 | 용어, 동작 원리, 짧은 예시, 자주 하는 오해 |
| 대안과 설계 판단 | 유사 목적의 방법 비교, 선택 조건, 이익·비용, 선택을 바꿀 신호 |
| 토론 | 토론형은 2~3개 쟁점, 각 입장의 출처·근거와 학습용 반박·재반박 |
| 적용 | 토론 기록 또는 실습의 준비·명령·기대 관찰·실패 해석·정리 절차 |
| 퀴즈 | 기본 확인 2개, 사례 적용 2개, 설계·설명 1개를 기본으로 조정 |
| 별도 해설 | 정답 근거, 오답 이유, 서술형 채점 기준, 복습 위치 |
| 참고 자료 | 표준·공식 문서 우선, 읽을 절과 해당 자료가 뒷받침하는 주장 |

토론의 결론은 ‘항상 A’가 아니라 ‘조건 X에서는 A, 조건 Y에서는 B’로 작성합니다. 상대 입장을 허술하게 만들어 이기지 않고, 실제로 감수해야 할 비용을 비교합니다. 조사에서 확인하지 못한 사람의 의견을 임의로 귀속하지 않습니다.

기술 실습은 Python·라이브러리·서버 버전과 실행 자원, 데이터 규모를 기록합니다. 이론상 예상과 실제 측정을 구분하며 한 번에 주요 변수 하나씩 바꿉니다. 본문을 작성하지 않은 실습은 아직 실행·검증하지 않은 상태입니다.

## 설명을 보완할 지점

아래는 제공된 요약을 확장할 때 반영할 사항입니다. 짧은 도입 그림을 모든 경우에 적용되는 규칙으로 오해하지 않도록 본문에서 조건을 붙입니다.

- HTTP/1.1에도 pipelining은 규격상 존재하지만 브라우저에서 널리 사용되지 않았습니다. ‘항상 한 요청만 전송 가능’과 구분합니다. 브라우저 병렬 연결 수는 고정된 규격값이 아닙니다.
- HTTP/2의 TCP 유실은 순서 있는 바이트 전달을 지연시켜 여러 스트림에 영향을 줍니다. HTTP/3는 이 전달 차원의 스트림 간 HOL을 줄이지만 공유 혼잡 제어·연결 흐름 제어·QPACK 의존성까지 없애지 않습니다. QUIC의 연결 이동도 네트워크·구현 조건이 있습니다.
- ‘GIL 때문에 한 스레드만 실행’은 GIL이 있는 CPython의 Python 코드 실행에 한정해 설명합니다. I/O, GIL을 놓는 확장 모듈, free-threaded 빌드, 프로세스 시작 방식은 구분합니다.
- FastAPI의 동기 경로 함수 실행, AnyIO 스레드 제한, asyncio executor는 같은 풀이라고 가정하지 않습니다. boto3의 max_pool_connections도 전체 동시 요청을 막는 세마포어라고 단정하지 않고 구현·버전을 확인합니다.
- OAuth는 권한 위임이고 OIDC는 인증 계층입니다. 제공된 그림 앞에 인가 요청을 보완하고 PKCE·state·토큰 검증을 포함합니다. client secret은 모든 클라이언트가 사용할 수 있는 값이 아니며 자체 JWT 발급도 필수가 아닙니다.
- DB 연결 수는 워커 수만이 아니라 인스턴스 수, overflow, 배치·관리용 연결을 포함합니다. 풀 크기와 서비스 처리량은 동일하지 않습니다.
- 모든 타임아웃이 총 요청 시간 제한인 것은 아닙니다. Uvicorn의 keep-alive 제한과 애플리케이션 deadline, LB 유휴 제한을 구분합니다.
- 컨테이너 도입과 GitOps 도입, 이미지 pull과 배포 제어 방식은 별개입니다. CPU 개수 API가 quota를 반영하는지는 런타임과 설정을 확인합니다.
- boto3 풀 대기 지표가 기본 제공된다고 가정하지 않습니다. 실제로 연결 획득이 대기하는지부터 확인하고, 계측 가능 범위와 대리 지표를 구분합니다.
- 부하 테스트의 2~3분은 시작점입니다. 워밍업·정상 상태·누수·확장·배치 주기에 따라 더 긴 실험이 필요합니다.
