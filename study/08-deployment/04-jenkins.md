# 8-4. Jenkins 기반 원격 배포

[목차](../README.md) · [정답·해설](04-jenkins-answers.md)

예상 45분. 목표: push 배포의 실패 지점을 나누고, 산출물 동일성·권한·롤백을 설계합니다.

## 1. 전통적인 경로

```text
소스 revision → Jenkins build/test → 버전 있는 artifact
  → scp/rsync로 전송 → SSH 명령 → 서비스 전환 → health 확인
```

Jenkins는 자동화 실행 도구입니다. SSH push만 가능한 제품은 아니며 컨테이너 빌드·배포 API 호출·GitOps용 저장소 갱신도 할 수 있습니다. 여기서는 과거부터 흔히 쓰인 push 배포 패턴을 분석합니다.

## 2. 어디서 버전이 어긋날까

서버마다 다시 빌드하거나 전송 중인 디렉터리를 즉시 서비스하면 파일 일부만 새 버전이 될 수 있습니다. 한 번 만든 불변 산출물을 버전 디렉터리에 전송하고 checksum을 확인한 뒤, 원자적인 포인터/링크 전환이나 서비스 시작 절차로 노출하는 편이 추적하기 쉽습니다.

`rsync`를 썼다는 사실만으로 앱 디렉터리 전체가 transaction처럼 바뀌지는 않습니다. 실행 중 프로세스가 옛 파일을 열고 있는 경우도 생각해야 합니다. 최종 health와 사용자 경로 확인이 필요합니다.

## 3. SSH 자격증명과 실행 권한

CI가 배포 서버에 접근할 수 있으므로 CI 침해가 운영 변경으로 이어질 수 있습니다. 배포 전용 계정·최소 명령 권한·대상 범위·짧은 자격 수명·감사 기록을 고려합니다. host key 검증을 끄면 배포 대상의 신뢰 확인을 잃습니다.

secret은 credential 저장소에서 사용하고 로그·명령 출력·artifact에 포함하지 않습니다. fork/외부 기여의 검증 단계와 운영 credential을 가진 배포 단계를 분리해야 합니다. 이 자료는 실제 SSH 키를 만들거나 서버에 접속해 배포하지 않습니다.

## 4. 실패와 롤백

| 실패 지점 | 관찰 | 대응 예 |
| --- | --- | --- |
| build/test | artifact 생성 실패 | 배포 시작 안 함 |
| 전송 | checksum 불일치/부분 파일 | 새 디렉터리 폐기, 이전 서비스 유지 |
| 시작 | 프로세스 종료/health 실패 | 트래픽 미전환, 로그 조사 |
| 전환 후 | 오류·지연 증가 | 이전 버전 전환, 데이터 호환성 확인 |
| 여러 서버 중 일부 | 버전 혼재 | 배포 상태표·정지/복구 정책 |

이전 바이너리를 되돌려도 DB schema나 이미 처리한 데이터까지 자동 복구되지 않습니다. 되돌릴 수 없는 데이터 변환은 별도 백업·보상·forward fix가 필요합니다.

## 5. 적용 과제

서버 3개 중 두 번째에서 시작이 실패하는 배포 절차를 작성하세요. 첫 번째는 신버전, 나머지는 구버전일 때 요청·DB 호환성·중단 기준·롤백 담당을 어떻게 정할지 적습니다.
