# 8-8. 두 앱 인스턴스의 전환·복구 실습

[목차](../README.md) · [정답·해설](08-rollout-lab-answers.md)

예상 70분. 목표: 진행 중 요청을 보존하며 새 요청 경로를 바꾸고, 관찰한 ‘무중단’의 범위를 수치로 기록합니다.

## 1. 실험 구성과 준비

[실행 코드](../labs/blue_green.py), [원본 결과](../results/blue-green-2026-10-01.json).

Linux/POSIX에서 표준 Python만 사용합니다. 별도 앱 프로세스 두 개와 교육용 HTTP 프록시를 loopback 임시 포트로 띄웁니다. 프로세스에 리스닝 FD를 넘겨 포트 확보와 실행 사이의 경합을 줄입니다. 물리 서버·컨테이너 두 개를 배포한 것은 아닙니다.

```bash
python3 study/labs/blue_green.py --output /tmp/blue-green-new.json
```

기존 출력 파일을 덮어쓰지 않습니다. 프록시와 앱은 도구 내부에서 시작하며 종료 시 정리합니다. 프록시는 이 실험의 제한된 GET/JSON 흐름만 다루며 운영 프록시로 사용할 구현이 아닙니다.

## 2. 실험 순서

1. blue-v1, green-v2 앱을 시작하고 실제 HTTP health 응답을 확인합니다.
2. 프록시는 처음 blue로 보냅니다.
3. **모의 503 후보 판정**에서는 전환하지 않는 분기를 검사합니다. 실제 고장난 서버를 띄운 검사는 아닙니다.
4. green의 실제 health를 확인한 뒤, blue 요청이 실행 중일 때 신규 요청 대상을 green으로 바꿉니다.
5. 전환 요청 40개의 응답을 모으고 오류·버전을 확인합니다.
6. blue로 한 번 되돌려 응답을 확인하고 다시 green으로 전환합니다.
7. blue 진행 요청이 없는 것을 확인한 후 프로세스를 종료하고 green 요청 10개를 추가 확인합니다.

## 3. 실제 결과

| 항목 | 관찰 |
| --- | --- |
| 전환 시 blue 진행 요청 | 3개 |
| 전환 구간 요청 | 40개 |
| 전환 응답 버전 | blue 3개, green 37개 |
| 전환 구간 오류 | 0개 |
| rollback 후 응답 | blue-v1 확인 |
| blue 종료 후 | green 응답 10개, 오류 0개 |
| 정리 | 두 앱 프로세스·프록시·소켓 종료 |

이전 요청은 기존 대상으로 끝내고, 이후 요청은 바뀐 대상을 선택했습니다. 3:37이라는 분포는 타이밍에 따른 이번 관찰값이며 다음 실행에서 달라질 수 있습니다.

## 4. 무엇을 주장할 수 있을까

‘이 제한된 로컬 시나리오의 측정 요청에서 오류가 없었다’고 말할 수 있습니다. 실제 인터넷의 모든 사용자가 무중단을 경험했다거나 p99 지연이 유지되었다는 결론은 아닙니다. 이 실험은 지연 분포를 측정하지 않았습니다.

nginx/ALB 대상 제거, 컨테이너 신호 처리, Kubernetes endpoint 반영, TLS, 장기 연결, DB migration, 앱 crash, 배포 도중 DB 풀 예산은 추가 검증 대상입니다. 동일한 체크리스트를 실제 두 컨테이너/서버에 옮겨 결과를 다시 수집해야 합니다.

## 5. 개선 과제

독자 확장 실험으로 green이 실제 503을 반환하게 하고 health 검사에서 거부되는지 확인하세요. 요청 처리 시간을 늘린 뒤 강제 종료와 drain의 차이도 비교합니다. 원 요청 ID·버전·상태·지연을 수집하고, 실패 응답뿐 아니라 연결 실패도 오류율 분모에 포함합니다. 이 확장 과제는 원본 결과에 포함하지 않았습니다.
