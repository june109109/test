# 9-1. 구조화 로그와 request-id

[목차](../README.md) · [정답·해설](01-logging-answers.md)

예상 45분. 목표: 사람이 읽는 메시지와 기계가 검색할 필드를 함께 설계하고, 요청을 경계 너머로 추적합니다.

## 1. 문장만으로 찾기 어려운 장애

`요청 실패`라는 로그만 있으면 어떤 경로·버전·의존성·오류인지 알기 어렵습니다. 구조화 로그는 timestamp, level, event, request_id, route, status, duration_ms, service_version 등의 필드를 일정하게 기록합니다. JSON은 직렬화 형식이고 필드 의미·단위·일관성이 실제 계약입니다.

```json
{"level":"ERROR","event":"payment_timeout","request_id":"generated-id",
 "route":"/orders/{id}/pay","duration_ms":1200,"dependency":"payment"}
```

이 값은 설명용 예시입니다. 전체 URL 대신 route template을 쓰면 개인정보·고유 ID 노출과 검색 변동을 줄일 수 있습니다.

## 2. logging 설정

Python logging의 logger는 이벤트를 만들고 handler는 출력 경로, formatter는 표현, filter는 선택·필드 보강에 관여합니다. 라이브러리 내부에서 root logger를 반복 설정하면 중복 출력·정책 충돌을 만들 수 있습니다. 앱 진입점에서 설정하고 각 모듈은 이름 있는 logger를 사용합니다.

문자열을 덧붙여 JSON을 만들면 개행·따옴표 때문에 형식이 깨질 수 있습니다. JSON serializer를 사용합니다. 예외에는 필요한 traceback을 남기되 요청 본문·헤더 전체를 무조건 출력하지 않습니다.

## 3. request-id의 수명과 신뢰

진입점에서 ID를 만들거나 허용된 형식·길이의 상위 ID를 처리하고 내부 호출·로그에 전달합니다. 외부 제공 ID는 사용자 입력이며 권한 증거가 아닙니다. 긴 값·개행·중복을 검사하고 내부 ID와 외부 correlation 값을 나누는 것도 방법입니다.

trace-id는 분산 trace의 식별자이며 request-id와 반드시 동일하지 않습니다. 큐 메시지로 이어지는 작업은 원 요청 ID와 새 작업 ID의 관계를 명시합니다. 로그에 식별자를 넣는 것만으로 네트워크 호출에 자동 전파되지는 않습니다.

## 4. 비용과 실패

| 방식 | 이익 | 비용 |
| --- | --- | --- |
| stdout JSON + 수집기 | 앱과 저장소 결합 감소 | 수집 지연·유실·backpressure |
| 파일 로그 | 로컬 조사 편리 | 회전·디스크 고갈·컨테이너 수명 |
| 동기 원격 전송 | 전송 결과 즉시 관찰 | 요청 지연·로그 시스템 장애 전파 |
| QueueHandler 계열 | 핫패스 출력 대기 감소 | 큐 상한·종료 flush·유실 정책 |

모든 debug를 운영에 남기면 비용·민감 정보·신호 잡음이 커집니다. 반대로 성공 로그를 전부 없애면 분모와 정상 경로를 모를 수 있습니다. 보존·샘플링·오류 급증 정책을 정합니다.

## 5. 적용 과제

결제 오류 로그 스키마를 설계하세요. 토큰·비밀번호·카드번호·개인 식별자는 원문을 제외하고, 오류 분석에 필요한 상태 코드·단계·요청/작업 연결·버전만 포함합니다. 개인정보 해시도 항상 익명 정보가 되는 것은 아닙니다.
