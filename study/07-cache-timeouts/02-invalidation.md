# 7-2. 캐시 갱신과 장애

[목차](../README.md) · [정답·해설](02-invalidation-answers.md)

예상 55분. 목표: 적중률보다 응답의 정확성과 복구 가능성을 먼저 설계합니다.

## 1. cache-aside의 기본 흐름

앱이 캐시를 읽고 miss면 원본에서 조회한 뒤 캐시에 저장합니다. 쓰기에서는 원본을 갱신하고 관련 캐시를 무효화하는 패턴이 흔합니다. 단순하지만 원본과 캐시가 하나의 transaction인 것은 아닙니다.

```text
읽기: cache GET → miss → DB SELECT → cache SET → 응답
쓰기: DB UPDATE + COMMIT → cache DELETE
```

삭제 실패·읽기와 쓰기의 경합을 생각해야 합니다. 독자 R이 오래된 DB 값을 읽고 멈춘 동안 W가 새 값을 commit하고 캐시를 지운 뒤, R이 옛 값을 다시 캐시에 넣을 수 있습니다. ‘쓰기 후 DELETE’만으로 모든 stale 경쟁을 없애지는 못합니다.

## 2. 신선도 대안과 비용

| 전략 | 얻는 것 | 남는 비용 |
| --- | --- | --- |
| TTL만 | 간단한 만료 경계 | 만료 전 오래된 값·동시 만료 |
| 쓰기 후 무효화 | 보통 더 빠른 갱신 반영 | 실패·경합·여러 키 추적 |
| 버전이 포함된 키/값 | 오래된 재삽입 구분 | 현재 버전 조회·원자적 비교·정리 |
| 동기 갱신(write-through 계열) | 쓰기 경로에서 캐시 최신화 시도 | 지연·두 저장소 실패 처리 |
| 이벤트 기반 무효화 | 서비스 간 전파·확장 | 지연·중복·누락·재처리 |
| stale-while-revalidate | 재생성 중 빠른 이전값 | 허용 가능한 오래됨의 상한 필요 |

캐시가 최신인지 확인하려고 매번 동일한 원본 조회를 한다면 원래 줄이려던 비용이 남습니다. 최신성과 지연·운영 복잡도의 균형을 업무별로 잡습니다.

## 3. stampede와 hot key

많은 요청이 같은 키 만료를 동시에 보면 원본에 조회가 몰립니다. 한 프로세스의 single-flight는 그 프로세스에서만 재생성을 합칩니다. 공유 잠금은 다른 워커까지 조정할 수 있지만 소유권·만료·갱신·장애 처리가 필요합니다.

TTL jitter는 여러 키의 만료 시점을 흩어 주지만 단일 hot key의 모든 miss를 해결하지 않습니다. 캐시 채우기 작업의 동시성 제한·확률적 조기 갱신·허용 범위의 stale 응답 등도 비교합니다. 분산 락을 썼다는 이유로 모든 쓰기 무결성이 보장되는 것은 아닙니다.

## 4. 키 설계는 접근 제어와 연결된다

`product:123`이 국가·통화·테넌트·권한·언어에 따라 다른 응답을 반환한다면 필요한 차원을 키에 포함해야 합니다. 개인화 결과를 전역 키로 저장하면 적중률이 높아도 다른 사용자의 데이터를 보여 줄 수 있습니다.

부재 결과를 짧게 저장하는 negative cache는 없는 ID 반복 요청을 줄입니다. 하지만 404와 일시적 DB 장애를 같은 ‘없음’으로 캐시하면 정상 데이터가 사라진 것처럼 보입니다. 에러의 종류와 TTL을 나눕니다.

## 5. Redis가 멈추면

모든 miss를 즉시 DB로 보내면 DB까지 과부하가 될 수 있습니다. 허용 stale, 제한된 DB fallback, 요청 거절, 중요한 기능 우선순위, circuit breaker를 조합합니다. 권한 검사 캐시는 오래된 허용을 쓰는 정책이 위험할 수 있고, 공개 뉴스는 잠깐 이전값을 제공하는 편이 나을 수 있습니다.

볼 지표는 hit ratio뿐 아니라 데이터 나이·갱신 실패·원본 증폭·키별 집중·메모리/eviction·오류율입니다. 높은 적중률이 정확한 결과의 증거는 아닙니다.

## 6. 적용 과제

캐시 서버가 30초 중단되어도 공개 메인 화면은 응답하고 결제 권한은 보수적으로 검사해야 합니다. 기능별 fallback·동시성 한도·stale 상한·복구 후 재충전 정책을 작성하세요. 이 장애 주입은 독자 과제이며 Redis에서 실제 실행하지 않았습니다.
