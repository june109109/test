# 7-5. 재시도와 과부하

[목차](../README.md) · [정답·해설](05-retries-answers.md)

예상 50분. 목표: 재시도가 복구와 부하 증폭을 동시에 만들 수 있음을 계산하고, 멱등성·예산·backoff를 설계합니다.

## 1. 한 번 더 보내는 비용

일시적 네트워크 오류는 재시도로 회복할 수 있습니다. 하지만 서버가 과부하일 때 같은 요청을 더 보내면 장애가 악화됩니다. API gateway·앱·SDK가 각각 원 요청 포함 3회씩 시도하면 최악의 하위 시도 수는 3×3×3=27입니다. 서로 독립적인 retry 정책이 숨은 증폭기를 만듭니다.

평소 성공 요청까지 고려한 전체 retry 비율, 요청 하나당 최대 횟수, 전체 deadline을 함께 제한합니다. 한 계층에서 책임지거나 계층별 예산을 명시적으로 나눕니다.

## 2. 무엇을 다시 시도할까

| 상황 | 판단 | 조건 |
| --- | --- | --- |
| 잘못된 입력·권한 없음 | 보통 즉시 실패 | 같은 요청 반복으로 해결되지 않음 |
| 일시적 503/연결 장애 | 제한된 retry 후보 | 전체 예산·부작용 확인 |
| 429 | 서버 신호 존중 | Retry-After와 자체 deadline/한도 |
| 요청 전 연결 실패 | 전송 전일 가능성 검토 | 라이브러리 오류 단계가 실제로 무엇인지 |
| read timeout | 결과 불명확할 수 있음 | 처리 성공 후 응답 유실 가능 |
| DB 40001 | 전체 transaction 재시도 | 읽기 판단 포함, 외부 부작용 분리 |

HTTP method 이름만으로 모든 재시도가 안전한 것은 아닙니다. POST도 멱등 키를 지원하면 안전한 반복을 설계할 수 있고, 잘못 구현한 GET은 부작용을 일으킬 수 있습니다. 제공자의 계약을 확인합니다.

## 3. backoff와 jitter

exponential backoff는 시도 사이 대기를 점차 늘리고 최대치를 둡니다. jitter는 많은 클라이언트의 재시도가 같은 순간에 겹치지 않도록 무작위로 분산합니다. 예를 들어 full jitter는 `0~min(cap,base*2**attempt)` 범위에서 지연을 고를 수 있습니다.

이 지연도 전체 deadline을 소비합니다. 남은 예산이 새 시도와 정리 시간보다 짧으면 중단합니다. jitter는 과부하를 줄이는 도구이며 성공 보장이나 요청률 제한의 대체가 아닙니다.

## 4. 멱등 키와 결과 불명확

결제 요청마다 새 멱등 키를 만들면 재시도인지 새 결제인지 구분할 수 없습니다. 같은 업무 시도의 재시도에는 안정된 키를 쓰고, 같은 키에 다른 payload가 오면 거부하는 정책을 둡니다. 키 보관 기간·완료 결과·진행 중 상태·경합 처리가 필요합니다.

서버가 키를 저장하고 부작용을 실행하는 두 단계 사이에도 실패할 수 있습니다. 하나의 DB transaction에 묶을 수 있는 범위를 정하고 외부 결제는 제공자 멱등성과 상태 조회로 이어야 합니다. ‘키를 붙였으니 exactly-once’라고 단정하지 않습니다.

## 5. circuit breaker와 admission

circuit breaker는 실패가 많은 의존성 호출을 잠시 차단하여 회복 기회를 줄 수 있습니다. half-open 상태에서 제한적으로 확인합니다. rate limiter는 시간당 유입, semaphore는 동시 작업, bounded queue는 대기량을 제한합니다. 각 도구가 제한하는 단위가 다릅니다.

사용자에게 즉시 오류를 돌려주는 비용을 감수해서라도 무한 대기·메모리 증가·하류 붕괴를 막는 상황이 있습니다. 관측 지표는 원 요청 수와 실제 시도 수, 최종 성공률, 지연, retry 원인, 한도 때문에 중단한 횟수를 구분합니다.

## 6. 적용 과제

SDK 최대 3시도, 앱 최대 2시도, gateway 최대 2시도인 결제 경로의 최악 요청 증폭을 계산하세요. 총 3초 예산 안에서 retry 책임을 하나로 모은 안과 계층별로 나눈 안을 비교합니다. 이는 설계 과제이며 장애 서버 부하 실험은 실행하지 않았습니다.
