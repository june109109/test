# 11-5. 개선 검증과 회귀 기준

[목차](../README.md) · [정답·해설](05-improvement-answers.md)

예상 55분. 목표: 개선을 같은 조건에서 평가하고, 처리량·꼬리·오류·비용·새 병목을 함께 기록합니다.

## 1. 좋아졌다는 말의 기준

처리량만 늘고 오류율·p99·비용이 악화되면 사용자에게 개선이 아닐 수 있습니다. 먼저 목표를 정합니다. 예: 같은입력100RPS에서 성공률 99.9% 이상, p99 300ms이하, 인스턴스 비용 증가 10% 이내. 이 숫자는 설명용이며 서비스 요구에 맞춰 정합니다.

11-4의 같은VUser8에서 비동기 경로는 약4.39배의 성공RPS를 보였고 p99는약523→106ms였습니다. 그러나 closed모델의 제공 부하도 변했으므로 고정 도착률SLO의 최종 검증을 대신하지 않습니다.

## 2. 전후 실험 설계

| 고정/기록할 것 | 이유 |
| --- | --- |
| workload·데이터·캐시·인증 | 쉬운 요청으로 바뀐 효과 제외 |
| CPU·메모리·워커·풀 | 자원 증설 효과와 코드 효과 구분 |
| 버전·commit·설정 | 재현과 rollback |
| 발생모델·연결·thinktime | 유입 변화 해석 |
| warmup·측정·반복·순서 | 캐시·시스템 변동과 효과 분리 |
| 정상/오류/미시작·지연분포 | 실패를 숨긴 ‘개선’ 방지 |

가능하면A/B순서를 바꾸고 대표 조건에서 반복합니다. 작은 차이보다 표본 간 변동이 크면 효과를 확정하지 않습니다. 평균 한 개와 소수점 많은 숫자는 신뢰구간을 대신하지 않습니다.

## 3. 병목 이동

루프블로킹을 고치면 더 많은 요청이 DB에 도달해 DB풀이 새 병목이 될 수 있습니다. 앱 처리량 개선이 하류 한도를 넘기지 않도록 admission·deadline·retry budget을 다시 봅니다. API를 빠르게 만든 것과 전체 시스템을 안전하게 운영하는 것은 함께 검증할 문제입니다.

비용당 성공처리량, 요청당CPU시간, 메모리피크, DB부하, 운영복잡도를 비교합니다. 스레드 수를 늘려 지연이 줄었더라도RSS와DB연결이 크게 늘면 그 비용을 기록합니다.

## 4. 회귀 기준과 배포

매PR의 짧은smoke는 큰 실패를 찾고, 대표부하의 긴 회귀실험은 전용환경/일정에서 수행할 수 있습니다. 공유CI의 타이밍 변동을 고려해 과도하게 좁은 절대시간assert를 두지 않습니다. 동작 정확성은10장의 빠른 테스트로 보호합니다.

canary에선 이전버전/새버전의 요청조합과 표본 수를 맞춰 지표를 봅니다. 중단·rollback조건, DB호환, 재측정·결과 보관을 정합니다. 예외 승인에는 이유와 다음 검증일을 남깁니다.

## 5. 제출 보고서

‘문제→가설→변경→고정조건→실행표본→효과/변동→새 병목→비용→미검증→배포 기준’ 순서로 한 페이지를 쓰세요. 근거와 한계를 숨기지 않는 보고서가 다음 개선을 가능하게 합니다.
