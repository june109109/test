# 11-1. 도구와 부하 모델

[목차](../README.md) · [정답·해설](01-load-models-answers.md)

예상 50분. 목표: 가상 사용자 수와 요청 도착률을 구분하고, 측정 목적에 맞는 발생기를 고릅니다.

## 1. 사용자 100명이 100 RPS는 아니다

닫힌 모델에서는 각 가상 사용자가 응답을 받은 뒤 다음 작업을 시작합니다. 생각 시간 Z와 평균 응답 시간 R이 있을 때 정상 상태의 대략적인 처리율은 `N/(R+Z)`입니다. 100명이 0.2초 응답 후 0.8초 쉬면 약100회/초, 응답이 2초로 느려지면 약35.7회/초입니다. 서버가 느려지자 발생기도 덜 요청하게 됩니다.

열린 모델은 이전 응답과 독립적인 일정으로 새 요청/iteration을 시작합니다. 초당100개 유입이라는 요구를 더 직접적으로 시험할 수 있지만, 처리가 느리면 실행 중 작업이 쌓입니다. 발생기의 동시 실행 한도 때문에 시작하지 못한 작업도 dropped iteration 등으로 기록해야 합니다.

| 모델 | 적합한 질문 | 주의 |
| --- | --- | --- |
| closed: 고정 VUser | 로그인한 동시 사용자가 반복 행동하면? | 서버 지연이 유입률을 낮춤 |
| open: 고정/증가 도착률 | 외부에서 계속 유입되면 감당하는가? | 발생기 용량·미시작 요청·큐 증가 |
| 실제 트래픽 재생 | 요청 조합과 시간 분포를 재현하면? | 개인정보·데이터 종속·부작용·재현 비용 |

k6 문서는 closed 모델에서 느려진 응답 때문에 새 작업 시작이 줄어드는 coordinated omission 문제를 설명합니다. closed 모델이 항상 틀린 것은 아닙니다. 실제 사용자가 응답을 기다리는 행동을 모델링한다면 유용하며, 도착률을 검증하려는 목적과 혼동하면 안 됩니다.

## 2. 도구 선택

| 도구 | 익숙한 작성 방식·강점 | 선택 비용 |
| --- | --- | --- |
| Locust | Python 사용자 행동, 사용자 정의 흐름, 분산 실행 | Python 실행 비용·blocking 라이브러리·발생기 관측 |
| k6 | JavaScript 계열 스크립트, scenario/executor·threshold | Node.js 전체 환경과 동일하지 않음, executor 의미 학습 |
| nGrinder | controller/agent, JVM 생태계·팀 운영 UI | 서버/agent 운영·스크립트 환경·버전 제약 |
| 작은 전용 harness | 실험 가정과 측정 경로를 읽기 쉬움 | 성숙한 집계·분산·프로토콜 기능 직접 구현 |

같은 도구도 설정에 따라 모델이 달라집니다. ‘Locust=RPS 고정’처럼 이름만으로 판단하지 않습니다. 팀의 언어·CI·분산 필요·프로토콜·결과 보관으로 선택합니다.

## 3. 발생기도 병목이다

클라이언트 CPU·소켓·connection pool·DNS·출력 로그가 포화되면 서버에 원하는 부하가 도달하지 않습니다. 발생기가 서버와 같은 머신이면 CPU·메모리·네트워크 자원을 경쟁합니다. 서버가 한가한데 RPS가 멈춘다면 발생기의 한도를 조사합니다.

원 요청과 retry를 분리하고, 연결/TLS 재사용·HTTP 버전·think time·데이터 조합을 기록합니다. 연결을 매번 새로 여는 테스트와 keep-alive 테스트는 다른 비용을 측정합니다.

## 4. 실습과 적용

[실행기](../labs/load_http.py)는 외부 대상을 받지 않고 자신이 띄운 로컬 Uvicorn만 호출합니다. 한 VUser당 하나의 지속 HTTP/1.1 연결, think time0의 closed 모델입니다. 도구 비교 표의 세 제품을 실제 설치해 비교한 실험은 아닙니다.

쇼핑몰 브라우징과 초당500건 webhook 유입에 각각 어떤 모델을 쓸지 적고, 발생기가 요청을 시작하지 못한 경우를 성공률 계산에서 어떻게 드러낼지 정하세요.
