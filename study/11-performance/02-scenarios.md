# 11-2. 재현 가능한 부하 시나리오

[목차](../README.md) · [정답·해설](02-scenarios-answers.md)

예상 55분. 목표: workload·실험 조건·중단 기준을 먼저 기록하고 짧은 결과의 한계를 설명합니다.

## 1. 명령보다 먼저 실험 질문

‘동기 sleep이 루프를 막는가’와 ‘현재 구성으로 피크1000RPS를 p99 300ms 이내에 처리하는가’는 다른 실험입니다. 전자는 실행 경계, 후자는 전체 경로·포화·오류·자원·발생 모델이 필요합니다.

실험서에 버전/commit, CPU quota·메모리, worker·thread·pool, 데이터 크기·분포, 인증·캐시 상태, 요청 조합, warmup, 측정 구간, 반복, 종료·복구를 적습니다. 비밀 값은 기록하지 않습니다.

## 2. 시간을 나누기

| 구간 | 목적 | 측정 처리 |
| --- | --- | --- |
| 기능 확인 | 잘못된 요청을 빠르게 찾음 | 성능 집계에서 분리 |
| warmup | 연결·캐시·시작 비용 분리 | warm/cold 목적에 맞게 기록 |
| 단계별 일정 부하 | 지연·오류·자원 안정 여부 | 최소2~3분은 시작점 |
| spike/soak | 급증 대응·누수·장기 주기 | 별도 충분한 시간 필요 |
| drain/cleanup | 진행 작업 완료·자원 반환 | 새 요청 중단과 완료 시각 구분 |

2분을 채웠다는 사실이 정상 상태의 증거는 아닙니다. autoscaling 주기·TTL·GC·배치·연결 수명보다 짧으면 중요한 문제가 안 보입니다. 앞 구간의 캐시가 다음 구간에 영향을 주므로 순서 교환·초기화·반복 전략이 필요합니다.

## 3. 데이터와 캐시

한 ID만 반복하면 실서비스보다 높은 캐시 적중률과 작은 working set을 시험합니다. 실제 hot/cold 분포·권한·쓰기 비율을 반영합니다. 반대로 모든 요청에 새 키를 쓰면 실제보다 낮은 적중률이 될 수 있습니다.

쓰기 테스트는 고유 namespace·총량 상한·정리·멱등성으로 범위를 제한합니다. 테스트가 이메일·결제·실사용 알림을 보내지 않도록 승인된 테스트 경로를 사용합니다. 여기의 부하 실험은 자체 loopback 서버의 읽기 응답만 사용합니다.

## 4. 이 자료의 재현 명령

```bash
python3 study/labs/load_http.py --seconds 120   --output /tmp/load-http-new.json
```

Linux/POSIX, 4장의 FastAPI/Uvicorn 의존성이 필요합니다. 각 경로5회 warmup 후 ①blocking VUser1 ②blocking VUser8 ③async I/O VUser8을 각120초 측정합니다. 진행 요청을 끝내므로 elapsed는120초보다 조금 길 수 있습니다. 총 약6분이며 출력 파일은 덮어쓰지 않습니다.

`--seconds 2`는 실행 확인용이며 본 측정과 구분합니다. 이 실행기는 timeout3초, VUser최대8의 유한한 자체 실험입니다. 운영 대상/분산 발생기/SLO 기반 자동 중단을 제공하는 완성 부하 도구는 아닙니다. 다음 편들에서 원본 결과를 해석합니다.

## 5. 적용 과제

10→30→100 VUser를 각3분 실행할 계획에 warmup·오류율/지연 중단 기준·발생기 자원·회복 관찰을 추가하세요. 메모리 누수 검증을 주장하려면 어떤 장기 실험이 더 필요한지 적습니다.
