# 5-8. DB 커넥션 풀 예산

[목차](../README.md) · [정답·해설](08-pool-budget-answers.md)

예상 50분. 목표: 배포 중 최대 연결을 계산하고, 연결 수·동시성·처리량을 분리합니다.

## 1. 워커의 풀은 합산된다

인스턴스 3개, 워커 4개, 워커마다 QueuePool `pool_size=10`, `max_overflow=5`라면 앱의 잠재적 동시 연결은 `3×4×(10+5)=180`입니다. 모든 풀이 시작 즉시 15개를 열었다는 뜻은 아닙니다. SQLAlchemy QueuePool은 수요에 따라 연결을 만들며, 반환 시 overflow 연결은 유지하지 않을 수 있습니다.

```text
최대 앱 연결 = 동시에 살아 있는 인스턴스 수
             × 인스턴스당 워커 수
             × 워커당 풀 개수
             × (풀 크기 + 허용 overflow)
전체 요구량 = 앱 + 배치 + 관리/마이그레이션 + 기타 서비스 + 여유
```

풀 크기가 서로 다르면 각 풀을 합산합니다. 읽기/쓰기 DB가 다르면 DB별로 예산을 따로 계산합니다. DB 프록시를 쓰면 앱 연결과 DB backend 연결이 다르므로 프록시의 제한·transaction pooling 의미도 확인해야 합니다.

## 2. max_connections를 끝까지 채우지 않기

DB max_connections 200이라고 앱에 200을 배정하면 관리 접속·장애 대응이 막힐 수 있습니다. DB의 예약 연결·메모리·CPU 한계도 있습니다. 연결 수 한도를 지킨다고 DB가 그 수의 동시 질의를 효율적으로 처리한다는 뜻은 아닙니다.

설명용 예산: 200에서 관리·기타·여유로 40을 남기면 앱 예산은 160입니다. 정상 3개 인스턴스 ×4워커 ×10연결=120이지만 rolling 배포 때 4개가 공존하면 160으로 여유가 사라집니다. overflow까지 허용하면 초과합니다. 자동 확장 최대치와 배포 surge를 반드시 포함합니다.

## 3. 동시성에서 처리량으로

평균적으로 연결을 잡고 있는 시간이 50ms이고 실제 이용 가능한 연결이 20개라면 단순 포화 근사는 `20 / 0.05 = 400 transaction/s`입니다. 이는 보장이 아닙니다. 락 경합·CPU·디스크·네트워크·긴 꼬리와 transaction당 쿼리 수가 상한을 낮춥니다.

Little의 법칙 `L=λW`를 안정된 시스템의 같은 측정 구간에 적용하면, DB 연결 점유 동시성 L은 transaction 처리율 λ와 평균 점유 시간 W의 곱으로 근사할 수 있습니다. 요청 전체 지연과 DB 점유 시간을 섞지 마세요. 요청 중 DB에 접근하지 않는 시간이 길면 필요한 연결은 전체 요청 동시성보다 적을 수 있습니다.

## 4. 대기·검사·수명 옵션은 다른 목적

| 설정·기법 | 해결하려는 문제 | 해결하지 못하는 것 |
| --- | --- | --- |
| pool_timeout | 연결 획득 대기 상한 | 실행 중 SQL 시간 제한 |
| statement_timeout | 문장 실행 제한 | 전체 업무 deadline |
| pool_pre_ping | 대여 시 죽은 연결 감지 | transaction 중 단절 복구 |
| pool_recycle | 오래된 연결 교체 기회 | 실행 중 연결의 강제 안전 교체 |
| backpressure | 유입·대기열 제한 | DB 자체 용량 증가 |

반환된 연결의 transaction 상태를 정리하지 않으면 다음 요청에 상태가 새어갈 수 있습니다. 동시 요청 사이에 ORM Session 하나를 공유하지 않습니다. SQLAlchemy async engine의 풀과 동기 QueuePool을 같은 객체로 사용하지 않습니다.

## 5. 큰 풀이 항상 빠르지 않은 이유

풀이 작아서 DB가 한가한데 앱만 기다린다면 확대가 도움이 됩니다. DB가 이미 포화이면 확대는 더 많은 질의를 동시에 밀어 넣어 경합·메모리·꼬리 지연을 악화시킬 수 있습니다. checkout 대기, 연결 점유 시간, DB CPU·I/O·락 대기, timeout과 오류율을 같이 봅니다.

트랜잭션을 짧게 하고 느린 쿼리를 고치는 것이 풀 증가보다 효과적일 수 있습니다. 상위 요청 취소 후 하위 SQL이 계속 실행되는지도 드라이버의 취소 의미를 확인해야 합니다.

## 6. 적용 과제

DB max_connections=240, 기타/관리/여유=60, 최대 인스턴스=4, 배포 추가=1, 워커=3입니다. 워커당 최대 연결 예산을 계산하고 pool_size·overflow 안을 두 개 제안하세요. DB 성능 실험 없이 예산 계산만으로 안전한 처리량을 선언하지 마세요.

### Python 트랙 보강: Pool과 Session의 수명

SQLAlchemy Engine/풀은 일반적으로 워커 수명, ORM Session/AsyncSession은 요청 또는 업무 transaction 수명으로 다룹니다. Session 하나를 전역에서 동시에 쓰거나 `asyncio.gather`의 여러 task에 공유하지 않습니다. 요청 수와 transaction 수가 같지 않은 서비스는 경계를 명시합니다.

예: 앱 인스턴스3개×워커2×(pool8+overflow2)=60연결, 배포 중 인스턴스가4개면80연결입니다. 관리10개와 배치10개를 더하면100이며 DB의 예약/여유를 별도로 남겨야 합니다. `pool_timeout`은 연결 획득 대기, SQL 실행 제한은 DB/드라이버 쪽 별도 설정입니다. 프로세스 생성 전 client/풀 상속은 [4-7](../04-fastapi/07-lifecycle.md)과 함께 점검하세요.
