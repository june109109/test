# 5-1. 저장소 종류와 선택 기준

[목차](../README.md) · [정답·해설](01-stores-answers.md)

예상 50분. 목표: 제품 분류를 외우는 대신 접근 패턴·정합성·운영 비용으로 저장소를 선택합니다.

## 1. 주문 서비스에 DB가 몇 종류 필요할까

주문 결제, 상품 상세 조회, 검색어 자동완성, 월별 매출 분석은 읽고 쓰는 방식이 다릅니다. 그렇다고 처음부터 저장소 네 개를 도입할 필요는 없습니다. 작은 서비스라면 PostgreSQL 하나로 거래·JSON 속성·기본 검색·일부 집계를 시작하고, 측정한 병목이나 기능 요구에 따라 분리할 수 있습니다.

먼저 ‘최근 주문 20개를 사용자별로 조회’, ‘가격 범위와 오타 허용 검색’, ‘3년간 전체 주문 매출 집계’처럼 **질의와 갱신 단위**를 적습니다. 데이터 크기만으로 선택하지 않습니다.

## 2. 분류는 대표적인 강점이다

| 계열·예 | 잘 맞는 접근 | 얻는 것 | 감수할 비용·확인점 |
| --- | --- | --- | --- |
| 관계형: PostgreSQL, MySQL | 관계·제약·트랜잭션, 다양한 질의 | FK·unique·조인·SQL | 인덱스/스키마 관리, 확장 설계 |
| 인메모리 자료구조: Redis | 캐시·카운터·정렬 집합 | 빠른 접근, 풍부한 원자 연산 | RAM 비용·만료·복구·복제 보장 검토 |
| 키-값/문서: DynamoDB | 키로 정해진 접근, 관리형 확장 | 운영 부담 감소, 예측 가능한 키 접근 | 파티션/보조 인덱스·hot key·비용 모델 |
| 문서형: MongoDB | 함께 읽고 바꾸는 중첩 문서 | 집합체를 자연스럽게 저장 | 무한 배열·중복 갱신·문서 경계 |
| 검색: Elasticsearch | 역색인·관련도·형태소·집계 | 검색 특화 기능 | 색인 지연·재색인·원본 동기화 |
| 분석: ClickHouse, BigQuery | 많은 행의 일부 열 집계 | 열 단위 읽기·압축·분석 처리 | 작은 행 갱신/짧은 거래와 다른 비용·특성 |

Redis를 ‘반드시 데이터가 사라지는 DB’, MongoDB를 ‘트랜잭션이 없는 DB’, DynamoDB를 ‘키 하나만 읽을 수 있는 DB’로 외우면 틀립니다. 지속성·트랜잭션·보조 인덱스 기능은 존재하지만 범위와 비용이 다릅니다. ClickHouse는 운영 배치와 서버 자원, BigQuery는 관리형 쿼리·용량 과금 등의 차이도 따로 살펴야 합니다.

## 3. 행 지향과 열 지향

행 지향은 한 주문의 여러 속성을 함께 읽고 바꾸기 좋습니다. 열 지향은 수억 주문에서 `금액`과 `날짜` 두 열만 읽어 합산할 때 읽는 양과 압축 효율에 이점이 있습니다. 이것은 주된 저장·처리 특성의 비교이며 ‘행 DB는 집계 불가’라는 규칙은 아닙니다.

키 조회와 검색도 다릅니다. `id=123`을 찾는 것과 ‘노이즈 캔슬링 헤드폰’에 적절한 문서를 관련도순으로 찾는 것은 필요한 자료구조와 기능이 다릅니다.

## 4. 선택을 바꾸는 질문

- 데이터가 2초 늦게 보여도 되는가, 결제 잔액처럼 즉시 맞아야 하는가?
- 개별 주문과 품목을 함께 원자적으로 바꾸어야 하는가?
- 조회 패턴이 확정되어 있는가, 운영팀의 새로운 분석 질문이 자주 생기는가?
- 초당 요청·데이터 분포·최대 키 집중도와 팀의 운영 가능 인원은 얼마인가?
- 백업 복원·권한·마이그레이션·장애 시 재구축 경로는 무엇인가?

DynamoDB 공식 설계 안내는 접근 패턴을 먼저 파악하라고 강조합니다. RDB도 접근 패턴이 성능에 중요하지만, 관계형 정규 모델과 임의 질의의 유연성은 설계 변경 비용을 다르게 만듭니다.

## 5. 의견 비교: 하나로 시작할까, 특화 저장소를 쓸까

다음은 제품 문서의 설계 관점을 바탕으로 구성한 **학습용 논증**이며 실제 인물의 발언 인용이 아닙니다.

**입장 A:** 먼저 RDB 하나로 시작한다. 운영·백업·정합성 경계가 단순하고 요구가 바뀌어도 질의로 대응하기 쉽다. **반박:** 전문 검색 기능이나 대규모 분석 때문에 거래 DB가 느려질 수 있다. **재반박:** 검색 품질·쿼리 비용·지연을 측정하고 분리 임계조건을 정한다. 특정 기능이 필수라면 처음부터 분리할 수 있다.

**입장 B:** 알려진 접근 패턴에 맞춘 특화 저장소를 쓴다. 한 가지 워크로드에 최적화하고 관리형 기능을 활용한다. **반박:** 데이터 복제·재처리·불일치가 새로운 문제다. **재반박:** 원본을 정하고 이벤트 전달·재색인·복구를 설계할 수 있으며, 얻는 기능이 그 비용보다 큰지 평가한다.

## 6. 적용 과제

동네 쇼핑몰의 주문 결제·상품 검색·주간 보고서에 대해 ‘하나로 시작하는 안’과 ‘분리하는 안’을 작성하세요. 각 안의 원본 데이터 위치, 허용 지연, 장애 시 동작, 팀이 맡을 운영 작업을 적습니다. ‘유명한 회사가 쓴다’는 선택 근거로 채점하지 않습니다.
