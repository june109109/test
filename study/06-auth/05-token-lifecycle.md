# 6-5. 토큰 수명과 계정 연결

[목차](../README.md) · [정답·해설](05-token-lifecycle-answers.md)

예상 50분. 목표: 만료·갱신·철회를 서로 구분하고, 이메일을 계정의 영구 키로 삼는 위험을 설명합니다.

## 1. 토큰 수명의 다른 시계

access token이 만료되어도 refresh token이나 자체 서비스 세션이 살아 있을 수 있습니다. 제공자 로그아웃, 서비스 로그아웃, 연동 동의 철회도 같은 사건이 아닙니다. 어떤 사건에 어떤 자격을 지울지 표로 정해야 합니다.

| 사건 | 가능한 조치 | 반드시 같지는 않은 것 |
| --- | --- | --- |
| access token 만료 | 허용된 refresh 수행 또는 재동의 | 서비스 세션 만료 |
| 자체 로그아웃 | 세션 폐기·쿠키 삭제 | 제공자의 전체 로그인 종료 |
| 연동 해제 | 제공자 토큰 폐기/철회 요청, 연동 삭제 | 서비스 계정 자체 삭제 |
| 탈취 의심 | 세션/토큰 계열 폐기, 재인증 | 과거 부작용 자동 복구 |

짧은 access token은 유출 후 사용 가능 시간을 줄이지만 갱신 요청과 실패 처리가 늘어납니다. 긴 수명은 편리하지만 탈취 영향이 오래갑니다. 정해진 만능 수치 대신 자원 민감도·제공자 정책·재인증 경험으로 결정합니다.

## 2. refresh rotation과 동시 갱신

refresh token을 쓸 때 새 refresh token으로 교체하고 이전 것은 다시 사용할 수 없게 하는 방식이 rotation입니다. 이미 사용한 이전 token이 다시 나타나면 탈취 또는 중복 갱신을 의심할 수 있습니다. RFC 9700은 public client의 refresh token에 sender-constrained 방식 또는 rotation을 요구합니다.

브라우저 탭 둘이나 워커 둘이 동시에 같은 refresh token을 쓰면 정상 요청도 재사용처럼 보일 수 있습니다. 갱신을 single-flight로 모으고 저장소의 원자적 교체·버전 비교, 제공자 정책에 맞는 실패 처리를 설계합니다. 무조건 무한 재시도하면 오히려 토큰 계열 폐기와 요청 폭증을 일으킬 수 있습니다.

refresh token은 긴 권한을 이어 주므로 로그·URL·브라우저의 불필요한 저장소에 노출하지 않습니다. 서버 저장 시 접근 권한·암호화·키 관리·폐기 절차를 정의합니다. 탈취한 토큰을 누가 사용할 수 있는지에 따라 sender constraint의 가치도 달라집니다.

## 3. 계정의 식별자는 issuer + subject

OIDC의 `sub`는 issuer 문맥의 사용자 식별자입니다. 따라서 `(iss, sub)`를 외부 계정의 키로 사용합니다. 동일한 sub 문자열이어도 issuer가 다르면 같은 사람이라고 결론낼 수 없습니다. pairwise subject를 사용하는 경우 client 간 값이 다를 수도 있습니다.

이메일은 바뀌거나 재할당될 수 있고, 제공자마다 검증·보장 의미가 다릅니다. OIDC Core도 email·전화번호·이름을 사용자 고유 식별자로 쓰지 말라고 명시합니다. `email_verified=true`도 우리 서비스의 기존 계정 소유를 지금 증명한 것은 아닙니다.

## 4. 안전한 계정 연결 절차

사용자가 기존 서비스 계정에 인증한 상태에서 ‘외부 계정 연결’을 시작하고, 필요한 경우 민감 작업 재인증을 요구합니다. 연결하려는 외부 계정도 정상 OAuth/OIDC 절차로 확인하고, 다른 서비스 계정에 이미 연결되어 있지 않은지 unique 제약과 transaction으로 검사합니다.

```text
users(id, ...)
external_identities(issuer, subject, user_id,
                    UNIQUE(issuer, subject))
```

이메일 일치만으로 자동 병합하면 다른 사람의 외부 계정을 기존 회원에게 연결하는 계정 탈취 경로가 생길 수 있습니다. 연결 해제 후 사용자가 로그인할 수단이 하나도 남지 않는 문제도 처리해야 합니다.

## 5. 적용 과제

두 워커가 같은 refresh token을 동시에 사용한 사건을 그리세요. 저장된 버전, 갱신 중 상태, 성공 응답 저장 실패, 이전 token 재사용을 각각 어떻게 처리하고 어떤 로그를 남길지 적습니다. 실제 제공자의 rotation 정책과 일반 설명을 구분하세요.
