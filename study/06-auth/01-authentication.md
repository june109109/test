# 6-1. 인증·인가·OAuth·OIDC

[목차](../README.md) · [정답·해설](01-authentication-answers.md)

예상 45분. 목표: 로그인과 API 권한 위임을 구분하고, 각 토큰의 수신자를 설명합니다.

## 1. ‘구글 로그인’에는 여러 역할이 있다

인증(authentication)은 ‘누구인가’를 확인합니다. 인가(authorization)는 ‘무엇을 해도 되는가’를 결정합니다. OAuth 2.0은 자원 접근 권한을 위임하기 위한 프레임워크입니다. OpenID Connect(OIDC)는 OAuth 위에서 사용자의 인증 결과를 전달하는 계층입니다.

사진 인쇄 서비스에 내 사진 일부를 읽을 권한을 주는 것은 OAuth의 예입니다. 서비스가 구글 인증 결과로 내 계정을 식별하는 것은 OIDC나 제공자가 정의한 로그인 프로토콜의 영역입니다. OAuth access token을 받았다는 사실만으로 범용적인 신원 검증 절차가 완성되지는 않습니다.

## 2. 등장인물과 토큰

| 역할·값 | 의미 | 주의 |
| --- | --- | --- |
| 사용자/resource owner | 권한 부여에 관여하는 주체 | 모든 OAuth 흐름에 사람이 있는 것은 아님 |
| client | 권한을 요청하는 앱 | 브라우저 화면과 백엔드를 포함할 수 있음 |
| authorization server | 인가·토큰 발급 담당 | 계정 DB·인증 방법은 제공자 영역 |
| resource server | 토큰을 검사하고 API 제공 | 앱 백엔드와 같은 의미로 고정되지 않음 |
| authorization code | 짧은 수명의 교환용 코드 | 일회용, 토큰과 다름 |
| access token | 특정 API 접근 권한 | opaque일 수 있음, 로그인 세션과 다름 |
| ID token | client에게 전달하는 인증 결과 | OIDC JWT, API access token 대용 아님 |
| refresh token | 새 토큰 발급을 위한 자격 | 자원 API로 보내지 않음 |

JWT는 토큰의 형식입니다. 모든 access token이 JWT인 것도, 모든 JWT가 인증용인 것도 아닙니다. 서명된 JWT의 payload는 대체로 읽을 수 있으며 암호화와 다릅니다.

## 3. 로그인 이후의 권한은 우리 서비스가 정한다

제공자가 ‘issuer X의 subject Y가 인증됐다’고 알려도 우리 서비스의 관리자 권한을 부여한 것은 아닙니다. 회원의 역할·테넌트·계정 정지·데이터 접근권한은 별도로 검사합니다.

예를 들어 구글 인증 성공 후 `email`에 회사 도메인이 있다는 이유만으로 최고 관리자 권한을 주면 도메인 소유·계정 정책·권한 부여 요건을 생략할 수 있습니다. 인증 결과와 서비스 권한 정책은 분리해서 설계합니다.

## 4. 선택 비교

| 방법 | 이득 | 비용·맞는 조건 |
| --- | --- | --- |
| 자체 비밀번호 로그인 | 계정 정책을 직접 통제 | 비밀번호 저장·복구·MFA·피싱 대응 책임 |
| OIDC 외부 로그인 | 인증 인프라 활용 | 제공자 장애·계정 연결·검증·개인정보 범위 |
| OAuth API 위임 | 사용자 비밀번호 없이 제한된 API 권한 | scope·토큰 수명·갱신·철회 관리 |

외부 로그인을 도입해도 우리 서비스의 세션 관리와 인가는 사라지지 않습니다. scope는 최소 필요 권한으로 요청하고 제공자 로그인과 연동 기능 동의를 묶어 과도한 권한을 요구하지 않습니다.

## 5. 적용 과제

‘구글로 로그인’과 ‘구글 캘린더에 일정 추가’ 기능을 분리해 데이터 흐름을 그리세요. 어느 토큰을 어느 서버에 보내며, 캘린더 동의를 철회해도 자체 서비스 세션을 어떻게 다룰지 적습니다.
