# 6-4. 자체 로그인 상태: 서버 세션과 JWT

[목차](../README.md) · [정답·해설](04-sessions-answers.md)

예상 55분. 목표: 토큰 형식·저장 위치·전달 방식을 분리하고, 폐기와 브라우저 위협을 고려해 세션을 선택합니다.

## 1. JWT 대 쿠키는 같은 축의 비교가 아니다

쿠키는 브라우저가 저장·전송하는 수단이고 JWT는 서명 가능한 토큰 형식입니다. 쿠키에 opaque session ID도 JWT도 담을 수 있습니다. JSON 응답으로 토큰을 보냈다면 그다음 어디에 저장하고 어떻게 보내는지를 추가로 결정해야 합니다.

| 축 | 선택 예 | 결정하는 문제 |
| --- | --- | --- |
| 상태 표현 | 임의 session ID / JWT | 서버 조회·claim·검증·폐기 |
| 저장 | HttpOnly cookie / JS 메모리 / 웹 저장소 | 접근 주체·수명·탈취 경로 |
| 전송 | Cookie / Authorization header | 자동 전송·CSRF·API 클라이언트 |

## 2. 서버 세션

브라우저에는 예측하기 어려운 ID를 주고 서버 저장소에서 user_id·만료·권한 버전 등을 찾습니다. 중앙 저장소에서 세션을 지워 즉시 철회하기 쉽지만 조회 지연·가용성·메모리 비용이 듭니다. 여러 워커라면 각 프로세스의 딕셔너리가 공유 세션 저장소를 대신하지 못합니다.

로그인 성공 시 기존 세션 ID를 회전하여 session fixation을 방지합니다. idle timeout과 absolute lifetime은 다릅니다. 계속 활동하면 무한히 유지되는 정책을 원하지 않는다면 둘을 함께 정의합니다.

## 3. JWT 기반 상태

검증 키를 가진 서버가 로컬에서 서명·claim을 검증할 수 있어 중앙 세션 조회를 줄일 수 있습니다. 대신 발급 뒤 권한 변경·로그아웃·탈취를 즉시 반영하기 어렵습니다. 짧은 만료·폐기 목록·권한 버전 조회 등을 도입하면 다시 상태나 외부 조회가 필요할 수 있습니다.

JWT에 민감한 개인정보를 많이 넣으면 서명되어도 내용을 읽을 수 있고 로그·헤더 크기도 커집니다. 검증 알고리즘·issuer·audience·만료를 제한하고 키 회전을 설계합니다. JWT라는 형식 자체가 시스템을 stateless하게 만드는 것은 아닙니다.

## 4. 브라우저 저장과 공격 조건

| 방식 | 이익 | 감수할 비용 |
| --- | --- | --- |
| Secure·HttpOnly 쿠키 | JS의 직접 토큰 읽기를 줄임 | 브라우저 자동 전송에 대한 CSRF 대책 |
| JS 메모리 + Bearer header | 앱이 명시적으로 전송, 재시작 시 소실 가능 | XSS가 앱 동작·메모리에 영향을 줄 수 있음 |
| localStorage 등 웹 저장소 | 새로고침 후 유지가 간단 | 동일 origin 스크립트/XSS가 읽을 수 있음 |
| BFF가 외부 토큰 보관 | 제공자 토큰의 브라우저 노출 감소 | 백엔드 세션·프록시 경로·CSRF 책임 |

HttpOnly는 XSS를 제거하지 않습니다. 공격 스크립트가 쿠키를 읽지 못해도 사용자 브라우저에서 인증된 요청을 보낼 수 있습니다. 입력/출력 처리·CSP 등 XSS 방어와 세션 설계는 함께 필요합니다.

쿠키에는 HTTPS의 Secure, 필요한 경우 HttpOnly, 적절한 SameSite, 최소 Domain/Path 범위를 사용합니다. SameSite는 site 개념이고 origin과 다릅니다. 로그인 callback 방식과 top-level 이동을 고려해 설정해야 하며 CSRF 방어 전체를 무조건 대체한다고 보지 않습니다. 상태 변경 요청에는 CSRF token·Origin 검증 등 앱 구조에 맞는 방어를 둡니다.

## 5. 의견 비교

다음은 선택 비용을 드러내기 위한 학습용 논증입니다.

**‘서버 세션이 기본으로 편하다’**: 브라우저 중심 서비스에서 로그아웃과 권한 변경이 단순하다. **반박:** 저장소 조회와 장애 의존성이 늘어난다. **재반박:** 운영 가능한 저장소와 짧은 조회 비용이 즉시 철회라는 요구보다 작은지 평가한다.

**‘JWT를 서비스마다 검증하자’**: 여러 API가 중앙 조회 없이 검증할 수 있다. **반박:** 오래된 권한과 탈취 토큰이 만료까지 유효하다. **재반박:** 짧은 수명과 명시적 철회 경로를 설계하되, 그 상태 관리 비용을 포함해 중앙 세션과 비교한다.

## 6. 적용 과제

관리자 페이지는 즉시 로그아웃·권한 변경 반영이 중요하고 사용자는 하루 1,000명입니다. 서버 세션과 JWT 안을 작성하고, 중앙 조회를 줄이기 위해 감수하는 위험/복잡도가 가치 있는지 판단하세요.
