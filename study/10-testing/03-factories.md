# 10-3. 테스트 데이터와 factory

[목차](../README.md) · [정답·해설](03-factories-answers.md)

예상 45분. 목표: 기본값 생성과 검증할 경계값을 분리하고, 난수·공유 데이터의 재현성을 관리합니다.

## 1. 큰 입력을 매번 손으로 만들지 않기

주문 객체에 필드가 20개라면 테스트마다 반복하면 읽기 어렵습니다. factory는 정상 기본값을 만들고 각 테스트가 중요한 필드만 덮어쓰게 합니다. 테스트 본문에서 왜 이 사례가 다른지 드러나야 합니다.

[예제 factory](../labs/testing_demo/conftest.py)는 SKU 순번을 fixture마다 새로 만들고 수량1·단가10000을 기본값으로 합니다. 테스트는 `line_factory(unit_cents=9999)`처럼 경계만 지정합니다. 무작위값을 쓰지 않아 실패 입력을 재현하기 쉽습니다.

## 2. 수동 factory와 생성 도구

| 방식 | 이익 | 비용 |
| --- | --- | --- |
| 작은 수동 factory | 업무 기본값과 의도가 명확 | 스키마 변화 반영 필요 |
| polyfactory 같은 타입 기반 생성 | 큰 모델 작성 부담 감소 | 타입에 맞아도 업무 규칙 위반 가능 |
| property-based 생성 | 넓은 입력·축소된 실패 사례 | 성질 정의·실행 비용·디버깅 |
| 고정 fixture 파일 | 외부 계약의 실물 구조 재현 | 오래된 fixture·개인정보·큰 diff |

생성기가 만든 무작위 금액으로는 정확히10000 경계가 잘 나오지 않을 수 있습니다. 무료배송 규칙은 명시적 경계 사례가 필요합니다. 생성 도구를 써도 중요한 조건은 직접 지정합니다.

## 3. 무작위와 시간

seed를 기록하면 같은 생성기의 같은 버전·순서에서 재현하는 데 도움이 됩니다. library 버전·병렬 실행·호출 순서가 바뀌면 seed만 같아도 결과가 달라질 수 있습니다. 실패한 구체 입력도 남깁니다.

현재 시각·UUID·순서를 직접 함수 안에서 만들면 테스트가 불안정해질 수 있습니다. 필요한 경우 clock/ID 생성기를 주입하고 ‘만료 직전·같음·직후’를 고정값으로 검사합니다. 실제 시간 경과 검증과 업무 시각 검증은 구분합니다.

## 4. 독립성과 가변 객체

factory가 같은 list/dict 객체를 재사용하면 한 테스트의 수정이 다른 테스트에 섞일 수 있습니다. 요청마다 새 인스턴스를 만들고 DB 행 키·스키마/namespace를 분리합니다. 테스트 순서를 바꿔도 결과가 같아야 합니다.

성능을 위해 공유하는 읽기 전용 자료와 테스트가 변경하는 상태를 구분하세요. deep copy의 비용도 있으므로 모든 데이터를 무조건 복사하기보다 소유권을 정합니다.

## 5. 적용 과제

주문 데이터 factory의 기본값을 정하고, 무료배송 경계·빈 주문·중복 SKU·할인100%·잘못된 수량을 각각 어떻게 명시할지 적습니다. 기본 factory의 값 변화가 어떤 테스트에 영향을 줄지도 검토합니다.

보강: polyfactory 2.19.0의 DataclassFactory를 사용해 경계값을 명시하고 객체 독립성을 확인한 예제를 [10-7](07-python-toolkit.md)에 추가했습니다. 위 본문의 수동 factory와 비교하세요.
