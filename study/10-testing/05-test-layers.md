# 10-5. 단위·통합·계약·E2E

[목차](../README.md) · [정답·해설](05-test-layers-answers.md)

예상 50분. 목표: 실패가 생기는 경계에 맞춰 테스트를 배치하고, 속도·현실성·진단 비용을 비교합니다.

## 1. 이름보다 무엇을 실제로 연결했는가

단위 테스트는 작은 동작의 빠른 피드백, 통합 테스트는 여러 구성요소가 함께 동작하는 경계, 계약 테스트는 양쪽이 기대하는 요청·응답 의미, E2E는 사용자 경로의 넓은 흐름을 확인하는 데 초점을 둡니다. 조직마다 이름의 범위가 달라 반드시 실제 의존성을 적습니다.

이 자료의 ASGI API 테스트는 FastAPI routing·validation·직렬화를 함께 검사하지만 TCP/Uvicorn/TLS를 쓰지 않습니다. PostgreSQL 격리 실습은 실제 DB transaction을 사용했고, OAuth 실습은 테스트 제공자 계약입니다.

## 2. 테스트 배치

| 위험 | 효율적인 검증 위치 | 이유 |
| --- | --- | --- |
| 배송비 경계 계산 | 순수 함수 단위 | 빠르고 실패 원인 명확 |
| 잘못된 query 422 | ASGI API 통합 | validation과 응답 계약 |
| DB write skew | 실제 DB 두 세션 | mock은 격리 구현을 재현하기 어려움 |
| 외부 API 필드/권한 | 계약·제한된 실제 연동 | 대역 가정 검증 |
| 로그인 후 구매 전체 | 일부 E2E | 브라우저·세션·서비스 경로 연결 |

모든 규칙을 느린 E2E로만 검증하면 비용과 실패 진단이 커집니다. 반대로 단위만 있으면 설정·네트워크·migration·연동 문제가 빠집니다. 테스트 피라미드의 정확한 비율을 만능 규칙으로 쓰지 않고 위험과 피드백 시간을 기준으로 배치합니다.

## 3. flaky 테스트

임의 sleep, 공유 데이터, 포트 경합, 시간대/현재 시각, 외부 rate limit, 순서 의존이 흔한 원인입니다. 같은 코드에서 가끔 실패한다고 무조건 rerun으로 녹색을 만들면 실제 경쟁 버그를 숨길 수 있습니다.

완료 조건·Event·격리된 namespace·고정 clock·고유 포트·bounded wait를 사용하고 실패 시 증거를 남깁니다. 불안정 테스트 격리에는 담당자와 복구 조건을 정해야 합니다. 영구 skip은 위험을 없애지 않습니다.

## 4. 계약도 내용이 중요하다

status=200만 맞는 테스트는 필수 필드·단위·정렬·오류 의미·호환성을 놓칠 수 있습니다. 실제 소비자가 의존하는 최소 계약을 검사하고, 내부 필드를 모두 snapshot으로 고정해 사소한 변경마다 깨지지 않게 합니다.

소비자/제공자 계약 테스트는 버전 호환을 도울 수 있지만 실제 DB 성능·권한 설정·브라우저 정책까지 대체하지 않습니다.

## 5. 적용 과제

결제 API 변경 PR의 빠른 검사, merge 전 통합, 배포 후 smoke를 나누세요. 각 단계가 막는 구체적 실패와 검증하지 않는 범위를 적습니다.
