# 3-5. 블로킹·논블로킹, 동기·비동기

[목차](../README.md) · [이전](04-waiting.md) · [정답·해설](05-sync-async-answers.md)

예상 55분. 목표: 용어를 API 경계와 실행 주체에 붙여 설명하고, 2×2 표를 과도하게 일반화하지 않으며, 대기 방식의 비용을 비교합니다.

## 1. “동기=블로킹”이 헷갈리는 이유

문헌마다 synchronous/asynchronous가 가리키는 범위가 다릅니다. POSIX I/O의 완료 조건, 애플리케이션의 호출 방식, Python coroutine 문법을 하나의 표로 완전히 통일할 수 없습니다. **무슨 API를 누가 호출하며 어떤 완료를 기다리는지** 먼저 말하세요.

이 편에서 블로킹은 관찰한 호출이 끝날 때까지 **호출 스레드가 다른 앱 작업을 수행하지 못하는 것**, 논블로킹은 완료되지 않았어도 호출이 반환해 다음 행동을 선택할 수 있는 것으로 설명합니다. 동기는 호출 흐름에서 결과를 직접 확인·진행하는 방식, 비동기는 제출과 나중의 결과 전달·재개가 분리된 방식으로 사용합니다. 이 정의는 앱 설계 설명을 위한 것이며 모든 표준의 정의와 동일하지 않습니다.

## 2. 2×2 예시와 읽는 방법

| 결과를 다루는 방식 | 호출 스레드가 기다림 | 호출 스레드가 기다리지 않고 진행 가능 |
| --- | --- | --- |
| 호출 흐름이 직접 결과 확인 | 데이터가 올 때까지 블로킹 `recv()` | O_NONBLOCK 소켓 `recv()`가 EAGAIN이면 호출자가 다음 시도를 결정 |
| 제출·완료가 분리 | executor에 제출 후 미완료 `Future.result()`로 기다리는 조합 | executor 완료 callback, 또는 task를 시작하고 나중에 await하여 결과 취득 |

왼쪽 아래는 ‘비동기 제출 뒤 블로킹 대기를 조합했다’는 예입니다. 비동기 API 자체가 모두 블로킹이라는 뜻이 아닙니다. 오른쪽 위의 nonblocking read를 문헌에 따라 ‘비동기’라고 넓게 부르기도 하므로 표의 라벨보다 실제 흐름이 중요합니다.

Python의 `await`는 **현재 코루틴의 후속 진행을 기다리게** 할 수 있지만, 정상적인 비동기 대기에서는 **이벤트루프 스레드 전체를 멈추지 않습니다.** “기다리니 블로킹이다”라고만 말하면 task와 thread를 혼동합니다. 이미 완료된 awaitable은 바로 반환할 수 있어 모든 await가 반드시 다른 task에 실행 기회를 준다고도 할 수 없습니다.

## 3. readiness와 completion

Linux epoll 같은 메커니즘은 소켓이 읽기·쓰기 가능한 상태인지, 즉 **준비됨(readiness)**을 알려 줍니다. 이는 원하는 전체 업무가 끝났다는 뜻이 아닙니다. 읽을 때 일부 데이터만 얻거나 EOF·오류를 볼 수 있고 상태가 바뀔 수도 있습니다.

**완료 통지(completion)**는 제출한 특정 작업이 끝났음을 결과와 함께 알려주는 모델입니다. 앱 라이브러리는 내부에서 readiness를 사용하면서 사용자에게 Future·코루틴 형태의 완료를 제공할 수도 있습니다. 구현 계층을 구분해야 합니다.

이벤트루프는 실행할 일이 없을 때 OS 이벤트를 기다리는 호출에서 스레드를 재울 수 있습니다. 이것이 ‘앱의 비동기 I/O 구조가 틀렸다’는 뜻은 아닙니다. 지금 실행할 일이 없으니 효율적으로 쉬는 것과, 실행할 다른 task가 있는데 한 task의 동기 호출 때문에 멈추는 것은 다릅니다.

## 4. 대기 방식 비교

| 방식 | 이익 | 비용·조건 |
| --- | --- | --- |
| 블로킹 호출 | 순차 흐름이 단순 | 스레드 점유, 많은 대기에 자원 필요 |
| 논블로킹 반복 검사 | 호출 반환이 빠르고 직접 제어 가능 | 계속 검사하면 CPU 낭비, sleep 간격은 반응 지연 |
| readiness 기반 이벤트 처리 | 많은 대기 대상을 효율적으로 관리 | 부분 결과·상태·콜백/코루틴 수명 관리 |
| executor 오프로딩 | 기존 동기 라이브러리 재사용 | 스레드/프로세스 한도·취소·전달 비용 |

busy polling은 극단적인 저지연 환경 등에서 제한적으로 선택할 수 있지만 CPU·전력·다른 작업의 기회 비용이 듭니다. 일반 서버에서 무조건 빠른 방법으로 권하지 않습니다.

## 5. 코드 읽기 연습

```python
# 실행 흐름 설명용 조각. executor와 work는 호출 환경이 제공한다.
future = executor.submit(work)
result = future.result()  # 미완료면 이 호출 스레드를 기다리게 함
```

submit 후 즉시 result를 호출하면 호출자는 그 사이 다른 일을 하지 않습니다. 다른 스레드에서 work가 실행되어도 호출자에게 비동기의 이익이 자동으로 생기지 않습니다. 단, GUI와 분리된 제어 스레드 등 의도적인 용도가 있을 수 있습니다.

```python
# asyncio 문맥에서 호출하는 설명용 조각
result = await asyncio.to_thread(blocking_work)
```

blocking_work는 별도 스레드에서 대기할 수 있습니다. 현재 코루틴은 결과를 기다리지만 이벤트루프는 다른 작업을 진행할 수 있습니다. 작업 수명·스레드 한도는 별도로 필요하고, 대기 코루틴 취소가 이미 실행 중인 함수를 강제로 멈추지는 않습니다.

## 적용 과제

‘동기 함수’, ‘논블로킹 소켓’, ‘await’, ‘Future.result’, ‘epoll_wait’를 각각 **호출자, 대기 주체, 완료를 알게 되는 방식** 세 항목으로 설명하세요. 단어를 표에 넣는 것보다 실행이 어디서 멈추는지를 그리는 것이 목표입니다. 위 코드 조각은 단독 실행 프로그램이 아닙니다.
