# 3-2. 프로세스·스레드·컨텍스트 스위칭

[목차](../README.md) · [이전](01-hardware-os.md) · [정답·해설](02-process-thread-answers.md)

예상 45분. 목표: 격리·공유의 단위와 전환 비용을 구분하고, 자원을 어디에 보관해야 할지 판단합니다.

## 1. 프로세스와 스레드

프로세스는 주소 공간·핸들 등 자원을 가진 실행 환경입니다. 스레드는 그 안에서 명령을 실행하는 흐름으로, 자기 레지스터·스택 등을 가지며 같은 프로세스의 많은 자원을 공유합니다. 한 프로세스에 여러 스레드가 있을 수 있습니다.

| 비교 | 프로세스 | 같은 프로세스의 스레드 |
| --- | --- | --- |
| 일반 메모리 | 다른 프로세스와 기본적으로 분리 | 힙·전역 객체 등 공유 |
| 통신 | IPC·소켓·공유 메모리 등 필요 | 참조 공유 가능, 동기화 필요 |
| 실패 영향 | 일부 오류의 격리 경계가 됨 | 프로세스 손상·종료의 영향 공유 |
| 비용 | 생성·초기화·메모리·직렬화 | 스택·스케줄링·락·공유 상태 관리 |

프로세스 격리는 모든 장애의 완전한 격리가 아닙니다. 같은 호스트의 메모리 고갈·공유 DB 장애는 여러 프로세스를 함께 해칠 수 있습니다. 일반 Python 객체를 프로세스끼리 같은 변수 이름으로 만든다고 상태가 자동 공유되지 않습니다.

## 2. 컨텍스트 스위칭

OS가 실행 중인 스레드를 바꿀 때 레지스터·스케줄링 상태 등을 저장하고 다른 흐름을 복원합니다. 주소 공간이 달라지면 추가적인 메모리 관리 비용이 있을 수 있고 CPU 캐시·TLB에 영향이 생길 수 있습니다. 정확한 비용은 플랫폼·부하·이전 상태에 따라 달라 고정된 나노초 숫자로 외우지 않습니다.

함수 호출, 코루틴의 일시 중단, 시스템 호출, OS 스레드 전환은 같은 사건이 아닙니다. 시스템 호출은 커널 모드로 넘어가지만 대기·스케줄링 없이 반환할 수도 있습니다. `await`에서 다른 task로 넘어가는 것은 일반적으로 사용자 공간의 협력적 스케줄링입니다.

## 3. 공유가 쉬우면 무엇이 어려워지나

‘잔액을 읽고→검사하고→차감하고→저장’하는 복합 동작에서 두 스레드가 같은 옛 값을 읽으면 갱신이 사라질 수 있습니다. 단순 자료구조의 내부 안전과 업무 규칙의 원자성은 다릅니다. GIL이 있어도 이 복합 계약을 자동 보장하지 않습니다.

| 대응 | 이익 | 감수할 비용 |
| --- | --- | --- |
| Lock으로 보호 | 임계 구역의 동시 접근 제어 | 대기·교착·락 범위 관리 |
| 메시지 큐로 소유자 한 곳에 전달 | 공유 가변 상태 축소 | 큐 대기·메시지 처리·종료 설계 |
| 불변 데이터·복사 | 읽는 쪽의 추론이 쉬움 | 복사·할당·최종 결과 합치기 |
| 프로세스 분리 | 주소 공간과 실패 경계 강화 | IPC·직렬화·복제·배포 비용 |

락은 짧고 필요한 영역을 보호하되 실제 불변 조건을 지켜야 합니다. 데이터 읽기만 락으로 감싸고 검사·갱신을 바깥에서 하면 경쟁이 남을 수 있습니다. 서로 다른 락의 획득 순서가 다르면 교착 상태가 생길 수 있습니다.

## 4. 선택 사례

CPU 계산을 독립적인 입력별로 나누고 결과가 작다면 프로세스 분리가 유리할 수 있습니다. 큰 배열을 매번 복사해야 하면 IPC 비용이 지배할 수 있으므로 데이터 배치·공유 메모리·GIL을 해제하는 라이브러리 등을 비교합니다.

기존 동기 HTTP SDK로 I/O를 병행하고 클라이언트의 스레드 안전 조건을 충족한다면 스레드가 간단한 선택일 수 있습니다. 수만 개 스레드를 만들기 전에 한도·풀·취소·대기를 설계합니다. 인터프리터 제약은 3-8에서 분리해 다룹니다.

## 적용 과제

두 프로세스의 전역 캐시, 한 프로세스의 두 스레드가 공유하는 리스트, 두 코루틴이 공유하는 dict를 그립니다. 누가 무엇을 공유하는지와 동시 변경 시 필요한 규칙을 표시하세요. ‘하나의 스레드니까 경쟁이 없다’고 단정하지 말고 코루틴이 양보하는 지점도 생각해 봅니다.
