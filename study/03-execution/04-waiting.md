# 3-4. CPU 바운드와 I/O 바운드

[목차](../README.md) · [이전](03-concurrency.md) · [정답·해설](04-waiting-answers.md)

예상 40분. 목표: 경과 시간과 CPU 시간을 구분하고, 대기가 생기는 위치를 찾으며, 병목이 이동할 수 있음을 설명합니다.

## 1. 오래 걸리는 이유는 하나가 아니다

**CPU 바운드**는 필요한 계산을 처리하는 CPU 능력이 주요 제한인 상태, **I/O 바운드**는 저장장치·네트워크 등 I/O 처리와 대기가 주요 제한인 상태를 뜻합니다. 함수 이름이나 언어가 아니라 **관찰한 부하와 실행 환경**을 기준으로 말해야 합니다.

JSON API도 작은 입력에서는 외부 조회 대기가, 큰 입력에서는 압축·직렬화 CPU가 병목일 수 있습니다. 파일 읽기도 메모리 캐시에 있으면 디스크보다 메모리 복사·파싱 비용이 더 중요할 수 있습니다. 같은 코드가 항상 같은 종류인 것은 아닙니다.

## 2. 경과 시간과 CPU 시간

| 측정 | 의미 | 해석의 한계 |
| --- | --- | --- |
| wall time | 시작부터 완료까지 실제 경과 | 대기·스케줄링·다른 작업 포함 |
| process CPU time | 해당 프로세스가 CPU에서 실행한 시간 | 별도 프로세스의 작업은 포함하지 않을 수 있음 |
| 개별 구간 시간 | 풀 획득·연결·외부 호출·직렬화 등 | 구간이 겹치면 단순 합계 주의 |

여러 스레드가 여러 코어에서 병렬로 CPU를 쓰는 환경에서는 프로세스 CPU 시간이 wall time보다 클 수도 있습니다. 단순히 ‘CPU 시간은 항상 경과 시간보다 작다’고 외우지 않습니다. 멀티프로세스 측정에서 부모 CPU만 보고 전체 작업이 I/O 바운드라고 판단해서도 안 됩니다.

## 3. I/O 대기 중 스레드는 무엇을 하나

블로킹 I/O 호출의 스레드는 결과가 가능해질 때까지 잠들고 OS는 다른 실행 가능한 스레드에 CPU를 줄 수 있습니다. 데이터가 도착해도 즉시 실행되는 것이 아니라 실행 기회를 기다릴 수 있습니다. 대기하는 동안 스택·소켓·풀 슬롯 등 자원은 계속 점유할 수 있습니다.

I/O 대기와 락 대기, 풀 획득 대기는 다릅니다. CPU가 낮고 지연이 높다고 무조건 인터넷이 느린 것은 아닙니다. 외부 호출 직전의 풀 대기일 수도 있고 서로 락을 기다리는 교착일 수도 있습니다.

## 4. 대응 비교

| 관찰한 제한 | 먼저 비교할 방법 | 얻는 이익 | 감수할 비용 |
| --- | --- | --- | --- |
| 순수 Python 계산 | 알고리즘·배치·프로세스·적절한 확장 모듈 | 계산량 감소·병렬 용량 | 구현·전달·메모리·환경 비용 |
| 외부 네트워크 대기 | 호출 수 감소·재사용·동시성·캐시 | 왕복·유휴 시간 감소 | 하류 부하·신선도·제어 복잡성 |
| DB 풀 대기 | 연결 누수·긴 트랜잭션·쿼리 확인 | 실제 점유 원인 감소 | 원인 분석·계약 변경 |
| 락 대기 | 임계 구역 축소·소유 구조 개선 | 경합 감소 | 원자성 보존·설계 비용 |
| 메모리 압박 | 스트리밍·복사 감소·작업 제한 | 상주 데이터·페이지 비용 감소 | 지연 실행·수명 관리 복잡성 |

CPU가 바쁜데 task 개수만 늘리거나, DB가 포화인데 풀만 키우는 것은 병목을 악화시킬 수 있습니다. 하나를 개선하면 그다음 제한이 나타납니다. 외부 호출을 줄인 뒤 JSON 압축이 병목이 되는 것은 개선 실패가 아니라 다음 단계의 관찰일 수 있습니다.

## 적용 과제

요청 하나의 시간을 ‘풀 획득 200ms, 네트워크·서버 응답 30ms, 파싱 5ms’로 가정합니다. ‘네트워크가 느리다’는 주장에 어떤 증거가 부족한지 적고, 풀을 늘릴 때 하류 용량·점유 원인 중 무엇을 확인할지 설명하세요. 숫자는 실제 측정이 아닌 학습용 상황입니다.
