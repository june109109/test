# 3-9. CPU·I/O 동시성 비교 실습

[목차](../README.md) · [이전](08-gil.md) · [정답·해설](09-benchmark-answers.md)

예상 70분. 목표: 같은 작업을 네 방식으로 실행하고, 결과의 정확성과 측정 경계를 확인하며, 관찰 범위 안에서 성능을 해석합니다.

## 1. 확인할 가설

1. GIL이 있는 CPython의 순수 Python 계산은 스레드를 늘려도 여러 코어의 선형 가속을 기대하기 어렵다.
2. 충분한 CPU 예산과 작업량이 있으면 프로세스가 계산 시간을 줄일 수 있지만 시작·전달 비용이 든다.
3. 외부 응답 대기를 겹치면 총 완료 시간이 줄어들 수 있다.
4. 코루틴 문법만으로 같은 루프의 CPU 계산이 병렬화되지는 않는다.

결론을 맞추려고 유리한 표본만 남기지 않습니다. 기대와 다른 결과가 나오면 작업량·측정 경계·환경·결과의 동일성을 조사합니다.

## 2. 실험 구성

[실행 코드](../labs/concurrency_bench.py)는 외부 패키지 없이 다음을 수행합니다. Python 3.11 이상이 필요하며 검증 환경은 CPython 3.12.14입니다.

| 항목 | 기본값·의미 |
| --- | --- |
| 계산 | task마다 800,000번의 순수 Python 정수 계산 |
| 작업 수 | CPU·I/O 각각 8개 |
| 병행 수 | 스레드·프로세스 워커 4, asyncio semaphore 4 |
| I/O | 실제 loopback TCP로 요청 1바이트·응답 1바이트 |
| 서버 지연 | 요청을 받으면 50ms 기다린 후 응답 |
| 반복 | 네 방식 각각 3회, 순서를 회차마다 회전 |
| 시간 | perf_counter로 제출·처리·결과 수집의 경과 시간 측정 |
| 정확성 | 모든 작업 결과가 순차 결과와 같은지 검사, 잘못된 응답이면 실패 |
| 프로세스 생성 | spawn 명시, 풀 생성·워밍업은 별도 기록 |

서버의 `sleep`은 통제된 응답 지연을 만드는 데 사용됩니다. **클라이언트는 실제 소켓 I/O를 기다립니다.** 실제 인터넷·TLS·HTTP·DB의 복잡성을 재현하지는 않습니다. 서버도 같은 머신에서 스레드를 사용하므로 그 스케줄링 비용이 결과에 포함됩니다.

프로세스 풀을 만들기 전에 이미 서버 스레드가 있으므로 fork 상속 대신 spawn을 명시했습니다. 계산 함수는 모듈 최상위에 있고 실행 진입점은 main guard로 보호합니다. 실습이 끝나면 풀과 서버를 닫습니다.

## 3. 실행 방법

```bash
cd /workspace/test
python3 study/labs/concurrency_bench.py --output /tmp/concurrency-my-run.json
```

다른 경로에 내려받았다면 저장소 최상위에서 같은 상대 경로로 실행하세요. 출력 파일이 이미 있으면 덮어쓰지 않고 실패하므로 새 이름을 사용합니다. 로컬 소켓·프로세스 생성이 허용된 실행 환경이 필요합니다.

부하를 바꾸고 싶다면 주요 변수 하나만 바꿉니다.

```bash
python3 study/labs/concurrency_bench.py --iterations 2000000 --output /tmp/concurrency-larger-cpu.json
```

기본값 외의 실험은 독자 과제이며 아래 측정 표에 섞지 않습니다. 인자는 실수로 너무 큰 부하를 만들지 않도록 상한을 두었습니다. 통계적 성능 시험·긴 부하 시험은 11장에서 별도로 설계합니다.

## 4. 실제 측정 결과

2026-10-01에 이 환경에서 실행했습니다. [원본 JSON](../results/concurrency-2026-10-01.json)에 개별 측정값·환경·검증 상태를 보존했습니다.

- CPython 3.12.14, Linux, 보이는 CPU·affinity 각각 5개.
- cgroup v2 `cpu.max`는 `400000 100000`: 약 4 CPU의 시간 예산. 전용 코어 보장은 아닙니다.
- spawn 워커 4개의 서로 다른 PID를 워밍업에서 확인했습니다.
- CPU와 I/O 각각 `4방식 × 3회 × 8작업`, 총 **192개 측정 작업 결과가 일치**했습니다. 작업을 생략하거나 실패한 빠른 요청을 성공으로 세지 않았습니다.

| 작업 | 순차 | 스레드 4 | 프로세스 4 | asyncio, 동시성 4 |
| --- | ---: | ---: | ---: | ---: |
| CPU, 8개 완료 중앙값 | 0.399853초 | 0.424584초 | 0.214645초 | 0.368216초 |
| I/O, 8개 완료 중앙값 | 0.408343초 | 0.105653초 | 0.105895초 | 0.109361초 |

**별도 초기화·워밍업 구간:** 스레드 약 0.101초, 프로세스 약 0.287초. 이 구간에는 워커를 깨우기 위한 0.1초 대기 작업이 포함되므로 순수한 프로세스 생성 비용으로 읽으면 안 됩니다. 본 표에서는 준비된 풀을 재사용했으며 프로세스 생성·종료 전체 비용을 포함하지 않습니다. 일회성 배치 도구의 총시간을 알고 싶다면 프로그램 시작부터 종료까지 별도 측정해야 합니다.

## 5. 어떻게 해석해야 하나

**CPU:** 프로세스 중앙값은 순차의 약 1.86배 가속이지만 네 배는 아닙니다. 전달·스케줄링·실제 CPU 이용·작업 분배 등의 비용이 있습니다. 프로세스의 세 표본도 약 0.142~0.229초로 변동이 있어 정밀한 배수로 일반화하면 안 됩니다.

스레드는 이 조건에서 개선되지 않았습니다. asyncio 값이 순차보다 조금 낮아도 병렬화의 증거가 아닙니다. 코드상 CPU 계산 중 await가 없어서 한 루프에서 순차로 계산합니다. 짧은 측정의 변동·실행 시점·캐시 등 영향을 분리하지 못했으므로 ‘asyncio가 CPU 계산을 가속했다’고 결론 내리지 않습니다.

**I/O:** 이상적 지연만 보면 순차는 `8×0.05=0.4초`, 병행 수 4이면 두 묶음으로 `ceil(8/4)×0.05=0.1초`입니다. 실제 측정이 이 근처여서 대기를 겹친 효과와 부합합니다. 별도의 CPU 병렬 계산이 빨라졌다는 뜻은 아닙니다.

스레드·프로세스·asyncio의 I/O 시간 차이가 작으므로 이 표만으로 도구 우승자를 고르지 않습니다. 메모리·CPU·구현 난이도·기존 SDK·수만 연결의 거동·취소·운영을 추가로 봐야 합니다. 이 실험은 그런 값을 측정하지 않았습니다.

## 6. 결과를 왜곡하기 쉬운 실수

| 실수 | 왜 문제인가 | 개선 |
| --- | --- | --- |
| 프로세스만 초기화 포함 | 같은 구간 비교가 아님 | cold end-to-end와 warm 작업 구간 분리 |
| I/O라고 sleep만 측정 | 실제 소켓·프로토콜·서버 비용 부재 | 목적을 명시하고 필요한 실제 I/O 포함 |
| 방식마다 작업 수 다름 | 빠른 이유가 적은 일일 수 있음 | 결과 개수와 값 비교 |
| 실패 요청을 빨랐다고 집계 | 처리한 유효 업무량이 다름 | 오류와 성공·완료 수 분리 |
| 워커 수=할당 CPU라고 가정 | quota·경쟁·SMT 무시 | 실제 제한·부하 기록 |
| 평균 하나만 보고 결론 | 변동·꼬리·작은 표본 문제 | 원본 표본과 한계 보존 |

이 코드도 완벽한 벤치마크는 아닙니다. 회차 수가 작고 전체 순서를 완전히 무작위화하지 않았으며 같은 머신의 서버와 공유 호스트 영향을 받습니다. 교육용 원리 확인과 상용 시스템 성능 검증을 구분합니다.
