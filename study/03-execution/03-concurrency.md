# 3-3. 동시성과 병렬성

[목차](../README.md) · [이전](02-process-thread.md) · [정답·해설](03-concurrency-answers.md)

예상 40분. 목표: 겹쳐 진행되는 작업과 동시에 실행되는 계산을 구분하고, 처리량·응답성·자원 사용의 목표를 나눕니다.

## 1. 한 코어에도 동시성이 있다

**동시성**은 여러 작업이 완료되기 전까지 겹쳐 진행되도록 다루는 구조입니다. **병렬성**은 여러 작업이 실제 같은 시각에 실행되는 성질입니다. 한 코어가 A를 하다가 B를 처리하면 동시성은 있지만 그 순간에 두 Python 계산을 같은 코어가 실행하는 것은 아닙니다.

```text
한 실행 흐름, 순차:  A계산 ─ A대기 ─ A완료 ─ B계산 ─ B대기 ─ B완료
한 코어, 동시성:     A계산 ─ B계산 ─ A/B 대기 ─ A완료 ─ B완료
여러 코어, 병렬:     코어1: A계산 ───────── A완료
                    코어2: B계산 ───────── B완료
```

이 그림은 개념 모델입니다. 대기가 겹치는 정도와 완료 순서는 실제 작업·도착 시점에 따라 달라집니다. 한 스레드의 이벤트루프도 여러 I/O의 대기를 겹칠 수 있고, 여러 프로세스라도 CPU quota가 작으면 같은 자원을 경쟁합니다.

## 2. 세 가지 목표를 구분하기

| 목표 | 관찰할 지표 | 혼동하기 쉬운 점 |
| --- | --- | --- |
| 응답성 | 짧은 작업이 빨리 기회를 얻는가, 루프 지연 | 긴 작업의 총시간 단축과 다름 |
| 처리량 | 단위 시간에 완료하는 유효 작업 수 | 오류로 빨리 끝낸 요청까지 성공으로 세지 않기 |
| 개별 지연 | 한 작업의 시작부터 끝까지 | 동시성 증가로 경쟁이 커지면 오히려 증가 |

I/O를 겹치면 총 완료 시간과 처리량이 좋아질 수 있지만 한 요청의 외부 서버 처리 시간이 줄어든 것은 아닙니다. CPU 작업을 잘게 쪼개 번갈아 실행하면 UI가 반응할 수 있지만 총 계산량은 그대로이고 전환 비용이 추가됩니다.

## 3. 병렬화의 한계

실행 시간의 20%가 반드시 순차이고 나머지 80%만 이상적으로 병렬화된다고 가정합니다. 4개 실행 자원에서 상대 시간은 `0.2 + 0.8/4 = 0.4`, 속도 향상은 `1/0.4 = 2.5배`입니다. 무한히 자원을 늘려도 순차 부분 때문에 이 단순 모델의 상한은 5배입니다.

이는 Amdahl 형태의 이상화된 계산입니다. 통신·스케줄링·락·자원 경쟁·부하 변화가 없다고 가정하므로 실제 예측에는 추가 비용이 필요합니다. 작업 자체가 커지는 경우나 파이프라인 등에서는 다른 분석이 필요합니다.

## 4. 동시성에도 상한이 필요한 이유

동시에 진행되는 작업은 대기 중이라도 메모리·소켓·파일·연결·큐 자원을 사용합니다. 무제한 task 생성은 이벤트루프를 쓰더라도 메모리 고갈과 하류 과부하를 만들 수 있습니다.

| 전략 | 이익 | 비용 |
| --- | --- | --- |
| 동시성 제한 | 자원·하류 부하 보호 | 큐 대기·거절 정책 필요 |
| 더 많은 병렬 자원 | 병렬 계산 용량 증가 | 비용·직렬 구간·공유 자원 제한 |
| 작업 분할·양보 | 짧은 작업의 응답성 개선 | 구현 복잡성·전체 실행 비용 |

선택은 목표에서 시작합니다. 빠른 버튼 반응이 목표라면 긴 계산을 다른 실행 자원으로 옮기거나 분할할 수 있습니다. 대량 일괄 계산의 처리량이 목표라면 큰 단위의 병렬 작업과 전달 비용을 봅니다.

## 적용 과제

작업 A와 B가 각각 계산 10ms→외부 대기 100ms→계산 10ms라고 가정합니다. 순차와 대기 중 계산을 겹치는 시간선을 그리세요. 처리량 개선이 어디에서 생기는지, 두 외부 요청 자체는 각각 100ms 걸린다는 점을 표시합니다. 계산 모델이며 실제 측정은 3-9에서 진행합니다.
