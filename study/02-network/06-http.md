# 2-6. HTTP와 stateless: 요청의 의미와 앱의 상태

[목차](../README.md) · [이전](05-connections.md) · [정답·해설](06-http-answers.md)

예상 60분. 목표: 요청·응답의 의미, 상태 유지 위치, safe·idempotent의 차이, 실패 후 재시도 위험을 설명하고 작은 실습으로 확인합니다.

## 1. 요청과 응답의 구성

HTTP/1.1을 사람이 읽기 쉽게 표시하면 다음과 같습니다. 실제 줄 구분은 CRLF이며 HTTP/2·3의 전송 형식은 이 텍스트와 다릅니다.

```http
GET /items/7 HTTP/1.1
Host: api.example.com
Accept: application/json

```

메서드가 의도를, 대상 경로와 호스트가 리소스를, 필드가 요청 조건·표현·인증 등 추가 의미를 전달합니다. 응답은 상태 코드, 필드, 필요하면 본문을 포함합니다. URL이 반드시 디스크의 실제 파일을 의미하지는 않습니다.

## 2. stateless가 의미하는 것

RFC 9110의 stateless는 각 요청의 의미를 독립적으로 이해할 수 있고 연결과 메시지의 관계가 그 해석을 결정하지 않는다는 뜻입니다. 같은 연결의 다음 요청이라고 앞 요청의 사용자를 자동으로 이어받으면 안 됩니다.

**서버에 데이터가 없다**는 뜻도, **로그인을 구현할 수 없다**는 뜻도 아닙니다. 앱은 세션·DB·쿠키·토큰으로 상태를 구현할 수 있습니다. 요청에 세션 식별자나 자격 정보가 들어오면 서버는 그에 맞는 상태를 조회·검증합니다.

| 설계 | 얻는 이익 | 감수하는 비용 |
| --- | --- | --- |
| 서버 세션 + 식별자 | 중앙에서 세션 폐기·정책 변경 용이 | 공유 저장소·조회·수명 관리 |
| 자체 포함 토큰 | 매 요청 세션 조회를 줄일 수 있음 | 크기·검증·키 회전·만료·즉시 폐기 문제 |
| 프로세스 메모리 세션 | 구현이 단순하고 조회 빠름 | 재시작 소실·다중 워커 불일치·sticky 의존 |

이들은 HTTP 위의 앱 설계입니다. 자체 포함 토큰도 사용자 상태 조회가 필요한 경우가 있어 ‘완전히 무상태’라고 단정하지 않습니다. 세부 인증은 6장에서 다룹니다.

## 3. safe와 idempotent

**safe**는 클라이언트가 리소스 상태 변경을 요청하지 않는 의미입니다. 접근 로그 같은 부수 효과가 전혀 없다는 뜻은 아닙니다. **idempotent(멱등)**는 같은 요청을 여러 번 수행할 때 의도한 서버 효과가 한 번 수행했을 때와 같다는 뜻입니다. 응답 코드·본문이 매번 같다는 뜻은 아닙니다.

| 메서드 | 대표 의도 | safe | 규격상 멱등 |
| --- | --- | --- | --- |
| GET | 현재 표현 조회 | 예 | 예 |
| HEAD | GET에 해당하는 메타정보, 응답 본문 없음 | 예 | 예 |
| PUT | 지정 리소스의 상태 생성·교체 | 아니오 | 예 |
| DELETE | 지정 리소스와 기능의 연결 제거 | 아니오 | 예 |
| POST | 대상 리소스가 정한 처리 | 아니오 | 일반적으로 보장 안 됨 |

GET에 삭제 동작을 넣으면 크롤러·미리 읽기·재시도·캐시와 충돌할 수 있습니다. DELETE를 두 번 보내 첫 응답이 204, 다음이 404여도 최종 의도인 ‘없음’이 유지되면 멱등성과 모순되지 않습니다. PATCH는 일반적으로 멱등을 보장하지 않지만 구체적인 작업은 멱등일 수 있습니다.

POST도 앱이 멱등성 키를 저장·검증해 중복 처리를 막는 계약을 만들 수 있습니다. 키의 사용자 범위·유효 기간·동일 키의 다른 내용·실패 후 재시도 처리를 함께 정해야 합니다.

## 4. 상태 코드를 업무 완료로 해석하기

| 상태 | 의미의 예 | 주의점 |
| --- | --- | --- |
| 200 / 201 | 성공 / 리소스 생성 | 앱의 계약에 맞는 본문·상태 확인 |
| 202 | 처리 접수, 아직 완료 아님 | 결과 조회·실패 경로 필요 |
| 204 | 성공, 응답 내용 없음 | JSON 본문을 기대하지 않기 |
| 304 | 조건부 조회에서 기존 표현 재사용 가능 | 일반적인 빈 200과 다름 |
| 400 / 401 / 403 | 요청 문제 / 유효한 인증 부족 / 요청 거부 | 무조건 재시도할 문제가 아님 |
| 404 / 409 | 찾지 못함 / 현재 상태와 충돌 | 앱 계약에 따라 대응 |
| 429 / 503 | 요청 과다 / 서비스 사용 불가 | 재시도 예산·서버 안내·폭주 방지 |

응답을 못 받았을 때 서버가 처리하지 않았다고 확신할 수 없습니다. 무조건 재시도하지 말고 메서드와 앱의 멱등성 계약을 확인합니다. 401 응답에는 적절한 인증 challenge가 필요하다는 등의 세부 규칙도 구현 시 봐야 합니다.

## 5. 실행 실습: 같은 연결, 다른 응답, 같은 최종 상태

준비: Python 3.10 이상, 외부 패키지 없음. 다음 스크립트는 로컬 loopback의 임시 포트를 열고 자기 자신에게만 요청한 뒤 종료합니다.

```bash
cd /workspace/test
python3 study/labs/http_semantics.py
```

다른 위치에 자료를 받았다면 저장소 최상위에서 같은 상대 경로 명령을 실행하세요. [실습 코드](../labs/http_semantics.py)는 다음을 검증합니다.

1. GET으로 리소스와 ETag를 받습니다.
2. 같은 연결에서 조건부 GET을 보내 304와 빈 본문을 확인합니다.
3. 새 연결은 다른 연결 식별자를 받는지 확인합니다.
4. DELETE 두 번의 상태가 204와 404여도 최종 GET이 404인지 확인합니다.

ETag는 표현 버전을 식별하는 validator입니다. 조건부 요청의 자세한 의미는 2-8에서 다룹니다. 여기의 ETag 처리는 단일 고정 값에 대한 학습용 부분 구현이며 전체 헤더 문법·동시 수정·영속 저장을 구현하지 않습니다. 쿠키·인증·TLS도 넣지 않았고 운영 서버로 사용하지 않습니다.

2026-10-01, 이 자료의 실행 환경(Python 3.12.14)에서 7개 검증을 실제로 통과했습니다. 처음에는 명령 sandbox의 소켓 제한으로 실행이 차단되었고, 허용된 실행 권한으로 다시 수행했습니다.

각 검증은 `PASS`로 표시되고 실패하면 비정상 종료합니다. 포트는 운영체제가 빈 포트로 정하며 항상 닫습니다. 실행이 소켓 권한으로 차단되면 허용된 로컬 실행 환경에서 수행해야 합니다. 이 실습은 네트워크 지연 벤치마크가 아닙니다.
