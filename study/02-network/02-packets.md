# 2-2. 패킷·라우터·해저광케이블

[목차](../README.md) · [이전](01-navigation.md) · [정답·해설](02-packets-answers.md)

예상 50분. 목표: 데이터를 나누는 이유와 비용, 링크의 속도와 거리의 차이, MTU와 전송 계층 분할을 구분합니다.

## 1. 긴 파일을 하나의 거대한 덩어리로 보내면

공유 링크를 한 사용자가 오랫동안 독점하고, 오류가 발생했을 때 큰 범위를 다시 전송해야 할 수 있습니다. 패킷 교환은 데이터를 작은 전송 단위로 나누고 여러 흐름이 링크를 공유하도록 합니다. 빈 시간에 다른 흐름의 데이터를 보내는 **통계적 다중화**가 가능하지만, 경쟁이 생기면 큐 대기와 손실이 발생합니다.

패킷은 ‘원래 HTTP 요청을 같은 크기로 잘라 놓은 조각’과 일대일로 대응하지 않습니다. 애플리케이션의 읽기·쓰기 경계, TCP segment, IP packet, 링크 frame은 서로 다른 계층의 단위입니다.

```mermaid
flowchart LR
    A[HTTP 데이터] --> B[TCP 바이트 스트림 또는 QUIC 스트림]
    B --> C[IP 패킷]
    C --> D[Wi-Fi·Ethernet 등 링크 프레임]
    D --> E[다음 홉 라우터]
    E --> F[다음 링크에 맞는 프레임]
```

이 그림에서 TCP와 QUIC의 구체적인 포장은 다릅니다. QUIC는 UDP 데이터그램에 실리며 하나의 QUIC 패킷에 여러 스트림의 프레임이 들어갈 수도 있습니다. 지금은 계층별 단위가 같지 않다는 점을 기억하세요.

## 2. 라우터는 무엇을 보고 어디로 보내나

라우터는 일반적으로 목적지 IP와 라우팅 정보를 바탕으로 다음 홉을 정합니다. 패킷마다 전체 인터넷 지도를 새로 계산하는 것은 아닙니다. 제어 영역에서 배운 경로를 전달 테이블에 반영하고, 데이터 전달 시 이를 사용합니다. 정책·동일 비용 경로·네트워크 상태 때문에 왕복 경로가 같다고 보장되지 않습니다.

다른 경로를 지날 가능성은 있지만, 모든 패킷을 일부러 서로 다른 길로 보내야 하는 것은 아닙니다. 흐름별로 같은 경로를 유지하려는 구현도 있습니다. IP는 순서·전달을 보증하지 않으며 필요한 신뢰성은 상위 계층에서 제공합니다.

## 3. 패킷 교환과 전용 자원 비교

| 방식 | 얻는 이익 | 감수할 비용 | 적합한 조건 |
| --- | --- | --- | --- |
| 공유 패킷 교환 | 버스트 트래픽의 자원 활용, 여러 흐름 공존 | 큐잉·손실·지연 변동 | 웹·일반 데이터 통신 |
| 예약·전용 용량 | 상대적으로 예측 가능한 자원 | 미사용 시간의 비용, 유연성 제약 | 안정된 용량·지연 요구와 비용 감당 |

현실의 네트워크는 두 방식을 결합할 수 있습니다. 전용 회선을 쓰더라도 양 끝 애플리케이션에서 패킷으로 데이터를 보내고 다른 구간에서 공유 자원을 사용할 수 있습니다.

패킷을 작게 하면 한 번에 차지하는 시간이 줄고 일부 오류의 복구 범위가 작아질 수 있습니다. 너무 작으면 헤더 비중과 패킷 처리 횟수가 늘어납니다. 크게 하면 헤더 효율은 좋아지지만 링크 제한·대기·손실 비용을 고려해야 합니다. ‘작을수록 좋음’도 ‘클수록 빠름’도 일반 규칙이 아닙니다.

## 4. MTU, MSS, IP 단편화

**MTU**는 해당 링크가 운반할 수 있는 네트워크 계층 패킷 크기의 한도입니다. 일반적인 Ethernet에서 IP MTU 1500바이트가 흔하지만 터널·다른 링크에서는 달라집니다. **경로 MTU**는 경로 전체에서 통과 가능한 크기와 관련됩니다.

**TCP MSS**는 TCP segment의 데이터 부분 크기입니다. IP·TCP 헤더 공간을 고려하므로 MTU와 같지 않습니다. IP MTU 1500, IPv4 헤더 20, TCP 헤더 20, 추가 옵션 없음이라는 단순 조건에서는 데이터 공간이 1460바이트입니다. 옵션·IPv6·터널을 쓰면 값이 달라집니다.

TCP가 바이트 스트림을 segment로 나누는 것과 **IP 단편화**는 다릅니다. IPv4에서는 조건에 따라 라우터가 단편화할 수 있지만, IPv6에서는 라우터가 단편화하지 않고 송신 측이 크기를 조절하거나 필요한 단편화를 수행합니다. 경로 MTU 탐색이 이를 돕습니다. 장비의 segmentation offload 때문에 패킷 캡처에 실제 선로보다 큰 단위가 보일 수도 있습니다.

단편 중 일부가 사라지면 재조립이 실패하므로 상위 데이터 전달에 영향을 줍니다. 앱은 큰 UDP 데이터그램을 무작정 보내기보다 경로와 프로토콜에 맞는 크기를 정해야 합니다.

## 5. 대역폭과 지연을 계산하기

| 성분 | 의미 | 개선 방향 |
| --- | --- | --- |
| 전파 지연 | 신호가 물리적 거리를 가는 시간 | 가까운 리전·CDN, 경로 개선 |
| 직렬화 지연 | 패킷 비트를 링크에 밀어 넣는 시간 | 링크 속도, 크기·압축 |
| 큐 대기 | 앞선 데이터와 자원 경쟁 | 부하 관리·큐 제어·용량 |
| 처리 지연 | 라우터·종단 처리 | 장비·CPU·구현 개선 |

학습용 계산: 1500바이트를 100Mbps 링크에 올리는 시간은 `1500×8 / 100,000,000 = 0.00012초 = 0.12ms`입니다. 링크의 다른 오버헤드와 대기는 생략한 값입니다.

광섬유 안의 신호 속도를 약 `200,000km/s`로 단순화하면 10,000km 경로의 한 방향 전파만 약 50ms, 왕복만 약 100ms입니다. 실제 케이블은 직선이 아니고 육상 구간·장비·큐 등이 더해집니다. 링크를 10배 넓혀도 이미 작은 직렬화 시간은 줄지만 거리는 사라지지 않습니다.

## 6. 해저광케이블과 서비스 설계

대륙 간 트래픽은 해저광케이블 등의 물리 경로를 지나고, 육양국과 육상 망을 거쳐 서버에 도달합니다. 광 증폭·다중 파장 같은 기술로 용량을 늘리더라도 거리와 경로의 제약은 남습니다. 지도상 가까운 도시가 실제 네트워크 경로에서도 가장 가깝다고 보장되지 않습니다.

지역 복제본·CDN은 거리 비용을 줄일 수 있지만 저장·복제·일관성·무효화·운영 비용이 듭니다. ‘해외 사용자가 느리다’면 필요한 데이터가 캐시 가능한지, 쓰기 동기화는 어떻게 할지 함께 판단해야 합니다.

## 적용 과제

실제 패킷 캡처 없이 계산으로 시작합니다. 1,000바이트 패킷을 10Mbps와 100Mbps 링크에 보낼 때 직렬화 시간을 비교하고, 한 방향 광섬유 경로가 5,000km라면 왕복 전파 시간을 근사하세요. 어느 부분이 회선 증설로 줄고 어느 부분이 그대로인지 표시합니다. 이 계산은 실제 네트워크 벤치마크가 아닙니다.

## 퀴즈

Q1·Q2 각 1점, Q3·Q4 각 2점, Q5 4점. 권장 통과 8점.

### Q1
HTTP 요청 한 개는 항상 IP 패킷 한 개에 대응하나요?

### Q2
IPv6 라우터는 너무 큰 패킷을 직접 잘라서 전달하나요?

### Q3
MTU 1500, IPv4 헤더 20, TCP 헤더 20, 추가 옵션 없음일 때 데이터 공간을 구하고 실제 모든 연결에 같은 값을 적용할 수 없는 이유를 쓰세요.

### Q4
10,000km 광섬유, 전파 속도 200,000km/s라는 가정에서 최소 왕복 전파 지연을 계산하세요. 대역폭을 두 배 늘리면 이 값이 절반이 되나요?

### Q5
해외의 작은 API 요청이 느립니다. ‘패킷을 크게 하고 회선을 늘리자’는 제안을 평가하세요. 확인할 지연 성분, 대안 두 가지, 대안의 비용을 포함합니다.
