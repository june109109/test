# 2-9. 정답과 해설

[본문](09-http-versions.md)

## Q1 — pipelining이 있다, 1점

HTTP/1.1은 여러 요청을 미리 보낼 수 있지만 응답 순서를 유지해야 합니다. 브라우저에서 널리 사용되지 않았다는 사실과 규격에 없다는 주장은 다릅니다. 복습: 2절.

## Q2 — 없애지 못한다, 1점

HTTP/2는 HTTP 메시지를 다중화하지만 TCP는 하나의 순서 있는 바이트 스트림입니다. 앞바이트 손실로 뒤바이트 전달이 늦어지면 여러 HTTP 스트림이 영향을 받습니다. 복습: 3절.

## Q3 — 전달 격리와 공유 자원은 다름, 2점

QUIC가 스트림별 순서 전달을 제공하지만 한 패킷에 여러 스트림 데이터가 들어 있으면 복수 스트림이 영향을 받을 수 있다는 설명에 1점입니다. 혼잡 제어·연결 흐름 제어·QPACK 의존성·CPU·링크 같은 공유 제한이 남는다는 설명에 1점입니다. ‘특정 스트림의 누락 때문에 무관한 스트림의 순서 전달이 직접 막히는 현상을 줄인다’가 더 정확합니다. 복습: 4~5절.

## Q4 — 항상은 아니다, 2점

경로 검증·새 네트워크 도달성·서버의 이동 허용·핸드셰이크 완료 조건 등 두 가지를 설명하면 각 1점입니다. connection ID는 연결 식별을 돕지만 물리 연결이 없는 상황까지 해결하지는 않습니다. 복습: 6절.

## Q5 — 사용자군과 비용을 함께 검증, 4점

예시: 긴 RTT·유실·망 전환 환경에서 응답 지연·연결 유지가 개선되는지 확인한다. 같은 콘텐츠·캐시 상태에서 HTTP/2와 비교하고 p95/p99, 오류율, 연결 설정, CPU·비용을 기록한다. UDP 차단·미지원 사용자는 HTTP/2로 fallback하도록 설계하고 비율과 지연을 관찰한다. 제한된 사용자군부터 적용하며 오류·CPU·fallback 지연이 허용 범위를 넘으면 중단·복구한다. 앱·DB 병목이 주원인이면 그 개선을 별도로 다룬다.

채점: 조건 있는 이익 1점, 실패 조건·fallback 1점, 통제된 비교와 여러 지표 1점, 중단·복구와 앱 병목 구분 1점. 복습: 6~7절.
