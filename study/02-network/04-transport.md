# 2-4. TCP/IP와 UDP: 무엇을 누가 보장하나

[목차](../README.md) · [이전](03-dns.md) · [정답·해설](04-transport-answers.md)

예상 55분. 목표: IP·TCP·UDP·애플리케이션의 책임을 나누고, 신뢰성·순서·메시지 경계·지연을 기준으로 전송 방식을 비교합니다.

## 1. IP만으로 파일을 안전하게 전달할 수 있을까

IP는 주소와 라우팅을 통해 패킷을 보내지만 전달 성공·순서·중복 방지를 보증하지 않습니다. 파일을 원래대로 복구하려면 손실 탐지·재전송·순서 복원 등의 기능이 필요합니다. TCP는 이 위에서 **신뢰성 있고 순서가 있는 바이트 스트림**을 제공합니다.

신뢰성은 네트워크가 끊겨도 반드시 성공한다는 뜻이 아닙니다. 오류를 탐지·복구하며 전달을 시도하다 연결 실패로 끝날 수 있습니다. **TCP가 데이터를 받았다는 것과 애플리케이션이 처리·커밋했다는 것은 다릅니다.**

## 2. TCP의 주요 장치

| 장치 | 해결하려는 문제 | 비용·한계 |
| --- | --- | --- |
| 연결 설정 | 양 끝의 상태·순서 번호 등 동기화 | 첫 통신 왕복과 상태 자원 |
| 순서 번호·ACK·재전송 | 유실·중복·순서 어긋남 | 복구 대기, 순서 앞부분 손실의 영향 |
| 흐름 제어 | 수신자가 감당할 양 초과 방지 | 수신자가 느리면 송신도 제한 |
| 혼잡 제어 | 네트워크 경로의 혼잡 완화 | 처음부터 회선 용량을 모두 쓰지 못할 수 있음 |
| 체크섬 | 전송 오류 탐지 | 암호학적 인증·암호화를 대신하지 않음 |

수신 윈도는 수신자의 공간과 관계되고 혼잡 윈도는 네트워크 상황에 대한 송신자의 제어와 관계됩니다. 둘은 다른 제한입니다. 수신 버퍼를 늘린다고 망의 혼잡이 해결되지는 않습니다.

TCP는 `send()` 한 번의 경계를 보존하지 않습니다. `send(b"AB")`, `send(b"CD")`가 수신에서 `ABCD`로 한 번에 오거나 `A`, `BCD`처럼 나뉠 수 있습니다. 앱은 길이 접두사·구분자·HTTP 같은 규칙으로 메시지 경계를 해석해야 합니다. `recv(100)`은 반드시 100바이트를 반환하라는 뜻이 아닙니다.

## 3. UDP는 무엇이 적나

UDP는 포트·길이·체크섬과 데이터그램 경계를 제공하지만 TCP 같은 내장 연결 핸드셰이크, 재전송, 순서 복원, 혼잡 제어는 제공하지 않습니다. 데이터그램은 유실·중복·역순 도착할 수 있습니다. 수신 버퍼가 작으면 데이터가 잘릴 수도 있습니다.

‘UDP는 체크섬이 없고 무조건 빠르다’는 설명은 잘못입니다. 체크섬 규칙은 IP 버전·예외 규격에 따라 구분해야 하며, 빠르다는 결과도 앱 프로토콜·손실·메시지 크기에 달려 있습니다. UDP의 `connect()` API를 호출할 수 있지만 이것이 TCP와 같은 네트워크 연결 협상을 수행한다는 뜻은 아닙니다.

| 비교 | TCP | UDP만 사용 | QUIC처럼 UDP 위에 추가 프로토콜 |
| --- | --- | --- | --- |
| 데이터 모델 | 바이트 스트림 | 데이터그램 | 여러 스트림 등 프로토콜 정의 |
| 신뢰성·순서 | 내장, 연결 실패 가능 | 앱이 필요 시 구현 | QUIC 스트림은 신뢰성·스트림별 순서 제공 |
| 혼잡 제어 | 내장 메커니즘 | 별도로 고려해야 함 | 프로토콜이 수행 |
| 의미 경계 | 앱이 메시지 정의 | 데이터그램 단위 | 스트림 안의 메시지는 앱 규칙 |
| 비용 | 연결·상태·손실 복구 대기 | 앱 설계·손실 처리 책임 | 구현·CPU·운영 복잡성, 네트워크 지원 |

HTTP/3가 UDP를 쓴다는 사실은 웹 응답이 유실되어도 그대로 포기한다는 뜻이 아닙니다. QUIC가 신뢰성과 보안을 제공합니다.

## 4. 선택 사례와 감수하는 비용

**파일·업무 API:** 누락된 데이터가 허용되지 않으므로 신뢰성 있는 전송이 적합합니다. 통상 TCP 기반 HTTPS나 QUIC 기반 HTTP/3 같은 이미 검증된 프로토콜을 사용합니다. 단순 파일 전송을 위해 UDP 위에서 신뢰성·혼잡 제어를 직접 만드는 것은 큰 구현·검증 비용입니다.

**실시간 음성·위치 갱신:** 오래된 데이터의 재전송이 새 데이터보다 가치가 낮을 수 있습니다. 지터 버퍼·일부 손실 허용·복구 부호·응용 재전송 등 필요를 선택합니다. ‘실시간이면 반드시 UDP’가 아니라 사용 프로토콜과 환경에 맞춰 판단합니다. 인증·암호화·혼잡 제어도 필요합니다.

**이름 조회:** 전통적인 DNS에는 UDP가 흔하지만 TCP도 사용하고, 암호화된 DNS 전송에는 TLS·HTTPS·QUIC 등을 쓸 수 있습니다. ‘DNS=항상 UDP’는 맞지 않습니다.

## 5. 애플리케이션 완료는 별도의 계약

결제 요청을 보낸 뒤 연결이 끊겼습니다. 서버가 받기 전일 수도, 결제를 끝낸 뒤 응답만 사라졌을 수도 있습니다. TCP 재전송은 하나의 연결 안에서 바이트를 복구하는 기능이지 새 HTTP 요청의 중복 결제를 막는 기능이 아닙니다.

이럴 때 앱 수준의 멱등성 키·처리 상태 조회·트랜잭션 같은 설계가 필요합니다. 어떤 전송을 고르더라도 **‘최대 한 번 실제 결제’ 같은 업무 의미를 TCP ACK만으로 만들 수는 없습니다.** 자세한 멱등성은 2-6에서 다룹니다.

## 적용 과제

로그 파일 전송, 실시간 음성, 결제 API의 요구를 각각 적습니다. 누락 허용·오래된 데이터 가치·순서·중복 부작용·암호화·운영 역량을 비교하고 적합한 기존 프로토콜을 제안하세요. 포트나 프로토콜 이름보다 필요한 보장과 남은 앱 책임을 설명합니다.

## 퀴즈

Q1·Q2 각 1점, Q3·Q4 각 2점, Q5 4점. 권장 통과 8점이며 Q4를 복습 대상으로 중요하게 봅니다.

### Q1
TCP에서 두 번 `send()`하면 상대도 두 번 같은 크기로 `recv()`하나요?

### Q2
UDP 위의 프로토콜은 신뢰성을 제공할 수 없나요? 반례를 드세요.

### Q3
흐름 제어와 혼잡 제어가 각각 보호하는 대상을 설명하세요.

### Q4
결제 데이터가 TCP ACK를 받았습니다. DB 결제 기록이 반드시 저장됐다고 결론 내릴 수 있나요? 필요한 앱 수준 확인을 하나 적으세요.

### Q5
매 50ms마다 최신 위치를 보내는 기능과 결제 완료 기능을 같은 앱에서 제공합니다. 두 경로의 요구 차이와 전송 선택의 비용, 앱에서 추가로 처리할 것을 설명하세요.
