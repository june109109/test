# 2-5. 정답과 해설

[본문](05-connections.md)

## Q1 — 아니다, 1점

TCP keepalive는 유휴 전송 연결의 상대 생존 탐지에 관계됩니다. 전체 HTTP 요청 deadline은 별도로 설계해야 합니다. 복습: 2절.

## Q2 — 아니다, 1점

HTTP/2는 한 연결에서 여러 스트림을 다중화합니다. 최대 동시 스트림·흐름 제어·서버 자원 등이 요청 처리에 영향을 줍니다. 복습: 3절.

## Q3 — 72개, 2점

6×12=72에 1점. 실제 hard limit인지, overflow·대상별 풀·다른 인스턴스·관리 작업 연결 등이 있는지 확인하면 1점입니다. 연결 수만으로 처리량을 확정할 수 없습니다. 복습: 4절.

## Q4 — 점유 원인과 하류 용량, 2점

적절한 원인 두 가지에 각 1점입니다. 예: 응답 본문 미소비·연결 반환 누락, 외부 서비스 지연, 요청 증가·재시도 폭증, 일부 긴 스트리밍 응답의 점유, 실제 획득 대기인지 다른 지연인지. 하류가 이미 포화면 연결 증가가 지연·오류를 더 악화시킬 수 있습니다. 복습: 3~5절.

## Q5 — 공유 수명과 격리, 4점

프로세스 수명에 맞는 클라이언트를 만들고 종료 시 닫습니다. 라이브러리의 동시 사용·프로세스 공유 조건을 확인합니다. 사용자별 인증 헤더·쿠키를 가변 전역 설정으로 섞지 않습니다. 프로세스·인스턴스를 곱한 한도와 하류 용량을 맞추고 전체 요청 예산 안에 획득·연결·읽기 timeout을 배치합니다. 연결 생성 횟수·대기·응답 지연·오류를 같은 부하에서 비교합니다.

채점: 수명·동시 사용 1점, 인증 격리 1점, 한도·timeout 1점, 재사용·성능·오류 검증 1점. 복습: 3~5절.

적용 과제: 2×3×8=48개, 이상적인 포화 처리량은 48/0.1=480요청/초입니다. 실제 외부 한도 200요청/초를 초과하므로 요청률 제한·부하 조절이 필요하며 480을 달성 가능한 목표로 삼으면 안 됩니다.
