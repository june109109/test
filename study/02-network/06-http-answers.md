# 2-6. 정답과 해설

[본문](06-http.md)

## Q1 — 금지되지 않는다, 1점

HTTP 요청 의미의 독립성과 애플리케이션의 상태 저장은 다른 문제입니다. 세션 식별자 등으로 매 요청의 사용자·상태를 확인할 수 있습니다. 동일 연결이라는 이유만으로 사용자 신원을 이어받으면 안 됩니다. 복습: 2절.

## Q2 — 아니다, 1점

202는 처리를 접수했지만 완료되지 않았다는 의미입니다. 상태 조회·알림·실패 결과의 계약이 필요합니다. 복습: 4절.

## Q3 — 응답 변화만으로는 판단 불가, 2점

멱등성은 응답이 아니라 의도한 서버 효과를 비교한다는 설명에 1점. 두 요청 뒤에도 대상이 없는 상태라면 한 번 삭제한 효과와 같다는 설명에 1점. 복습: 3절.

## Q4 — 중복 방지와 결과 확인, 2점

멱등성 키와 처리 결과를 적절한 범위·기간에서 저장하고 같은 요청에 중복 결제가 생기지 않게 하는 계약에 1점. 결제 ID/키로 상태를 확인하거나 재시도 시 기존 결과를 돌려주는 계약에 1점. 저장과 실제 부작용 사이의 경쟁·실패도 설계해야 합니다. 단순히 클라이언트가 키를 보내는 것만으로 보장되지 않습니다. 복습: 3~4절.

## Q5 — 요청 신원과 상태의 분리, 4점

동일 연결을 동일 사용자로 가정하지 않고 요청별 자격 정보를 검증합니다. 공유 세션 저장소는 폐기·정책 변경이 쉬운 대신 조회·운영 비용이 듭니다. 자체 포함 토큰은 조회를 줄일 수 있지만 검증·키 회전·만료·폐기 관리가 필요합니다. 프로세스 로컬 세션은 재시작·분산 시 일관성 문제가 있습니다. 재시도는 메서드 의미뿐 아니라 실제 부작용과 앱 멱등성 계약을 확인합니다.

채점: 요청별 신원 1점, 상태 저장 대안 1점, 비용·분산 조건 1점, 재시도 부작용 1점. 복습: 2~4절.
