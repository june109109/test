# 13-3. 문제에서 출발하는 디자인 패턴

[목차](../README.md) · [정답·해설](03-patterns-answers.md)

예상 55분. 목표: 패턴 이름보다 반복되는 변화·경계를 먼저 발견하고, 단순 함수와 비교합니다.

## 1. 배송비가 여러 정책으로 바뀐다면

한두 고정 분기면 명시적 if가 쉬울 수 있습니다. 지역·등급·프로모션별 정책이 독립적으로 바뀌고 테스트/선택이 반복되면 전략을 전달하는 구조가 유용해집니다.

```python
def regular_shipping(amount_cents):
    return 0 if amount_cents >= 10000 else 599

def total_with_shipping(amount_cents, shipping_policy):
    return amount_cents + shipping_policy(amount_cents)
```

설명용 부분 코드이며 금액 검증은 호출 경계에서 별도 수행한다고 가정합니다. Python에서는 callable만으로 Strategy의 핵심 의도를 구현할 수 있습니다. 상태·여러 관련 메서드·수명 관리가 필요하면 객체/Protocol이 더 적절할 수 있습니다.

## 2. 자주 만나는 패턴과 더 단순한 대안

| 문제/패턴 | 이익 | 비용 | 작은 대안 |
| --- | --- | --- | --- |
| Strategy: 알고리즘 교체 | 정책별 테스트·선택 | 간접 호출·선택 위치 | if/함수 인자 |
| Adapter: 외부 인터페이스 변환 | SDK 세부를 업무에서 격리 | 오류/수명 매핑 유지 | 작은 wrapper 함수 |
| Factory: 생성 규칙 분리 | 환경별 생성·의존성 집중 | 생성 경로 추적 | 명시적 생성함수 |
| Repository: 저장 접근 경계 | 업무와 쿼리 경계 | 과도한 공통 추상화 위험 | 필요한 쿼리 함수 |
| Observer/event: 변경 알림 분리 | 여러 반응의 결합 감소 | 순서·오류·추적 | 명시적 호출 목록 |

상속계층을 만들었다고 패턴의 이익이 생기지 않습니다. callback 하나로 가능한 문제에 class10개를 만들면 비용이 커질 수 있습니다. 반대로 상태 있는 외부 client를 함수 하나로 숨기다 소유권이 모호해질 수도 있습니다.

## 3. Adapter는 예외를 지우는 곳이 아니다

S3의 get_object/Body를 업무의 ‘파일 읽기’ 계약으로 바꾸더라도 not found·권한 없음·timeout을 모두None으로 만들면 필요한 정책을 잃습니다. 오류 의미·stream close·retry·부분 읽기·관측이 adapter계약에 포함됩니다.

비슷해 보이는 두 저장소가 transaction·검색·일관성 보장이 다르면 무리하게 완전히 같은 인터페이스로 감추지 않습니다. 실제 공통 요구만 추상화합니다.

## 4. 학습용 논증

**패턴 도입 입장:** 변형 정책이 세 곳에서 반복되어 수정 누락이 발생하므로 하나의 선택 경계와 전략으로 모은다. **반박:** 정책이 둘뿐인데 추상화와 파일이 늘어 읽기 어렵다. **재반박:** class 계층 대신 함수 전달로 시작하고 공통 테스트·선택 위치만 통합할 수 있다.

**단순 분기 유지 입장:** 변경 압력이 확인될 때까지 명시적 if를 유지한다. **반박:** 새 정책마다 핵심 함수를 수정해야 한다. **재반박:** 실제 변경 빈도·독립 배포/테스트 요구를 기록하고 분기가 서로 다른 축으로 반복되는 시점에 분리한다.

이 논증은 실제 저자의 발언이 아니라 선택 비용을 비교하는 연습입니다.

## 5. 적용 과제

현재 업무 코드에서 변화가 잦은 정책 하나를 골라 if 안·함수 전략 안·객체 전략 안을 비교하세요. 상태·생성·오류·테스트와 ‘아직 패턴이 필요하지 않은 조건’도 적습니다.
