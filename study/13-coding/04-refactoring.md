# 13-4. 테스트로 감싸고 리팩토링하기

[목차](../README.md) · [정답·해설](04-refactoring-answers.md)

예상 65분. 목표: 외부 동작을 보존하는 구조 변경과 의도한 버그 수정을 분리하고, 실행 증거로 확인합니다.

## 1. 무엇을 보존할 것인가

리팩토링은 외부에서 관찰할 동작을 유지하며 내부 구조를 개선하는 작업입니다. 가격·오류 타입·응답 키·반올림·부수효과·API호환성 등 어떤 계약이 중요한지 먼저 적습니다. 버그도 현재 동작일 수 있으므로 ‘현재를 기록하는 테스트’와 ‘원하는 요구의 테스트’를 구분합니다.

특성화 테스트는 잘 모르는 코드의 현재 동작을 드러냅니다. 발견한 버그를 영원히 보존하라는 뜻은 아닙니다. 의도한 수정은 별도 기대값·변경 이유·호환성 판단으로 명시합니다.

## 2. 작은 변경 순서

```text
현재 동작과 위험 경계 파악
  → 중요한 사례의 테스트 추가/실행
  → 작은 구조 변경
  → 관련 테스트 실행
  → diff와 외부 계약 검토
  → 다음 작은 변경
```

구조 변경과 할인 정책 변경을 한 번에 하면 실패 원인을 분리하기 어렵습니다. 포맷 전면 변경·불필요한 이름 교체를 섞지 않습니다. 테스트가 통과해도 운영 성능·동시성·외부 연동까지 자동 보존되지는 않습니다.

## 3. 실제 변경과 검증

[기존 코드](../labs/testing_demo/pricing.py), [추출본](../labs/pricing_refactored.py), [검증 실행기](../labs/check_refactor.py), [원본 결과](../results/refactor-2026-10-02.json).

기존quote의 입력 검증·공개 함수·응답을 유지하고, 합계·할인·배송비를 세 helper로 분리했습니다. 정수 할인 후 내림, 할인 후10000cent 무료배송 규칙을 그대로 유지했습니다. 업무 규칙을 바꾸거나 예외를 숨기지 않았습니다.

```bash
/workspace/study-python/bin/python study/labs/check_refactor.py   --output /tmp/refactor-new.json
```

10장의 의존성이 설치된 다른 venv에서는 python경로를 바꾸세요. 실행기는 임시 디렉터리에 기존 앱·테스트를 복사하고 가격 모듈만 추출본으로 교체하여 **기존 21개 테스트를 그대로 실행**합니다. 2026-10-02 결과는21passed,0failed였습니다. 이후 임시 디렉터리를 제거하고 원본 바이트가 바뀌지 않았는지 확인했습니다.

이것은 검증된21개 사례의 보존 증거입니다. 모든 가능한 입력의 동치 증명이나 성능 개선 증거는 아닙니다. helper를 직접 호출하는 새API를 공개하려면 전제·검증·호환성을 별도로 정의해야 합니다.

## 4. 테스트가 실제로 막는가

10-6에서>=를>로 바꾼 임시 변이는 기존 테스트 3개가 실패했습니다. 따라서 무료배송 경계의 회귀를 잡는 assertion이 있다는 증거도 갖고 있습니다. 한 변이를 잡았다고 테스트가 모든 잘못된 변경을 찾는 것은 아닙니다.

테스트가 내부 함수 호출 순서에 과도하게 묶였다면 동작 보존 추출에도 깨질 수 있습니다. 외부 결과와 중요한 부작용을 중심으로 옮기되, 실패한 테스트를 이유 없이 삭제하거나 expectation을 변경해 녹색으로 만들지 않습니다.

## 5. 적용 과제

추출본에 새회원 무료배송 정책을 추가하려면 먼저 요구사항 테스트를 작성하세요. 그 작업이 이번 순수 리팩토링과 다른 이유, 기존 정책과의 우선순위, 회귀 범위를 설명합니다. 추가 정책은 이 자료에서 구현하지 않았습니다.
