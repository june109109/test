# 4-5. Uvicorn 워커와 연결 분산

[목차](../README.md) · [정답·해설](05-workers-answers.md)

예상 50분. 목표: 프로세스 수와 요청 분산을 구분하고, 워커별로 복제되는 자원을 계산합니다.

## 1. 워커를 늘리면 무엇이 늘어날까

`uvicorn app:app --workers 2`는 두 애플리케이션 프로세스를 실행합니다. 일반적인 워커마다 이벤트루프, Python 힙, 전역 변수, lifespan에서 만든 연결 풀을 갖습니다. GIL이 있는 CPython에서도 서로 다른 프로세스는 별도 GIL로 실행하므로 CPU 병렬 실행의 기회를 얻습니다. 실제 CPU quota가 작으면 프로세스 수만큼 계산 용량이 늘지는 않습니다.

```text
리스닝 소켓
  ├─ 워커 A: 이벤트루프, 로컬 캐시, DB 풀, SDK 클라이언트
  └─ 워커 B: 이벤트루프, 로컬 캐시, DB 풀, SDK 클라이언트
```

공유 리스닝 소켓과 이미 수락한 연결은 다릅니다. 수락된 HTTP/1.1 연결의 후속 요청은 보통 그 연결을 맡은 워커에서 처리됩니다. 매 요청을 라운드로빈으로 다른 PID에 보내는 기능이라고 생각하면 실험을 오해합니다. 앞단 프록시의 연결 재사용도 분포에 영향을 줍니다.

## 2. 워커·스레드·컨테이너 비교

| 선택 | 이득 | 비용·선택 조건 |
| --- | --- | --- |
| 같은 워커에서 비동기 I/O | 적은 스레드로 많은 대기 처리 | 블로킹 코드 하나가 루프 진행을 방해 |
| 스레드 오프로딩 | 동기 SDK를 병행 | 스레드·토큰·하류 자원 한도, GIL CPU 제약 |
| 여러 Uvicorn 워커 | 프로세스 격리, CPU 병렬 기회 | 메모리·풀·캐시 복제, 장애 관리 |
| 여러 컨테이너 | 배포·확장 단위 분리 | 네트워크·오케스트레이션·전체 연결 예산 |

`워커 수 = CPU 수 × 2 + 1` 같은 경험칙을 모든 ASGI 서비스에 적용하지 않습니다. CPU quota, 메모리, I/O 대기, 각 풀의 대기 시간, p95/p99 지연을 함께 측정합니다. 루프를 막는 코드를 둔 채 워커만 늘리면 잠시 완화되더라도 요청 증가 시 같은 문제가 반복될 수 있습니다.

## 3. 직접 실행한 실험

[앱 코드](../labs/pid_app.py), [실행기](../labs/uvicorn_workers.py), [원본 결과](../results/uvicorn-workers-2026-10-01.json).

```bash
python3 study/labs/uvicorn_workers.py --output /tmp/uvicorn-workers-new.json
```

POSIX/Linux의 소켓 FD 전달과 프로세스 그룹을 사용하는 실습입니다. Python과 `requirements-fastapi.txt`의 패키지가 필요합니다. 출력 경로가 이미 있으면 거부합니다. 실행기가 loopback 임시 포트를 확보하고 자신의 서버를 시작·종료합니다.

2026-10-01, CPython 3.12.14 / Uvicorn 0.52.1 / FastAPI 0.141.1에서 실제 TCP HTTP/1.1로 확인했습니다.

| 관찰 | 실제 결과 |
| --- | --- |
| 워커 설정 | 2 |
| 하나의 지속 연결로 순차 요청 12개 | PID 1종 |
| 새 연결로 요청 24개, 클라이언트 병행 8 | PID 2종, 각 12개 |
| 워커별 lifespan 생성 토큰 | 서로 다른 값 2개 |
| lifespan 시작 / 종료 기록 | 각각 2개 |
| 종료 코드 | 0 |

이번의 12:12는 **관찰값**입니다. 균등 분산 보장이나 서버 처리량 측정이 아닙니다. 다음 실행에서는 분포가 다를 수 있습니다. 반환되는 `local_request_count`는 프로세스별 값이므로 서비스 전체 요청 수로 합의된 값이 아닙니다. readiness 요청도 카운터를 올립니다.

앱의 UUID는 자원 생성이 워커별이라는 것을 관찰하기 위한 표식이며 인증 토큰이 아닙니다. PID도 운영 외부 API에 반드시 노출해야 하는 정보는 아닙니다.

## 4. 설계 계산

컨테이너 3개, 컨테이너당 워커 4개, 워커당 DB 풀 10이면 기본 풀만 최대 120연결입니다. overflow 5가 각 풀에 허용되면 최대 180연결이 될 수 있습니다. 여기에 배치·관리·배포 중 구버전과 신버전의 공존을 더합니다.

한 워커의 로컬 캐시에 사용자 설정을 저장해도 다른 워커의 캐시가 자동 갱신되지는 않습니다. 전역 정확성이 필요하면 DB/Redis 같은 공유 저장소나 명시적 무효화·버전 전략이 필요합니다. 캐시를 공유 저장소로 옮기면 네트워크 지연과 장애 의존성이 생깁니다.

## 5. 적용 과제

요청 1개가 평균 CPU 20ms와 외부 I/O 대기 180ms를 사용한다고 가정합니다. CPU quota 2, 메모리 1GiB에서 워커를 1→2→4로 변경할 계획을 작성하세요. 이것은 독자 과제이며 이 자원 조건의 부하 테스트를 실행한 결과는 아닙니다. RPS뿐 아니라 CPU 사용량·루프 lag·워커별 RSS·하류 대기를 기록해야 합니다.

## 출처와 확인 범위

- [Uvicorn deployment](https://www.uvicorn.org/deployment/): 워커 실행 옵션의 참고 문서. 이 편의 동작 증거는 저장한 실험 결과입니다.
- 설치된 Uvicorn 0.52.1의 `uvicorn._subprocess.get_subprocess`와 multiprocess supervisor를 직접 확인했습니다. 이 버전은 spawn 컨텍스트를 사용합니다. OS의 multiprocessing 기본값과 동일하다고 추정하지 않습니다.
- [FastAPI lifespan](https://fastapi.tiangolo.com/advanced/events/): 자원 시작·종료의 생명주기.

확인일: 2026-10-01. 재시작·장애 복구·프록시 부하 분산·운영 처리량은 이 실험의 검증 범위가 아닙니다.
