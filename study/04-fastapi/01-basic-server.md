# 4-1. 표준 라이브러리로 작은 서버 만들기

[목차](../README.md) · [정답·해설](01-basic-server-answers.md)

예상 60분. 선수 지식: 2장의 HTTP, 3장의 스레드·대기. 목표: 프레임워크 없이 요청 수락·처리·응답·종료를 이해하고, 단일 처리와 제한된 스레드풀의 차이를 실제로 관찰합니다.

## 1. 서버가 해야 하는 최소 일

소켓을 열어 주소에 bind하고 listen 상태에서 연결을 accept합니다. HTTP 구현은 요청을 해석해 handler로 넘기고, handler는 업무를 처리해 응답합니다. 응답의 길이·연결 종료를 정확히 표시해야 클라이언트가 끝을 알 수 있습니다.

이 편은 HTTP 파서를 직접 다시 만들지 않고 Python의 `HTTPServer`·`BaseHTTPRequestHandler`로 전송·요청 해석을 맡깁니다. FastAPI 없이 실행 구조를 관찰하기 위한 작은 서버이며 공개 운영 서버가 아닙니다.

```text
단일 처리: accept → handler → 응답/종료 → 다음 accept
풀 처리:   accept → executor에 handler 제출 → 다음 accept
                      ↳ 워커들이 각 요청 처리·응답/종료
```

스레드풀이 붙어도 모든 요청이 즉시 실행되는 것은 아닙니다. 워커가 모두 차면 작업은 큐에 기다립니다. 이 실습의 executor는 실행 워커를 4개로 제한하지만 제출 큐는 무제한입니다. 유한한 4개 요청만 보내며, 실제 서버의 admission control을 완성한 코드로 읽지 않습니다.

## 2. 코드에서 볼 지점

[실습 코드](../labs/server_models.py)의 두 클래스는 같은 handler를 사용합니다.

- `SingleServer`: HTTPServer의 단일 처리 경로를 사용합니다.
- `PooledServer`: `process_request`에서 같은 처리 작업을 4개 워커의 executor에 제출합니다.
- handler는 80ms 동안 동기 대기한 뒤 `ok`, PID, 스레드 식별자를 응답합니다.
- Lock으로 현재 실행 중인 handler 수와 최고 동시 실행 수를 기록합니다.
- 성공·오류와 관계없이 연결을 정리하고 종료 시 executor도 닫습니다.

`Connection: close`를 명시한 이유는 요청 처리 모델에 초점을 맞추기 위해서입니다. 단일 서버가 유휴 keep-alive 연결을 기다리는 문제까지 섞지 않도록 했습니다. 이는 연결 재사용이 나쁘다는 뜻이 아니라 이번 실험의 통제 조건입니다.

## 3. 선택의 이득과 비용

| 모델 | 이익 | 비용·제약 |
| --- | --- | --- |
| 단일 처리 | 흐름·상태 추론 단순 | 느린 요청이 뒤 요청을 지연 |
| 요청마다 새 스레드 | 쉽게 대기를 겹침 | 요청 폭주 시 스레드·메모리 증가 |
| 제한된 스레드풀 | 실행 스레드 수·재사용 관리 | 제출 큐·취소·공유 상태·종료 정책 필요 |
| 비동기 서버 | 비동기 I/O의 많은 대기 관리 | 동기 호출 혼입·task 수명·별도 실행 자원 관리 |

이 실습은 두 번째 모델 대신 **제한된 실행 워커**를 사용합니다. 그래도 큐·연결·읽기 시간 제한은 별도로 설계해야 합니다. 클라이언트가 데이터를 매우 천천히 보내도 워커를 점유할 수 있고, 큰 요청 본문·불완전한 요청도 운영상의 문제입니다.

## 4. 실행과 결과

준비: Python 3.10 이상, 외부 패키지 없음. 로컬 소켓 사용 허용.

```bash
cd /workspace/test
python3 study/labs/server_models.py --output /tmp/server-models-my-run.json
```

새 출력 경로를 사용하세요. 스크립트는 임시 loopback 서버 두 개를 **순서대로** 띄워 각각 동시 요청 네 개를 보내고 종료합니다. 결과 파일이 이미 있으면 덮어쓰지 않습니다.

2026-10-01 CPython 3.12.14의 [실제 결과](../results/server-models-2026-10-01.json):

| 모델 | 네 요청 완료 시간 | 최고 동시 handler 수 | 응답의 서로 다른 PID / 스레드 수 |
| --- | ---: | ---: | --- |
| 단일 처리 | 0.326081초 | 1 | 1 / 1 |
| 4워커 스레드풀 | 0.087121초 | 4 | 1 / 4 |

총 8개 응답의 성공과 동시 처리 수 조건을 검증했습니다. 지연만 근사하면 `4×80ms=320ms`와 약 `80ms`이므로 대기가 겹친 결과와 부합합니다. 단 한 번의 소규모 관찰이므로 정확한 가속 배수나 운영 처리량을 주장하지 않습니다. 클라이언트 시작·연결·서버 처리 비용도 측정에 들어 있습니다.

## 5. 블로킹과 GIL을 혼동하지 않기

단일 서버의 `time.sleep`은 CPU를 계속 쓰지는 않지만 handler가 끝나기 전 다음 요청을 처리하지 못합니다. 스레드풀은 다른 스레드가 그동안 별도의 요청을 처리합니다. 계산이 네 배 빨라진 것이 아닙니다.

handler의 sleep을 큰 순수 Python 반복 계산으로 바꾸면 GIL 있는 환경에서 같은 결과를 기대할 수 없습니다. 어떤 일을 병행했는지 설명해야 합니다. PID와 스레드 ID는 실행 위치의 증거이지만 부하가 균등하게 배분됐다는 일반 증거는 아닙니다.

## 적용 과제

이 코드에서 실행 한도와 대기열 한도를 각각 찾아 설명하세요. 운영 서버로 만들려면 요청 크기·읽기 timeout·큐 길이·포화 시 응답·정상 종료 중 무엇을 더 설계해야 하는지 적습니다. 이 과제는 공개 인터넷에 서버를 노출하라는 뜻이 아닙니다.
