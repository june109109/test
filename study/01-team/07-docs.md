# 1-7. 변화하는 스펙을 어떻게 문서화할까

[목차](../README.md) · [이전](06-debt.md) · [정답·해설](07-docs-answers.md)

예상 45분. 목표: 독자의 목적에 맞는 문서를 고르고, 원본과 파생 문서의 역할을 정하며, 변경과 문서 갱신을 함께 설계합니다.

## 1. 예쁜데 틀린 문서, 정확한데 찾을 수 없는 문서

팀에는 보기 좋은 API 소개 슬라이드, 자동 생성 API 명세, 오래된 위키 예제가 있습니다. 세 곳의 필수 필드가 다릅니다. 어떤 문서를 더 예쁘게 만들어야 할까요?

우선 어느 정보를 어디에서 책임지는지 정해야 합니다. 서체와 색도 읽기에 영향을 주지만 핵심은 **정확성, 찾기 쉬움, 독자의 작업 수행 가능성, 변경 비용**입니다. 장식이 정교해도 오래된 예제가 실행되지 않으면 신뢰가 낮아집니다. 반대로 정확한 정보를 링크 없이 흩어 놓으면 실무에서 사용하기 어렵습니다.

## 2. 문서의 목적 네 가지

Diátaxis [S1]는 사용자의 필요에 따라 tutorial, how-to, reference, explanation을 구분합니다. 다음은 이 구분을 팀 문서에 적용한 예입니다.

| 종류 | 독자의 질문 | 들어갈 내용 | 피할 혼합 |
| --- | --- | --- | --- |
| 튜토리얼 | 처음 배우는데 성공 경험을 얻고 싶다 | 준비된 예제, 단계, 기대 결과 | 모든 예외를 한꺼번에 설명 |
| 작업 안내 | 특정 일을 끝내려면 어떻게 하나 | 전제·절차·검증·실패 시 대응 | 긴 배경 설명으로 단계 묻기 |
| 참조 | 정확한 필드·옵션·제약은 무엇인가 | 구조화된 계약·기본값·오류 | 맥락 없는 산문 속에 사양 숨기기 |
| 설명 | 왜 이렇게 동작하거나 결정했나 | 모델·이유·대안·장단점 | 현재 사양의 유일한 저장소로 사용 |

문서 네 권을 반드시 만들라는 뜻은 아닙니다. 작은 프로젝트는 한 페이지에서 명확한 구역과 링크로 구분할 수 있습니다. ADR은 결정 이유를 설명하고 API 명세는 현재 계약을 알려 줍니다. 어느 하나가 다른 하나를 완전히 대신하지 않습니다.

## 3. 실제 입장과 토론

### A. 문서는 사용자의 필요에 맞춰 나누자

**확인한 입장 — Daniele Procida의 Diátaxis [S1]:** 네 가지 필요와 그에 대응하는 문서 형태를 구분하고 그 관계에 따라 내용을 조직한다.

**반박 — 학습용:** 작은 팀에서 형식만 늘고 같은 설명을 복제할 수 있다.

**재반박 — 학습용:** 파일 수보다 정보 역할을 나눈다. 튜토리얼은 필요한 명세를 연결하고, 참조를 복사해 두지 않는다. 독자가 실제로 묻는 문제부터 작은 문서로 만든다.

### B. 긴 문서보다 작은 결정 기록이 유지되기 쉽다

**확인한 입장 — Michael Nygard [S2]:** 의사결정의 동기를 작은 기록으로 남기고, 장단점과 대체 관계를 보존한다.

**반박 — 학습용:** ADR이 많으면 현재 유효한 결정을 찾기 어렵다.

**재반박 — 학습용:** 현재 시스템 개요에서 유효한 ADR을 연결하고 이전 기록은 대체 상태로 둔다. 이전 기록을 현재 사용법으로 보여 주지 않는다. 역사와 현재 상태의 검색 경로를 분리한다.

### C. 문서 갱신을 PR 필수 조건으로 둘까

**확인한 입장 — Google 리뷰 항목 [S3]:** 빌드·테스트·사용·배포 방법이 바뀌면 관련 문서를 함께 갱신하고, 코드 삭제·폐기 시 문서 삭제도 검토한다.

**반박 — 학습용:** 모든 내부 변경에 문서를 요구하면 불필요한 작업이 된다.

**재반박 — 학습용:** 독자에게 보이는 계약·절차·판단 근거가 바뀌는지를 기준으로 삼는다. 로컬 변수 이름 변경에는 문서 변경이 없을 수 있다. 문서 영향 없음도 이유를 짧게 남길 수 있다.

## 4. 빠르게 변하는 스펙의 원본을 설계하기

‘단일 진실 공급원’은 모든 지식을 한 파일에 쓰라는 뜻이 아닙니다. **정보 종류별로 책임지는 원본을 정하고 중복을 줄인다**는 뜻으로 사용합니다.

| 정보 | 원본 후보 | 파생 자료와 검증 | 한계 |
| --- | --- | --- | --- |
| 필드·타입·경로 | 코드 스키마 또는 명세 우선 계약 | OpenAPI 생성·차이 검토·계약 테스트 | 자동 생성만으로 의미·호환성을 보증하지 못함 |
| 비즈니스 의미 | 도메인 규칙 문서와 예제 | 테스트·API 설명에서 링크 | 코드와 분리되면 의도와 실제가 어긋날 수 있음 |
| 운영 절차 | 버전 관리된 runbook | 실제 절차 연습·검토 날짜 | 명령의 존재와 안전한 실행 조건은 다름 |
| 결정 이유 | ADR | 현재 개요에서 연결 | 옛 결정이 현재 유효한지 상태 필요 |

자동 생성 명세와 코드가 일치해도 둘 다 잘못된 요구를 구현할 수 있습니다. 예를 들어 `amount: number`만으로 통화, 반올림, 음수 허용 여부를 알 수 없습니다. 이런 의미는 별도 설명·예시·검증이 필요합니다.

문서마다 소유자·대상 버전·최종 확인 정보를 둘 수 있습니다. ‘30일마다 무조건 검토’ 같은 날짜 정책만으로 정확성을 보장하지 말고, 관련 코드 변경이 발생하면 갱신되는 연결을 만듭니다.

## 5. 변경을 따라가는 최소 절차

1. PR에서 바뀌는 독자 행동이나 계약을 적습니다.
2. 해당 정보의 원본을 수정하고 파생물을 갱신합니다.
3. 대표 예제·링크·명령을 확인합니다. 파괴적 운영 명령은 안전한 연습 환경과 승인 절차를 구분합니다.
4. 명세의 차이가 호환성을 깨는지 검토합니다.
5. 사용자가 보는 현재 문서와 구버전 문서의 경계를 표시합니다.

예쁜 문서는 판단을 돕는 표·명확한 제목·적절한 여백·복사 가능한 예제에서 출발합니다. 위험한 명령을 복사하기 쉬운 모양만으로 강조하지 말고 전제·대상·복구 조건도 함께 표시합니다.

## 적용 과제

도입 사례의 세 문서에 대해 ‘유지·자동 생성·링크로 대체·폐기’ 중 하나를 고르세요. 신규 개발자가 첫 API 호출을 성공하는 경로와 운영자가 필드 의미를 확인하는 경로를 각각 설계합니다. 변경이 들어왔을 때 수정할 곳이 불필요하게 늘지 않는지 확인하세요.

## 퀴즈

Q1·Q2 각 1점, Q3·Q4 각 2점, Q5 4점. 권장 통과 8점.

### Q1
‘옵션 timeout의 단위와 기본값은?’이라는 질문에는 네 문서 형태 중 무엇이 우선인가요?

### Q2
자동 생성된 OpenAPI 문서가 있으면 비즈니스 의미 설명과 계약 테스트가 불필요한가요?

### Q3
튜토리얼에 API 필드 표를 복사해 뒀더니 명세와 달라졌습니다. 재발을 줄이는 방법 두 가지를 쓰세요.

### Q4
‘코드가 바뀌면 무조건 위키도 수정’보다 유용한 문서 변경 판단 기준 두 가지를 제시하세요.

### Q5
스펙이 매주 바뀌는 API의 최소 문서 체계를 설계하세요. 첫 사용자·기존 사용자·운영자 중 최소 두 독자, 정보 원본, 변경 검증, 오래된 문서 처리 방법을 포함하세요.
