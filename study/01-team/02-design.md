# 1-2. 설계 의견이 다를 때 결정하기

[목차](../README.md) · [이전: 스타일 합의](01-style.md) · [정답·해설](02-design-answers.md)

예상 50분. 선수 지식: 1-1. 목표는 ① 취향과 설계 제약을 구분하고 ② 대안의 비용을 비교하고 ③ 결정을 바꿀 증거가 있는 ADR을 작성하는 것입니다. ADR은 Architecture Decision Record, 중요한 설계 결정을 남기는 짧은 기록입니다.

## 1. “Redis가 더 좋다”를 검토할 수 있는 주장으로 바꾸기

가상의 콘텐츠 목록 API에 캐시를 넣으려 합니다. A는 서버 프로세스 안에 저장하자고 하고 B는 Redis를 쓰자고 합니다. 현재 서버 프로세스는 하나지만 다음 달에 네 개로 늘어날 수 있습니다. 데이터는 최대 60초까지 오래되어도 되며, Redis 운영 경험은 없습니다.

“빠르다”, “확장 가능하다”만으로는 결정을 내릴 수 없습니다. **누구에게 어떤 조건에서 얼마나 좋은가**를 정해야 합니다. 아직 모르는 수치에는 ‘가정’이라고 표시합니다. 이 편의 캐시는 설계 판단용 예시이며 구현은 7장에서 다룹니다.

| 질문 | 확인할 내용 | 판단에 주는 영향 |
| --- | --- | --- |
| 얼마나 최신이어야 하는가 | 목록은 60초 허용, 권한 정보도 같은가 | 권한 데이터에는 같은 정책을 적용하면 안 될 수 있음 |
| 어떤 요청이 반복되는가 | 공통 키인지 사용자별 키인지 | 적중률, 메모리, 개인정보 경계 |
| 프로세스가 늘면 무엇이 달라지는가 | 메모리 복제, 무효화, 프로세스별 값 차이 | 로컬 캐시의 운영 비용 |
| 캐시 장애 시 어떻게 할 것인가 | 원본 조회 가능 여부와 원본 처리 여유 | Redis 장애가 DB 과부하로 번지는지 |
| 무엇을 실제로 아는가 | 측정값·요구사항·일정과 추측 구분 | ‘다음 달 확장’의 확실성에 따라 선택이 달라짐 |

**제약**은 반드시 만족해야 할 조건, **선호**는 가능하면 얻고 싶은 특성, **가정**은 아직 검증되지 않은 설명입니다. 세 가지를 같은 수준의 점수로 더하면 안 됩니다. 개인정보 격리를 위반하는 대안은 저렴하다는 이유로 선택할 수 없습니다.

## 2. 대안의 이득과 비용

| 대안 | 얻는 이득 | 감수하는 비용 | 선택하기 좋은 조건 | 다시 판단할 신호 |
| --- | --- | --- | --- | --- |
| 캐시 없이 원본 조회 | 구조·갱신 규칙이 단순 | 원본 부하와 지연 | 현재 목표 지연·부하를 충족 | 원본이 실제 병목임을 측정 |
| 로컬 캐시 | 네트워크 왕복 없음, 별도 서비스 불필요 | 프로세스별 중복, 값 차이, 재시작 시 초기화 | 값 차이를 허용하고 메모리가 충분 | 다중 프로세스에서 메모리·일관성 문제 |
| 공유 Redis | 여러 프로세스가 공통 데이터를 조회·갱신 | 서비스·네트워크·장애·직렬화·운영 비용 | 공유 값·무효화가 중요하고 운영 가능 | Redis 지연·비용 또는 장애 영향이 기대 초과 |

공유 저장소를 쓴다고 애플리케이션 캐시 갱신 경쟁이 자동으로 해결되지는 않습니다. 로컬 캐시가 빠르다는 말도 최종 응답 시간이 캐시 조회에 지배될 때 의미가 있습니다. **아예 추가하지 않는 대안**을 포함해야 개선의 순이익을 판단할 수 있습니다.

가중치 점수표는 논의의 도구입니다. ‘운영성 4점’ 같은 숫자는 사실처럼 보이지만 가중치·점수 자체가 의견일 수 있습니다. 필수 조건을 먼저 걸러내고, 남은 대안에 대해 근거와 민감도를 설명하세요.

## 3. 공개 문헌의 입장과 토론

아래 ‘입장’은 원문 요약이고 반박·재반박은 학습용 구성입니다.

### A. 큰 설계 문서보다 짧은 결정 기록

**입장 — Michael Nygard [S1]:** 중요한 결정마다 맥락·결정·상태·결과를 짧게 기록한다. 결과에는 단점도 포함하고, 결정이 바뀌면 기존 기록을 삭제하지 않고 대체된 상태와 새 기록을 연결한다.

**반박:** 기록을 작게 나누면 전체 시스템을 이해하기 어렵고 문서가 흩어진다.

**재반박:** 시스템 지도와 개별 결정 기록은 역할이 다르다. 개요 그림에서 ADR을 연결하면 된다. 모든 사소한 변수 이름까지 ADR로 만들 필요는 없다.

**적용:** 구성요소 경계, 외부 의존성, 데이터 계약, 품질 속성에 영향을 주는 결정에 사용한다. 상세 사용법은 별도 문서로 둔다.

### B. 충분히 좋은 결정을 진행할 것인가, 완벽한 합의를 기다릴 것인가

**입장 — Google 리뷰 기준 [S2]:** 기술적 근거를 우선하고, 여러 접근이 동등하게 타당하면 작성자 선택을 수용한다. 합의가 막히면 대화·기록·책임자 판단을 이용해 변경을 방치하지 않는다.

**반박:** 빨리 끝내려다 데이터 모델 같은 비싼 결정을 잘못할 수 있다.

**재반박:** 검토 깊이는 되돌리기 비용에 비례해야 한다. 설정값 변경과 공개 데이터 형식 변경을 같은 속도로 결정하지 않는다. 일정까지 정하고, 필수 위험을 확인한 뒤 남은 불확실성을 기록한다.

**적용:** 합의는 모든 사람의 선호가 같아지는 상태보다 ‘근거와 책임, 결과를 받아들일 절차가 명확한 상태’를 목표로 삼는다. 안전·보안상 반대 근거는 단순한 소수 의견으로 무시하지 않는다.

### C. 미래를 대비한 범용 설계가 유리할까

**입장 — Google 리뷰 항목 [S3]:** 실제로 필요하지 않은 일반화와 가상의 미래 기능을 경계한다.

**반박:** 데이터가 쌓인 다음에는 교체 비용이 너무 커질 수 있다.

**재반박:** 확인된 변화 압력에만 작은 경계를 만든다. 예컨대 캐시 접근을 한 모듈로 모을 수는 있지만, 아직 쓰지 않는 다섯 종류의 캐시 구현과 거대한 플러그인 체계가 필요한 것은 아니다.

**적용:** “미래 대비”를 주장하면 예상 변화, 발생 가능성, 나중에 바꾸는 비용, 지금 추가하는 비용을 적는다. 모듈로 감쌌다고 저장된 데이터의 이관 비용까지 사라지는 것은 아니다.

## 4. 짧은 실험으로 무엇을 확인할까

spike는 구현 전체를 만들기 전에 중요한 불확실성 하나를 확인하는 제한된 조사·시제품 작업입니다. 출시용 품질을 갖춘 구현과 구분합니다.

캐시 사례에서는 먼저 반복 키 비율과 원본 조회 지연을 조사할 수 있습니다. 다음으로 대표적인 키 분포·값 크기·동시성에서 캐시 대안을 비교합니다. 빈 데이터로 한 번 호출해서 “10배 빠름”을 보이는 실험은 실제 적중률·갱신·장애 비용을 알려주지 않습니다.

결과를 보기 전에 성공 기준을 적습니다. 예를 들어 ‘대표 부하에서 p95가 목표 이내이고, 오래된 데이터 허용 범위를 넘지 않으며, 원본 요청이 줄어드는지’입니다. p95는 요청 지연의 95백분위수로, 약 95%가 이 값 이하라는 뜻입니다. 숫자는 실제 요구에서 정하고 유리한 결과가 나온 뒤 바꾸지 않습니다.

## 5. ADR 작성 예시

아래는 **실측 결과가 없는 학습용 가상 기록**입니다. 사실과 가정을 구분하는 형식을 보세요.

```text
ADR-001: 콘텐츠 목록 캐시를 아직 추가하지 않는다
상태: 제안
맥락: 현재 목표 지연을 넘는다는 측정이 없다. 프로세스 확대는 예정이나 미확정이다.
필수 조건: 사용자별 권한 격리 유지. 목록의 신선도 요구는 최대 60초이다.
대안: 원본 조회 유지 / 로컬 캐시 / 공유 Redis.
결정: 우선 조회 지연과 반복 키 비율을 측정한다. 이번 변경에는 캐시를 추가하지 않는다.
긍정적 결과: 운영 구성요소와 무효화 규칙을 당장 늘리지 않는다.
부정적 결과: 부하 증가 시 원본 조회 비용을 계속 부담한다.
확인: 담당자가 대표 부하·키 분포에서 측정하고 결과 링크를 추가한다.
재검토: 원본 조회가 목표 지연을 깨는 병목이거나 공유 무효화 요구가 확정되면 재논의한다.
결정 책임: 서비스 담당자. 검토자: 운영 담당자와 데이터 소유자.
```

원형 ADR에는 반드시 정해진 모든 추가 필드가 있는 것은 아닙니다. 여기서는 검증·재검토·책임을 학습 목적으로 보완했습니다. 결정을 바꾸면 새 ADR을 쓰고 이 기록을 `superseded by ADR-...`로 연결합니다.

## 6. 적용 과제

도입 사례의 A와 B를 각각 가장 설득력 있게 옹호하는 문장을 두 개씩 쓰세요. 이후 ‘현재는 한 프로세스, 다음 달 네 개 확정, 게시물 삭제는 모든 사용자 화면에서 즉시 반영되어야 함’으로 조건을 바꿔 봅니다. 단순 TTL 캐시만으로 충족 가능한지, ‘즉시’의 정확한 의미는 무엇인지 먼저 질문하세요.

10~15줄의 ADR을 작성하되 필수 조건, 불확실성, 선택하지 않은 대안의 장점, 자신의 결정을 버릴 조건을 포함하세요. 특정 제품을 고르는 것보다 계약을 분명히 하는 것이 목표입니다.

## 7. 퀴즈

Q1·Q2 각 1점, Q3·Q4 각 2점, Q5 4점. 8점 이상이면 다음 편을 권합니다.

### Q1
‘Redis가 업계 표준이므로 사용한다’에 가장 부족한 것은 무엇인가요? A. 유행하는 제품명 B. 현재 요구와 선택 비용을 연결하는 근거 C. 코드 줄 수.

### Q2
ADR 결정을 뒤집었습니다. 기존 문서를 삭제해야 하나요, 대체 상태와 새 ADR 링크를 남겨야 하나요? 이유도 한 문장 적으세요.

### Q3
한 팀이 ‘운영비 30점, 응답 속도 40점’을 합산해 개인정보 격리 요구를 위반하는 대안을 선택했습니다. 절차의 오류와 수정 방법을 설명하세요.

### Q4
하나의 키를 연속 조회하는 로컬 실험에서 캐시가 빨랐습니다. 실제 서비스 적용을 결정하기에 부족한 정보 두 가지와 이유를 적으세요.

### Q5
프로세스 네 개에서 같은 목록을 제공해야 하고, 30초의 오래된 데이터는 허용되며, Redis 운영자는 없습니다. 로컬 캐시·Redis·캐시 없음 중 하나를 선택하는 짧은 ADR을 쓰세요. 모르는 사실은 가정으로 표시하고 장점·단점·검증·재검토 조건을 포함하세요.
