# 1-2. 정답과 해설

[본문](02-design.md)

## Q1 — B, 1점

보급 정도는 생태계·채용·도구 지원을 판단하는 자료일 수 있지만 해당 시스템에 필요한지를 대신하지 못합니다. 제약과 비교한 장단점이 필요합니다. 복습: 본문 1~2절.

## Q2 — 기존 기록을 남긴다, 1점

대체 상태와 새 기록을 연결해야 과거 코드와 당시 판단을 이해할 수 있습니다. 현재 결정만 남기면 예전 구현이 왜 생겼는지 알 수 없습니다. 선택과 이유를 모두 맞히면 1점. 복습: 3절 A, 5절.

## Q3 — 필수 제약을 먼저 확인, 2점

보안·개인정보 격리와 같은 필수 요구는 다른 장점의 점수로 상쇄할 대상이 아닙니다(1점). 필수 조건을 만족하는 후보만 남긴 뒤 비용과 선호를 비교해야 합니다(1점). 실제로 필수 조건을 바꾸려면 요구 소유자와 별도의 근거 있는 결정이 필요합니다. 복습: 1~2절.

## Q4 — 대표성·일관성·장애 조건, 2점

다음 중 타당한 정보와 이유를 두 가지 연결하면 각 1점입니다.

- 실제 키 분포·적중률: 반복 한 키 실험은 대부분 적중하므로 캐시 효과를 과장합니다.
- 값의 크기와 키 수: 메모리 사용과 퇴출 비용이 달라집니다.
- 갱신 빈도·허용 신선도: 읽기가 빨라도 틀린 값을 오래 보여줄 수 있습니다.
- 동시성과 워커 수: 로컬 캐시 복제와 갱신 차이가 발생할 수 있습니다.
- 원본 처리 여유: 미스·캐시 장애 때 부하를 견디는지 알아야 합니다.

복습: 2절·4절. 단순히 “운영에서 테스트”라고 쓰면 무엇을 검증하는지 부족합니다.

## Q5 — 조건에 맞는 ADR, 4점

예시: ‘현재 지연·원본 부하가 목표를 만족한다는 가정하에 캐시를 추가하지 않는다. 별도 운영 서비스나 네 프로세스의 무효화 규칙을 만들지 않는 이익이 있지만 반복 조회 비용은 유지된다. 대표 부하에서 원본 조회 지연과 반복 키 비율을 측정한다. 목표 지연을 넘고 반복 조회가 주원인이면 30초 신선도 계약을 만족하는 로컬 캐시를 먼저 비교하고, 공유 갱신·메모리 요구가 커지면 Redis 운영 비용도 검토한다.’

이는 가정을 포함한 예시이지 측정이 끝난 실제 권고가 아닙니다. 이미 원본이 포화 상태라면 다른 판단이 필요합니다. 네 프로세스가 있다고 반드시 Redis여야 하는 것은 아닙니다.

| 1점씩 | 확인할 내용 |
| --- | --- |
| 요구·가정 | 30초 허용과 운영 역량을 반영하고 모르는 성능을 가정으로 표시 |
| 대안 비용 | 선택의 이익과 단점을 각각 설명 |
| 검증 | 실제 요구에 맞는 부하·신선도·장애 확인 방법 |
| 재검토 | 어떤 사실이 달라지면 결정을 바꿀지 구체적으로 제시 |

복습: 5절. 틀린 답은 특정 제품을 고른 답이 아니라 근거 없이 필수 조건을 무시하거나 단점을 숨기는 답입니다.
