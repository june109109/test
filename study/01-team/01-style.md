# 1-1. 코딩 스타일이 다를 때 합의하기

[전체 계획](../PLAN.md) · [정답과 해설](01-style-answers.md)

예상 학습 시간: 읽기 20분, 적용 과제 15분, 퀴즈 15분. 선수 지식은 간단한 Python 함수와 코드 리뷰의 개념입니다. PR은 코드 변경을 제안하고 검토받는 단위인 Pull Request를 뜻합니다.

## 학습 목표

이 편을 마치면 다음을 할 수 있어야 합니다.

1. 리뷰 의견을 취향, 합의된 규칙, 유지보수 문제, 동작·호환성 문제로 분류한다.
2. 동료의 코드를 바꾸라고 요청할 때 영향과 근거, 필수 여부를 설명한다.
3. 포매터·린터·사람의 리뷰가 각각 해결할 수 있는 문제를 구분한다.
4. 스타일을 통일할 때 얻는 이익과 전환 비용을 함께 계산해 적용 범위를 정한다.

## 1. 먼저 판단해 보기

동료가 작성한 함수입니다. `users`는 리스트이고 각 항목에 `id`와 `active`가 있다고 가정합니다.

```python
def active_user_ids(users):
    result = []
    for user in users:
        if user["active"]:
            result.append(user["id"])
    return result
```

리뷰어는 다음 코드가 더 파이썬답다며 변경을 요청합니다.

```python
def active_user_ids(users):
    return [user["id"] for user in users if user["active"]]
```

팀에 comprehension 사용 규칙은 없습니다. 기존 코드에는 두 형태가 모두 있고, 성능 문제가 보고된 적도 없습니다.

메모해 보세요. 변경이 필수인가요? 두 코드 중 무엇이 더 읽기 쉽다는 것을 어떤 방식으로 설명할 수 있나요? 지금 PR을 막을 만큼 중요한가요?

두 형태 모두 이 입력 가정에서 같은 값을 돌려줍니다. 짧은 변환에는 comprehension이 간결하지만, 팀원의 익숙함이나 곧 추가될 예외 처리에 따라 명시적인 반복문이 이해하기 쉬울 수도 있습니다. ‘파이썬답다’만으로 변경을 강제할 근거는 부족합니다. 성능 차이가 의사결정에 중요하다면 실제 입력과 실행 환경으로 측정해야 합니다.

## 2. ‘스타일’이라는 말 안에 서로 다른 문제가 있다

| 종류 | 예시 | 확인할 근거 | 기본 대응 |
| --- | --- | --- | --- |
| 표현상 취향 | 한 가지 따옴표 선호, 짧은 반복문과 comprehension | 팀 규칙·주변 코드, 구체적인 읽기 어려움 | 비차단 제안, 규칙이 없으면 작성자 선택 존중 |
| 합의된 형식 | 포매터 결과, 들여쓰기, 정해진 import 규칙 | 저장소 설정, 문서, CI | 자동 검사로 처리하고 예외는 사유 기록 |
| 이해·변경 비용 | 단위를 알 수 없는 변수, 지나친 중첩, 역할이 섞인 함수 | 오독 가능한 지점, 변경 시 영향 범위 | 설명·예시·작은 대안으로 개선 제안 |
| 동작·호환성 | 외부 JSON 키 이름 변경, 예외 누락, 계산 순서 변경 | API 계약, 호출부, 테스트, 장애 사례 | 취향으로 취급하지 않고 별도로 검증 |

같은 변경도 문맥에 따라 분류가 달라집니다. 내부 지역 변수 `userId`를 `user_id`로 바꾸는 일과 외부 API의 JSON 키를 바꾸는 일은 비용이 다릅니다. 후자는 기존 클라이언트를 깨뜨릴 수 있습니다.

‘읽기 쉽다’도 구체화할 수 있습니다. 예를 들어 `timeout = 30`은 단위가 불명확하지만 `timeout_seconds = 30`은 초 단위임을 드러냅니다. 반면 `items`를 아무 설명 없이 자신이 좋아하는 이름으로 바꾸라는 요청은 근거가 약합니다. 이름이 항상 정답 하나를 갖는 것은 아니므로 읽는 사람이 무엇을 오해하는지 말해야 합니다.

## 3. 실제 문서들은 무엇을 권하는가

다음은 공개 문서에서 확인한 입장입니다. **인용문이 아니라 요약**이며, 뒤의 반박·재반박은 학습을 위해 구성합니다. 조직의 가이드를 모든 팀에 그대로 적용해야 한다는 뜻은 아닙니다.

| 출처 | 확인한 주장 | 해당 주장으로 뒷받침할 수 있는 판단 | 주장 범위의 한계 |
| --- | --- | --- | --- |
| PEP 8 [S1] | 스타일 가이드보다 프로젝트 내부의 일관성, 그보다 모듈·함수 내부의 일관성이 중요하다. 가이드 준수만을 위해 하위 호환성을 깨뜨리지 말라. | 외부 규칙을 들고 와 기존 API를 무작정 바꾸지 않는다. | 기존 관행에 문제가 있어도 영구히 유지하라는 주장은 아니다. |
| Google 코드 리뷰 기준 [S2] | 기술적 사실·데이터를 취향보다 우선한다. 규칙과 기존 스타일이 없으면 작성자 스타일을 받아들인다. 완벽하지 않아도 전체 코드 건강을 개선하는 변경을 승인하는 쪽을 선호한다. | 사소한 선호로 개선 PR을 장기간 막지 않는다. | 기능·설계·품질 문제까지 무조건 승인하라는 뜻은 아니다. |
| Black 스타일 문서 [S3] | 일관성·가독성·작은 diff를 목표로 하며 설정 선택지를 의도적으로 제한한다. | 반복되는 형식 논의를 도구에 맡겨 리뷰 자원을 아낀다. | 포매터는 업무 규칙과 API 설계를 판단하지 못한다. 초기 도입에는 큰 diff가 생길 수 있다. |

세 입장은 함께 적용할 수 있습니다. 기존 코드를 존중하면서 앞으로의 형식은 자동화하고, 자동화되지 않는 표현 문제는 근거와 중요도에 따라 리뷰합니다.

### 쟁점 A. 규칙이 없을 때 작성자에게 맡겨야 할까

**입장:** Google 지침처럼 기존 관행도 없고 품질상 차이를 제시할 수 없다면 작성자의 선택을 존중한다. 사소한 선택 때문에 전달이 지연되는 비용을 줄일 수 있다. [S2]

**반박 — 학습용 구성:** 매번 각자 선택하면 비슷한 코드가 여러 형태로 퍼지고, 새 동료가 배워야 할 패턴이 늘어난다. 장기적인 일관성 비용이 누적될 수 있다.

**재반박 — 학습용 구성:** 실제로 반복되는 문제는 팀 규칙으로 논의할 수 있다. 다만 아직 합의하지 않은 규칙을 한 사람의 PR에서 갑자기 필수 조건으로 만들지는 않는다. 현재 PR은 진행하고 대표 사례를 모아 다음 규칙을 정한다.

**선택 기준:** 일회적인 표현 차이는 비차단 제안이 적절하다. 여러 PR에서 같은 논쟁이 반복된다면 규칙화의 이익이 커진다. 단, 보안·호환성·명확한 오독 위험은 ‘규칙이 없다’는 이유로 넘기지 않는다.

### 쟁점 B. 포매터로 통일하면 문제가 해결될까

**입장:** Black처럼 일부 선택권을 줄이면 표현이 예측 가능해지고, 형식에 쓰는 리뷰 시간을 줄일 수 있다. [S3]

**반박 — 학습용 구성:** 오래된 저장소에 일괄 적용하면 변경량이 커지고, 진행 중인 브랜치와 충돌할 수 있다. 수식·표·도메인 특수 코드에서는 자동 배치가 덜 읽기 쉬울 수도 있다.

**재반박 — 학습용 구성:** 일회성 전환 비용과 이후 절약을 나눠 판단해야 한다. 팀 규모가 작고 병행 작업이 적다면 독립적인 포맷 PR로 빠르게 전환할 수 있다. 병행 작업이 많다면 적용 디렉터리를 나눠 점진적으로 전환할 수 있다. 예외는 좁은 범위와 이유를 남긴다.

**선택 기준:** 반복 논쟁이 많고 도구가 언어·파일을 잘 지원하면 자동화가 유리하다. 다만 버전·설정·실행 범위를 고정하지 않으면 개발자마다 다른 결과가 나온다. 예외와 도구 업데이트에도 유지 비용이 든다.

### 쟁점 C. 기존 스타일을 언제 버려야 할까

**입장:** PEP 8은 주변 코드와의 일관성을 중요하게 보며, 가이드에 맞추기 위한 호환성 파괴를 경계한다. [S1]

**반박 — 학습용 구성:** 과거의 코드가 복잡하고 실수를 자주 유발하는데 일관성만 유지하면 개선이 불가능해진다. ‘원래 이렇게 했다’가 품질 판단을 대신할 수는 없다.

**재반박 — 학습용 구성:** 일관성은 변경 비용을 평가하는 기준이지 변경 금지가 아니다. 결함이 확인되거나 팀의 도구·요구가 바뀌었다면 수정할 수 있다. 이때 동작 변경과 기계적 형식 변경을 분리하고, 공개 인터페이스는 별도 호환 계획을 세운다.

**선택 기준:** 단순 미관에는 보수적으로 접근한다. 실제 오독·반복 결함·변경 난이도가 확인되면 국소적 개선부터 시도하고 효과를 관찰한다. 모든 파일을 한 번에 ‘현대화’하는 비용도 함께 적는다.

## 4. 포매터, 린터, 리뷰는 무엇이 다른가

포매터는 코드를 정해진 모습으로 배치하는 도구입니다. 린터는 정적 규칙으로 의심스러운 코드나 규칙 위반을 찾습니다. 코드 리뷰는 변경의 의도와 업무 맥락까지 검토합니다. 한 제품이 여러 역할을 제공할 수 있지만 역할 자체는 다릅니다.

| 방법 | 잘하는 일 | 얻는 이익 | 감수할 단점·관리 비용 | 선택할 때 |
| --- | --- | --- | --- | --- |
| Formatter | 공백·줄바꿈·괄호 배치 | 일관된 출력, 반복 논의 감소 | 초기 diff, 예외 처리, 버전 변경 영향 | 결과를 기계적으로 정할 수 있는 형식 |
| Linter | 미사용 이름, 위험한 패턴, 설정한 규칙 | 빠르고 반복 가능한 피드백 | 오탐·누락, 규칙 간 충돌, 설정 유지 | 구문·정적 정보로 판단 가능한 문제 |
| 사람의 리뷰 | 도메인 의미, API 계약, 설계·명명 의도 | 문맥에 맞는 판단과 지식 공유 | 시간, 편향, 리뷰어 사이의 불일치 | 도구만으로 의도·영향을 알 수 없는 문제 |
| 짧은 팀 가이드 | 도구 밖의 원칙, 예외·결정권 | 반복되는 판단의 예측 가능성 | 문서 노후화, 과도한 규칙 | 실제로 자주 부딪히는 공통 문제 |

린터의 일부 경고는 취향이 아니라 실제 결함 가능성입니다. ‘도구가 지적했다’만으로 중요도를 결정하지 말고 규칙이 방지하려는 문제를 확인합니다. 반대로 도구 검사를 통과했다고 기능이 맞는 것도 아닙니다.

**도입 설계 포인트:** 한 저장소의 동일 파일에 서로 충돌하는 포매터를 적용하지 않습니다. 포매터와 린터의 중복 규칙은 호환되도록 맞춥니다. CI와 로컬에서 같은 버전·설정을 사용하고, 예외에 이유와 범위를 남깁니다. 이 편에서는 도구 설치나 저장소 설정 변경을 실행하지 않습니다.

## 5. 의견 충돌을 해결하는 순서

1. **원하는 효과를 말한다.** ‘내 스타일이 좋다’ 대신 ‘반환 타입을 오해할 여지가 있다’처럼 영향부터 적습니다.
2. **문제 종류와 근거를 확인한다.** 규칙이 있는지, 외부 계약을 바꾸는지, 동작 차이나 실제 오독 사례가 있는지 봅니다.
3. **필수 여부를 표시한다.** `[필수]`, `[제안·비차단]`, `[질문]` 등 팀이 합의한 표기를 씁니다. 표기만 붙이지 말고 이유를 적습니다.
4. **현재 변경에 맞는 범위를 정한다.** 기능 PR에 저장소 전체 포맷 변경을 끼워 넣으면 핵심 변경을 검토하기 어려워질 수 있습니다.
5. **반복되면 짧게 대화하고 결론을 남긴다.** 예를 들어 두 번의 댓글 왕복 후에는 짧은 대화로 바꿀 수 있습니다. 이 횟수는 학습용 제안이며 표준 규칙이 아닙니다.
6. **합의가 안 되면 정해진 책임자에게 판단을 요청한다.** 대안·근거·남은 불확실성을 전달하고 결정·적용 범위·재검토 조건을 PR에 기록합니다. 직급 자체를 기술 근거로 쓰지 않습니다.

예를 들어 다음 두 댓글은 받아들이는 사람이 해야 할 일을 다르게 만듭니다.

> 모호한 요청: “이렇게 쓰면 안 예뻐요. comprehension으로 바꿔 주세요.”

> 구체적인 제안: “[제안·비차단] 여기서는 조건 하나와 값 변환 하나라 comprehension으로 줄여도 읽기 쉽겠습니다. 다만 현재 반복문도 동작과 이해에 문제가 없어 이번 PR의 필수 수정은 아닙니다.”

> 동작 문제의 지적: “[필수] `userId` 응답 키를 `user_id`로 바꾸면 현재 앱이 값을 읽지 못합니다. 기존 응답 계약을 유지하거나 별도 버전 전환 계획이 필요합니다.”

명시적인 반복문을 선택한 이유가 디버깅·추후 분기 추가라면 그 이유도 존중하되, 아직 필요하지 않은 미래를 근거로 과도하게 복잡한 코드를 만들 필요는 없습니다.

## 6. 적용 과제: 팀 합의안 한 장 만들기

다음은 가상 상황입니다. 정답을 먼저 정하지 말고 제약을 사용해 선택하세요.

- Python 개발자 6명이 일합니다.
- 저장소에 포매터 설정은 없습니다. 코드 스타일은 두세 종류가 섞여 있습니다.
- 최근 PR 다섯 개에서 따옴표·줄바꿈 의견이 반복됐습니다.
- 동시에 진행 중인 큰 기능 브랜치가 세 개 있고 이번 주 릴리스가 있습니다.
- 외부 API 키는 camelCase로 문서화되어 있습니다.

아래 항목을 채우세요.

| 항목 | 작성할 내용 |
| --- | --- |
| 해결하려는 문제 | 무엇 때문에 시간이 들거나 오해가 생기는가 |
| 이번 주 조치 | 즉시 적용할 규칙과 이후로 미룰 변경 |
| 전환 방식 | 일괄·점진 중 선택, 또는 다른 방법과 근거 |
| 변경 경계 | 내부 코드·외부 API·생성 파일의 적용 범위 |
| 비용 | 충돌, 학습, 예외, CI 설정·버전 유지 비용 |
| 확인 방법 | 리뷰 댓글·대기 시간·충돌 사례 등 관찰할 정보 |
| 재검토 조건 | 언제 어떤 증거를 보고 규칙을 바꿀 것인가 |

후보 지표를 하나의 점수로 사람을 평가하는 데 사용하지 마세요. 리뷰 시간이 줄어도 결함 누락이나 질문 위축이 늘면 목적을 달성했다고 보기 어렵습니다. 전후 비교도 PR 크기·난이도·팀 일정의 영향을 받습니다. 작은 표본으로 포매터의 인과 효과를 단정하지 않습니다.

## 7. 이해도 퀴즈

해설을 닫은 채 풉니다. 1·2번 각 1점, 3·4번 각 2점, 5번 4점으로 총 10점입니다. **8점 이상이면서 4번의 호환성 문제를 설명할 수 있으면** 다음 편으로 진행하는 것을 권합니다. 이는 학습용 기준입니다.

### Q1. 규칙이 없을 때

팀 규칙과 주변 코드의 관행이 없고, 동작·이해상의 문제도 제시되지 않았습니다. 리뷰어가 작은따옴표를 좋아한다는 이유로 큰따옴표를 바꾸라고 합니다. 가장 적절한 대응은 무엇인가요?

A. 리뷰어가 승인권자이므로 항상 바꾼다.<br>
B. 작성자 선택을 존중하고, 필요하면 비차단 제안이나 별도 규칙 논의를 한다.<br>
C. 스타일 이야기는 어떤 경우에도 리뷰에서 금지한다.<br>
D. 그 PR에서 저장소 전체를 작은따옴표로 바꾼다.

### Q2. 역할 연결

다음 세 문제를 주로 맡길 수단을 formatter, linter, 사람의 리뷰에서 각각 고르세요. 실제 제품의 기능 중복은 허용하되 기본 역할을 기준으로 답합니다.

1. 같은 코드의 줄바꿈이 개발자마다 다르다.
2. 사용하지 않는 import가 남았다.
3. 고객이 취소한 주문을 매출로 집계하는 로직이 들어왔다.

### Q3. 줄 길이 논쟁

저장소는 Black의 기본 줄 길이 88을 사용합니다. 새 리뷰어는 PEP 8에 79가 있으니 이번 버그 수정 PR부터 79로 강제하고 전체 파일을 다시 배치하자고 합니다.

권고할 조치와 근거를 각각 하나 이상 적으세요. ‘88이 객관적으로 우월하다’는 주장만으로 답하지 마세요.

### Q4. 이름만 바꾼 PR?

공개 API의 응답이 `{"userId": 7}`에서 `{"user_id": 7}`로 바뀌었습니다. 작성자는 Python 이름 규칙에 맞춘 순수 스타일 변경이라 테스트가 필요 없다고 합니다.

어떤 종류의 변경인지, 무엇을 확인해야 하는지 답하세요.

### Q5. 합의안과 댓글 작성

위 적용 과제의 6인 팀에서 포매터를 도입할지 결정하세요. 다음 네 항목을 포함해 8~12문장으로 작성합니다.

1. 해결할 문제와 선택의 근거
2. 전환 범위·시기와 감수할 비용
3. 현재 PR에 남길 필수 또는 비차단 리뷰 댓글
4. 효과를 확인하는 방법과 재검토 조건

특정 도구 이름이나 일괄·점진 중 어느 쪽을 고르는지가 정답을 결정하지 않습니다.

이제 [정답과 해설](01-style-answers.md)을 열어 자신의 근거와 비교하세요.

## 8. 참고 자료와 읽을 부분

아래 문서의 원문 소스를 2026-10-01에 확인했습니다. 링크의 기본 브랜치 문서는 이후 바뀔 수 있습니다. 문서의 규범적 권고를 생산성 효과가 입증된 실험 결과로 해석하지 않습니다.

- **[S1] PEP 8 — Style Guide for Python Code**: [공식 문서](https://peps.python.org/pep-0008/), [확인한 원문 소스](https://github.com/python/peps/blob/main/peps/pep-0008.rst). `A Foolish Consistency is the Hobgoblin of Little Minds`, `Maximum Line Length`, `Naming Conventions`를 읽습니다. 일관성의 범위, 하위 호환성, 팀의 줄 길이 합의를 뒷받침합니다.
- **[S2] Google Engineering Practices — The Standard of Code Review**: [문서](https://google.github.io/eng-practices/review/reviewer/standard.html), [확인한 원문 소스](https://github.com/google/eng-practices/blob/master/review/reviewer/standard.md). `Principles`, `Resolving Conflicts`와 앞부분의 승인 기준을 읽습니다. 취향과 설계의 구분, 비차단 의견, 합의·상향 논의 근거입니다.
- **[S3] Black — The Black code style**: [공식 문서](https://black.readthedocs.io/en/stable/the_black_code_style/current_style.html), [확인한 원문 소스](https://github.com/psf/black/blob/main/docs/the_black_code_style/current_style.md). `Code style`, `How Black wraps lines`, `Line length`를 읽습니다. 설정을 제한하는 이유, diff, 기본 줄 길이 88의 출처입니다.

다음 편은 **1-2. 설계 의견이 다를 때 결정하기**입니다. 표현상의 선호에서 한 단계 나아가, 둘 다 그럴듯한 설계 중 어떤 것을 선택하고 언제 다시 판단할지 다룹니다.
