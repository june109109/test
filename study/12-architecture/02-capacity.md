# 12-2. 트래픽·데이터·서버 수 추정

[목차](../README.md) · [정답·해설](02-capacity-answers.md)

예상 65분. 목표: 단위와 가정이 보이는 계산으로 초기 용량 범위를 잡고 실측으로 교정합니다.

## 1. 계산의 입력

다음은 모두 교육용 가정입니다. DAU100만명, 하루1인당 메인5회, peak/평균8배, 방문30%는 로그인, 방문마다 공개 API1회·로그인 방문만 개인화 API1회, 공개 API의 CDN hit90%를 가정합니다.

```text
일 페이지뷰 = 1,000,000 × 5 = 5,000,000 /day
평균 페이지 RPS = 5,000,000 / 86,400 ≈ 57.9 /s
피크 페이지 RPS = 57.9 × 8 ≈ 463 /s
공개 원본 API = 463 × (1 - 0.9) ≈ 46.3 /s
개인화 원본 API = 463 × 0.3 ≈ 138.9 /s
원본 API 합계 ≈ 185.2 /s
```

CDN hit는 해당 공개 API 경로의 값입니다. 개인화에 같은90%를 적용하지 않습니다. 봇·앱 재시도·refresh·어드민·검색 등 제외한 트래픽은 별도 예산입니다.

## 2. 평균의 오차와 민감도

피크8배는 측정 전 가정입니다. 이벤트 때20배라면 원본 부하는 약463/s로 늘어납니다. CDN hit가90%→50%로 내려가면 피크463 기준 공개 원본231.5 + 개인화138.9 =370.4/s입니다. 평균 트래픽보다 cache miss 사건이 서버 수에 더 큰 영향을 줄 수 있습니다.

계산표에 입력의 낮음/기준/높음과 확신도를 적어 민감한 가정을 우선 검증합니다. 페이지뷰와 API수·시도수를 분리하지 않으면 두 배·세 배 오차가 쉽게 생깁니다.

## 3. 대역폭과 저장량

전체 전송량을 방문당200kB(십진 단위)라고 가정하면 하루 약1TB, 피크463/s에서는 약92.6MB/s ≈741Mb/s입니다. 이것은 사용자에게 전달하는 전체 edge payload 근사이며 원본 서버 대역폭과 같지 않습니다. 압축·이미지·정적 파일 캐시·TLS·재전송도 따로 봅니다.

콘텐츠 하루10만건×본문/메타데이터2kB면200MB/day, 365일73GB의 논리 데이터입니다. 복제3개면 본문만219GB입니다. 인덱스·WAL·backup·여유·이미지 원본·보관 삭제 정책은 추가입니다. 요청량과 저장량은 다른 계산입니다.

## 4. 서버 수의 조건부 추정

동일 workload에서 인스턴스1개가 목표 지연·오류를 지키며250RPS를 처리한다고 **가정**합니다. 운영 사용률60%를 택하면 계획 용량은150RPS/개입니다. N-1 한 대 장애에서도185.2RPS를 받으려면 `(N-1)×150 >=185.2`이므로 최소3개입니다.

250RPS는 이번 로컬 실험에서 얻은 값이 아닙니다. 실제 workload·quota·DB·network로 검증해야 합니다. 3개라는 숫자도 AZ 단위 장애나 CDN 대량 miss를 모두 감당한다는 의미는 아닙니다. 배포 때 추가 인스턴스의 DB 연결도 계산합니다.

## 5. 적용 과제

CDN hit50%, peak계수20배가 동시에 발생하면 원본 요구량을 다시 구하세요. 최소 서버 수·DB/네트워크·유입 제한 중 무엇을 먼저 재검토할지 설명합니다.
