# 12-4. 우리 스택의 처리 한도 계산

[목차](../README.md) · [정답·해설](04-stack-limits-answers.md)

예상 65분. 목표: 워커×스레드라는 숫자를 RPS로 오해하지 않고, 자원별 점유량의 최솟값과 실측을 결합합니다.

## 1. 가정이 붙은 한 인스턴스

이 편은12-2의250RPS 가정을 다른 수식으로 ‘입증’하지 않습니다. 별도의 설명용 자원 모델입니다: CPU시간 예산2코어 상당, 워커2개, 워커당 AnyIO토큰20, DB풀8·overflow0, 요청당 평균CPU5ms, 요청80%가 동기SDK100ms, 요청50%가 DB연결20ms를 점유한다고 가정합니다.

같은 요청이 SDK와 DB를 모두 사용할 수도 있습니다. 평균 확률·점유 시간을 자원별로 계산하고, 하나의 스레드 안에서 두 작업을 연속 수행한다면 스레드 점유에는 두 시간이 모두 들어간다는 점에 주의하세요. 아래 스레드 계산은 SDK만 그 토큰을 사용한다는 단순화입니다.

## 2. 거친 상한 후보

| 자원 | 단순 근사 | 후보 상한 |
| --- | --- | --- |
| CPU | 2 CPU-s/s ÷0.005 CPU-s/request | 400request/s |
| AnyIO토큰 | 40 ÷(0.8×0.1s/request) | 500request/s |
| DB연결 | 16 ÷(0.5×0.02s/request) | 1600request/s |

이 모델의 가장 작은 후보는CPU400/s입니다. 목표 지연과 여유를 위해 예를 들어60%만 쓰면240/s를 계획 후보로 잡을 수 있지만 **측정으로 검증한 서비스 용량이 아닙니다**. 서로 경쟁하는 자원·분포·락·네트워크·burst·GC·발생기·동시 요청 스케줄을 단순화했습니다.

CPU5ms를 벽시계200ms와 혼동하지 않습니다. 요청이 기다리는 시간이 길다고 그만큼CPU를 점유하는 것은 아닙니다. 반대로 루프에서 동기100ms를 기다리면 CPU는 낮아도 각 워커의 루프 진행은 직렬화됩니다.

## 3. 동시 요청 수는 별도 질문

워커2×토큰20=40은 해당 동기 오프로딩의 실행 토큰이지 HTTP요청 최대40이라는 뜻이 아닙니다. 많은 coroutine이 대기할 수 있지만 무한 수락은 메모리·deadline·오류를 악화시킵니다. 유입 제한과 bounded queue를 함께 설계합니다.

`max_pool_connections`도4-6의 boto3 구현에서는 hard concurrency limit이 아닙니다. 의도한 SDK 동시성 제한은 앱 admission으로 명시하고, 요청 timeout 뒤에도 스레드가 남는다면 실제 작업 수명에 맞춰 제한합니다.

## 4. 전체 DB 예산과 배포

컨테이너3개×워커2×DB풀8이면 최대48연결입니다. 배포 중2개 컨테이너가 추가 공존하면80입니다. 배치·관리 연결을 더하고 DB 상한·성능과 비교합니다. 한 워커가 DB두개에 각각 풀을 가지면 DB별로 따로 셉니다.

트래픽이 균등하지 않을 수도 있습니다. keep-alive·hot key·sticky session 때문에 한 워커가 먼저 포화될 수 있어 전체 평균과 워커별 지표를 함께 봅니다.

## 5. 검증 계획

저부하에서CPU시간·DB/SDK점유 시간을 먼저 측정하고, 예상 병목 근처로 도착률을 단계적으로 올립니다. 한 변수만 변경하여 최솟값이 실제로 이동하는지 봅니다. 스레드를40→80으로 늘렸는데 CPU가 먼저 포화라면 이익이 없거나 더 나빠질 수 있습니다.

## 6. 적용 과제

CPU가2.5ms로 줄고 SDK평균이200ms로 늘면 상한 후보를 다시 계산하세요. 풀을 늘릴지, 요청 기능을 줄일지, 하류 최적화를 할지 근거를 적습니다.

### Python 트랙 보강: FastAPI 계산의 완료 조건

설계서에는 ①HTTP 진행 요청 수 ②async task 수 ③실제 AnyIO 실행 토큰 ④DB세션 점유 ⑤실제 외부 호출 수 ⑥완료 RPS를 별도 단위로 적습니다. 예를 들어 요청 중DB를 쓰는 비율과 DB점유시간이 작다면 전체 동시HTTP요청보다 DB풀은 훨씬 작아도 됩니다. 반대로 transaction을 쥔 채SDK를 기다리면 DB점유시간이 길어집니다.

평균식은 초기 가설입니다. 피크·긴 꼬리·워커별 불균형·배포 공존·한 대 장애에서 목표 지연을 지키는지11장 실험으로 검증한 뒤 용량으로 승인합니다. ‘worker×40이면 그만큼 요청을 받을 수 있다’는 단일 계산으로 끝내지 않습니다.
