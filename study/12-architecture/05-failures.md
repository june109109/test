# 12-5. 실패·일관성·운영 설계

[목차](../README.md) · [정답·해설](05-failures-answers.md)

예상 60분. 목표: 구성요소 고장을 사용자 결과로 연결하고, 정확성·가용성·복잡도의 선택을 명시합니다.

## 1. 정상 경로 그림만으로는 부족하다

개인화 서비스가 죽었을 때 공개 메인은 보일 수 있어도 관리자 게시 권한을 캐시된 허용으로 계속 처리하면 위험할 수 있습니다. 기능마다 fail-open/closed, stale 허용, retry, deadline을 다르게 정합니다.

| 실패 | 사용자에게 보이는 동작 | 방어·복구 | 비용 |
| --- | --- | --- | --- |
| 개인화 지연 | 공개 목록 fallback | 짧은 예산·격리 | 개인화 품질 감소 |
| Redis 장애 | 제한된 원본 조회/허용 stale | admission·warmup | 일부 요청 거절·오래된 정보 |
| DB writer 장애 | 게시 중단, 공개 읽기는 정책 범위 유지 | failover·복구·상태 확인 | 변경 지연·불명확 commit |
| 검색 색인 지연 | 갱신 지연 표시/제한된 결과 | lag경보·replay | 최신성 손실 |
| 계정 제공자 장애 | 기존 세션 정책 유지, 새 로그인 제한 | 재시도 예산·안내 | 신규 사용자 로그인 불가 |
| 잘못된 배포 | 이전버전/forward fix | canary·오류율·호환성 | 중복 자원·복구 복잡도 |

‘모든 장애에 캐시로 응답’은 삭제된 게시물·권한·개인정보에는 적절하지 않을 수 있습니다. stale 상한과 콘텐츠 종류를 분리합니다.

## 2. 연쇄 장애 막기

캐시가 죽자 모든 요청이 DB로 향하고, DB가 느려지자 앱이 재시도하고, 큐가 늘어 메모리가 고갈될 수 있습니다. bounded queue·동시성·retry budget·deadline·load shedding을 조합합니다. 장애 시 원본 조회 비율이 어떻게 바뀌는지12-2의 민감도와 연결합니다.

Google SRE의 과부하 논의는 자원이 고갈된 뒤 무조건 받아들이는 대신 유용한 처리를 유지할 수 있도록 부하를 제한하는 설계의 근거가 됩니다. 우선순위가 낮은 모듈을 생략해 핵심 기능을 유지할 때, 그 결과를 성공으로 볼지 품질 저하로 따로 측정할지 정합니다.

## 3. 일관성의 사용자 의미

일반 뉴스60초 지연과 긴급 삭제60초 지연은 결과가 다릅니다. 게시/삭제 버전, 무효화 확인, CDN캐시·앱캐시·검색의 서로 다른 경로를 설계합니다. 캐시 TTL 하나가 모든 복사본의 삭제를 확인해 주지는 않습니다.

관리자 권한 변경과 콘텐츠 편집은 인증·인가·감사 기록을 갖추고, source of truth를 하나로 정합니다. 결제·회원 같은 별도 도메인이 있다면 메인 페이지와 장애 영역을 무조건 공유하지 않습니다.

## 4. 백업과 복원

복제는 실수로 삭제한 데이터도 빠르게 전파할 수 있어 백업과 같지 않습니다. RPO는 허용 데이터 손실 시간, RTO는 복구 목표 시간입니다. 백업 존재 확인 외에 실제 복원·권한·암호화 키·외부 의존성·복구 후 정합성을 시험해야 합니다.

관측에는 사용자 오류/지연·게시 반영 지연·큐 lag·원본 부하·복구 진행을 넣습니다. 알림에는 누가 어떤 조치를 할지 연결합니다. 대시보드가 많아도 대응 경로가 없으면 운영 준비가 아닙니다.

## 5. 적용 과제

Redis와 개인화가 동시에 느려지는 사건을30초·5분·1시간 시점으로 나누어 사용자 경험·유입 제한·복구·알림을 적으세요. 실제 고장 주입은 승인된 테스트 환경에서 별도 수행합니다.
