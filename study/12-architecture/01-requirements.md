# 12-1. 네이버 메인 요구사항 정하기

[목차](../README.md) · [정답·해설](01-requirements-answers.md)

예상 60분. 목표: 큰 서비스 이름을 구체적인 사용자 행동·제약·SLO로 바꿉니다.

## 1. 실제 네이버 구조를 맞히는 문제가 아니다

이 장은 ‘네이버 메인과 비슷한 포털’을 가정한 설계 연습입니다. 실제 네이버 트래픽·서버 수·내부 구조를 알고 있다는 주장이 아닙니다. 아직 공개되지 않은 요구를 임의로 사실처럼 채우지 않고 가정과 질문을 분리합니다.

첫 산출물은 구성도보다 요구사항 표입니다.

| 기능 | 이번 연습의 범위 | 제외/미정 |
| --- | --- | --- |
| 공개 메인 | 편집한 뉴스·인기 콘텐츠 목록 | 뉴스 전체 수집·전문 저장 |
| 개인화 | 로그인 사용자의 관심 카테고리 | 실시간 추천 모델 학습 |
| 검색 | 기존 검색 서비스로 질의 전달 | 웹 전체 크롤링/랭킹 구축 |
| 어드민 | 초안·검토·게시·감사 | 다단계 조직 결재는 추가 요구 |
| 계정 | OIDC 연동·서비스 세션 | 제공자 인증 서버 직접 구현 |

## 2. 품질을 사용자 결과로 표현

‘Redis를 쓴다’는 요구가 아니라 구현 선택입니다. ‘게시 후60초 이내 공개 메인 반영’은 측정 가능한 요구입니다. 다음은 설명용 목표이며 실제 서비스의 계약이 아닙니다.

- 공개 목록 API: 유효 요청의99.9% 성공, p99 300ms 이내를 정해진 관측창에서 확인.
- 개인화 실패 시 공개 목록으로 대체하고 로그인 상태를 잘못 표시하지 않음.
- 일반 게시 변경은60초 신선도, 긴급 삭제는 별도 빠른 무효화 경로와 목표 필요.
- 어드민 게시·권한 변경은 감사 기록과 중복 방지, 허용된 운영자만 수행.

성공이 HTTP200인지, 필수 콘텐츠가 정상인지, 빈 fallback도 성공으로 셀지 정의합니다. 클라이언트 오류·봇·예약 점검을 제외한다면 제외 기준을 명시합니다. availability와 freshness는 다른 SLI입니다.

## 3. 한 요청에 다 묶을까

서버가 공개·개인화·날씨·검색 추천을 한 번에 조합하면 클라이언트가 단순하지만 가장 느린 의존성이 전체 응답에 영향을 줍니다. 공개 shell과 선택 모듈을 분리하면 독립 캐시·실패 격리가 쉬워지지만 요청 수와 UI 상태가 늘어납니다.

| 안 | 이득 | 비용 |
| --- | --- | --- |
| 전체 서버 조합 | 일관된 한 응답·클라이언트 단순 | fan-out 지연·공개 캐시 어려움 |
| 공개/개인화 분리 | 공개 캐시·선택 기능 degradation | 추가 왕복·화면 조합 |
| BFF에서 제한된 조합 | 기기별 API·공통 정책 | BFF 병목·추가 운영 계층 |

## 4. 질문의 우선순위

트래픽·지역·콘텐츠 신선도·로그인 비율·핵심 기능·운영 인원·예산·데이터 보관부터 확인합니다. 지금 결정할 수 없는 값은 ‘가정 A’로 표시하고 값이 바뀌면 어떤 설계가 달라지는지 적습니다. 처음부터 모든 기능을 Kafka/k8s로 만드는 것이 목표는 아닙니다.

## 5. 적용 과제

한 페이지 요구사항 문서를 만드세요. 필수 기능5개 이하, 미포함 범위, SLI/SLO·신선도, 예상 부하, 장애 시 fallback, 결정이 필요한 질문3개를 적습니다. 다음 단원의 계산은 이 문서의 가정을 참조합니다.
